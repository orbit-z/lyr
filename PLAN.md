# Orbit — an Astro-like web framework with Go on the server

## Context
**Goal: Astro's developer experience, with much faster SSR.** Performance is a first-class concern: every design choice on the render path is judged by its cost per request (§4b), and the results are measured against Astro and published, with no fixed target number (§4b, milestones 9 and 11).

Build a web framework modeled on Astro, but with Go instead of JS on the server. Users write `.orbit` single-file components: a Go frontmatter block followed by an HTML template. The `orbit` CLI compiles them to plain Go code, so the Go compiler type-checks everything: props, expressions, and calls into the user's own Go packages. **Orbit is SSR-only**: every page renders per request, served by one Go binary. There is no static-site generation, by design (§12); for static sites, Astro is the better choice. The only static files are the bundled `/_orbit/*` assets and `public/`. Client JS is limited to vanilla `<script>` tags, bundled per page with esbuild's Go API, so Node isn't needed. There are **no framework islands, by design** (§12). Two Astro-style directives keep pages fast (§2.3, §3.4): `server:defer` renders a slow component in its own request after the page is sent (Astro's server islands), and `client:idle|visible|media` loads a component's scripts lazily. A language server (`orbit lsp`) gives editors Go autocompletion inside `.orbit` files by proxying to gopls. The dev server live-reloads the page on every change. On the server, Orbit is a standard `net/http` middleware: the user's own `main.go` places it in their handler chain and decides whether their custom routes or the pages take precedence. There's one middleware model: plain `net/http` middleware, which passes typed request-scoped `locals` to pages (§5b). Components can render themselves recursively.

**Spike, then docs first**: a throwaway spike (milestone 0, done) proved the riskiest mechanisms, and its findings are folded into this plan (§11). The first real deliverable is the user documentation in `docs/` (milestone 1). It acts as the spec, to be reviewed before any framework code is written.

This is a greenfield project: `/home/bertrandkhe/Projects/rs-astro` is empty. Node 25 is used only to build the VS Code extension and to run the Astro benchmark (`bench/astro-site`). Bun is used for TypeScript type checking (`orbit check`).

## 1. User project layout

```
my-site/
  go.mod               module example.com/blog; requires github.com/orbit-z/orbit;
                       `tool github.com/orbit-z/orbit/cmd/orbit` pins the CLI (§6)
  orbit.json           optional config (see §8)
  src/
    pages/             file-based routes (.orbit)
    components/        any .orbit outside pages/ is a component
    layouts/
  cmd/server/main.go   the user's server: composes Orbit's middleware with their own handlers (§5b)
  src/locals/          optional Go package `locals` declaring the typed `Locals` struct (§5b)
  internal/...         the user's normal Go code (db, content loaders, ...)
  public/              copied as-is to dist/client/
  orbit_gen/           GENERATED Go packages: decl/, impl/, app/, link/, manifest/, cmd/ (default server only)
                       (gitignored by default; committing it is supported, §6)
  .orbit/              cache: built binaries, dev assets (gitignored)
  dist/                build output: dist/server (the binary) + dist/client/ (_orbit/ assets, public/ files)
```

A fresh clone has no `orbit_gen/`, so `go build`, `go vet` and `go mod tidy` fail until `go tool orbit generate` runs. The fresh-clone and CI steps are in §6.

## 2. The `.orbit` file format

### 2.1 Example
```orbit
---
import (
    "strings"
    "example.com/blog/internal/posts"
    Layout "../layouts/Base.orbit"     // .orbit imports = components (alias required)
    Card   "../components/Card.orbit"
)

type Props struct { Title string }      // hoisted to package level

list, err := posts.All()                 // everything else = body of Render()
if err != nil { return err }
title := strings.ToUpper(props.Title)
---
<Layout title={title}>
  <h1 class="hero">{title}</h1>
  {if len(list) == 0}
    <p>No posts</p>
  {else if len(list) == 1}
    <p>One post</p>
  {else}
    {for _, p := range list}
      <Card post={p} featured><em>default slot</em></Card>
    {/for}
  {/if}
  <div set:html={orbit.HTML(list[0].Body)}></div>
  <p slot="footer">footer content</p>
</Layout>
<style> .hero { color: red } </style>
<script> document.querySelector(".hero").addEventListener("click", () => alert("hi")) </script>
<script is:inline> /* emitted verbatim */ </script>
```

### 2.2 Frontmatter rules
- It is delimited by `---` lines at the very top of the file. It's optional, and a file without it is pure template.
- Tokenize it with `go/scanner`. At brace/paren depth 0, a statement starting with `import`, `type` or `const` is **hoisted** to package level. A statement starting with `func` is hoisted only when `func` is followed by a name, or by a receiver `(…)` and then a name; an IIFE (`func() { … }()`) stays in the body. Everything else becomes the body of `Render()`, in order.
- Hoisted declarations are split between the declaration and implementation packages (§3.1): `Props` and what it depends on go to the declaration package, everything else to the implementation package.
- Hoisted declarations can't see `props`, `ctx`, `slots`, `locals` or `params`, which only exist inside `Render`. Document this.
- **Implicit identifiers** inside the body: `ctx *orbit.Ctx`, `props Props`, `slots orbit.Slots`, `locals *locals.Locals` (typed, from the user package `src/locals`, §5b; `*orbit.NoLocals` if none is declared), in **pages only** `params Params` (the typed route params, see Pages below), and the package `orbit`, which user code can use without importing it.
  - These are the only documented generated names. Every other generated identifier starts with `orbit__` (`orbit__ctx`, `orbit__props`, `orbit__slots`, `orbit__params`, `orbit__w`, `orbit__rt`, `orbit__render`, `orbit__err`, `orbit__locals`) or `Orbit__` (`Orbit__Render`). User identifiers with either prefix, and a hoisted `Render`, are rejected.
  - **Generated glue never refers to a name the user can shadow.** `render`'s parameters are private (`orbit__ctx`, `orbit__props`, `orbit__slots`, plus `orbit__w`), and the user names are bound at the top of `render` (`ctx, props, slots := orbit__ctx, orbit__props, orbit__slots`, then `locals`; a page binds `params` too: `ctx, props, slots, params := orbit__ctx, orbit__props, orbit__slots, orbit__params`). Glue uses only the private names, and imports the runtime as `orbit__rt`. The `orbit` import is emitted only in the generated packages whose user code uses it (decided by the same object-resolution scan as other imports, §3.1). So a nested `{for _, ctx := range …}` around a component call, or a local `orbit` in a nested block, can't break the generated code.
  - Redeclaring `ctx`, `props`, `slots`, `locals` or `orbit`, or in a page `params`, at the top level of the body (`props := …`, `var ctx …`) is an error: "props is provided by Orbit and can't be redeclared here". Shadowing in nested blocks is allowed, as in Go. In a component, `params` is an ordinary name, since Orbit doesn't provide it there (*decided by rule*: simplest; the error message would be false in a component).
  - A user import of `github.com/orbit-z/orbit` under the name `orbit` is merged with the implicit one.
- **No `func init`**: a hoisted `func init()` in the frontmatter is rejected at its position: "func init isn't allowed in a component; use a package under internal/ for initialization". Rendering a component during package initialization isn't supported (§3.1).
- If there's no `type Props`, generate `type Props struct{}`. Every `Props` field must be exported (a parent can't set an unexported field); an unexported field is an error naming the field: `src/components/Card.orbit:5:5: Props field post must be exported, since a parent sets it (rename it to Post)`.
- **Unused locals**: Go rejects variables that are declared but not used, and Astro allows them. Parse the body with `go/parser`, collect names declared at its top level (`:=`, `var`), and emit `_ = name` after the body. These lines are recorded in the source map as `kind=echo` (§3.3), so an LSP rename drops gopls's edits to them (§9). Unused imports stay a Go error, which is consistent with Go.
- **Errors and control flow**: the body may `return err` (500), `return ctx.Redirect("/login", 302)` or `return orbit.ErrNotFound` (404).
  - **Return positions** (user decision: wrap at codegen): every `return X` of the body, nested ones included, is generated as `return orbit__rt.ErrorAt("<path>:L:C", X)`, the position of the `return` keyword. `ErrorAt` passes `nil`, `ErrNotFound`, a `*RedirectError` and an already-positioned error through, and otherwise wraps (`Unwrap` keeps `errors.Is/As` working), so the 500 log line (§4) names the `.orbit` position. Returns inside function literals and hoisted funcs, bare returns and multi-value returns aren't touched. `X` keeps its exact segment and inline directive; the wrapper is glue. `CleanGoOutput` turns "in argument to orbit__rt.ErrorAt" back into "in return statement".
  - **Terminating last statement**: if the last top-level body statement is terminating in the Go spec's sense (e.g. `return nil`, or an `if`/`else` that returns on every branch), the `_ = name` lines are emitted *before* it and no template code after it, so `go vet` doesn't report `unreachable code` in the generated file. A template with content after it (anything but whitespace) is an Orbit error at that statement: "the frontmatter always returns here, so the template below is never rendered".
- **Pages**: every page renders per request (SSR only, §12). A page reads its route params from **`params`** and the rest of its route data from `ctx` (`ctx.Request`, `ctx.URL`). Pages never receive props: the route adapter passes the zero (generated, empty) `Props`.
  - **Typed route params** (user decision). For each page, codegen generates `type Params struct { … }` in the page's declaration package, next to `Props` (§3.1), with one `string` field per route param, in path order:
    - `[slug]` → `Slug`; `[...path]` → `Path`, the rest value (the matched segments joined with `/`, `""` when it matches none). Values are percent-decoded (§4).
    - Field names follow the props PascalCase rules (§2.3): the name is split into words at `-`, `_` and lower-to-upper case changes, each word is capitalized, and words in golint's initialism table are written in capitals: `[post-id]` → `PostID`, `[postId]` → `PostID`, `[id]` → `ID`, `[api-url]` → `APIURL`.
    - A route without params (`index.orbit`, `about.orbit`, `404.orbit`) gets `type Params struct{}`, so `params` exists in every page.
    - `params` is a plain struct value, filled with one `ctx.Param("slug")` call per field by the page's generated `Render` wrapper, the adapter between the uniform `Render` signature and the page's `render` (§3.1, §3.2). Filling it there, not in the route table, means `orbittest.Render` on a page sees the params set with `orbittest.WithParam` (§4). A typo is Go's own compile error at the `.orbit` position (`params.Slg undefined (type Params has no field or method Slg)`), and the LSP completes `params.` through gopls (§9).
    - Components, layouts and generic code (e.g. a `Pagination` component) don't get `params`: they call `ctx.Param(name)`, which returns `""` for a name the route doesn't have (§4).
  - **Declaring `type Params` in a page is a build error** at the declaration, like `Props`: `src/pages/x.orbit:L:C: Params is generated from the page's route; rename this type` (wording *decided by rule*: simplest, `go vet` style). Components may declare a `Params` type.
  - **Route param names must make Go field names**: two params of one route whose field names collide (`[post-id]/[postId].orbit`, or the same name twice, `[id]/[id].orbit`) are a build error at the file: `src/pages/[post-id]/[postId].orbit: route params [post-id] and [postId] both become params.PostID; rename one`. A param name must match `[A-Za-z][A-Za-z0-9_-]*`; otherwise (`[1st]`, `[é]`) it's a build error at the file: `src/pages/[1st].orbit: route param [1st] can't become a Go field name; use letters, digits, - and _, starting with a letter`. *Decided by rule* (simplest; log both in `docs/DECISIONS.md`).
  - **Declaring `type Props` in a page is a build error** at the declaration: `src/pages/x.orbit:L:C: pages don't receive props; move this to a component or read params`. Components are unchanged. *Decided by rule* (simplest option: a page `Props` could never be set, so it's always a mistake; log it in `docs/DECISIONS.md`).
- **Unused component import** (user decision): an `.orbit` import whose alias the template never uses is an Orbit error at the alias: `src/pages/index.orbit:3:5: component Card is imported but not used; remove the import`.
- **`.orbit` imports**: the alias is required, and the path is relative to the file. An import without one, or with `_`, is an error suggesting one from the file name: `a component import needs an alias: Card "./Card.orbit"` (decided by rule: simplest). The alias must start with an uppercase letter, because a lowercase tag is always an HTML element: `src/pages/index.orbit:5:5: component alias card must start with an uppercase letter (rename it to Card)` (decided by rule: simplest). It's rewritten to the component's generated *declaration* package (`orbit_gen/decl/...`, §3.1), so other components are ordinary Go imports. Components may import each other in cycles (mutual recursion), because calls go through the declaration package (§3.1). The one remaining cycle error is two `Props` types referencing each other's packages (e.g. `A.Props` has a `B.Props` field and vice versa); it's rare because declaration packages hold only `Props` and its dependencies, and it's reported with the full chain.
- **No framework components.** A frontmatter import of a `.tsx`, `.jsx`, `.svelte` or `.vue` file is an error at the import path: `src/pages/index.orbit:4:5: framework components aren't supported; use a .orbit component with a <script>`. Orbit has no framework islands, by design (§12). Any other relative path (`./`, `../`) that doesn't end in `.orbit`, such as `"./util.ts"`, is an error too: `only .orbit components can be imported by relative path; import client modules from a <script>` (decided by rule: simplest; the framework message would mislead for a plain `.ts` file). Go packages are imported by their import paths, as usual.
- **Recursion**: inside a component, `<Self …>` renders the component itself, like Astro's `<Astro.self>`, e.g. a tree or nested comments. Mutual recursion (`A` renders `B`, which renders `A`) also works. Termination is the user's responsibility (usually an `{if}` around the recursive call). The render-depth guard is **always on**, in dev and prod: a Go stack overflow is fatal and can't be recovered, so a depth over 1000 returns an error naming the component stack instead. It costs an int increment per component render.

### 2.3 Template grammar
| Construct | Meaning |
|---|---|
| text | Anything except `{` and a `<` that starts a tag; emitted verbatim. `<` starts a tag only when followed by a letter, `/` or `!`; any other `<` (`a < b`, `<3`, `<=`) is text. A literal brace is written `{"{"}`. |
| `{expr}` | Any Go expression, escaped (typed writes, §3.3; `Expr` fallback, §4). The end is found with a Go-aware scanner that tracks `()[]{}` depth, strings, runes, raw strings and comments. |
| `{/* … */}` | Template comment, emits nothing. |
| `{if c}` `{else if c}` `{else}` `{/if}` | Copied as a Go `if` chain. |
| `{for clause}` `{/for}` | Any Go for clause (`range`, 3-clause, condition). Go 1.22 per-iteration variables make closures safe. |
| `<tag …>` lowercase or containing `-` | HTML or custom element. |
| `<Name …>` capitalized | Component. Must match a `.orbit` import alias, otherwise it's an error: `unknown component <Crad>: no .orbit import with this alias`. |
| `<Self …>` | The current component, rendered recursively. Same props and slots rules. |
| `<Name server:defer …>` | Deferred server rendering (Astro's server islands): the page gets a placeholder holding the `fallback` slot, and the browser fetches the component's HTML in a separate request (§3.4, §5b). |
| `<Name client:idle …>` (also `client:load`, `client:visible`, `client:media`) | Controls when the component's `<script>` modules load (§3.4, §5). |
| `<slot />`, `<slot name="x">fallback</slot>` | Slot outlet, with fallback children. |
| `<Fragment>` | Grouping with no wrapper element; mostly used for `<Fragment slot="x">`. As in Astro, it takes only `slot`, `set:html` and `set:text` (`<Fragment set:html={body} />` writes raw HTML with no wrapper); any other attribute is a compile error. |
| `<!DOCTYPE …>`, `<!-- … -->` | Passed through. `{…}` inside an HTML comment isn't evaluated. |

`{switch}` blocks (**accepted, being implemented**; user decision 2026-10-26: keyword `switch`, not `match`, since the header is copied as Go like `{if}`/`{for}` and `match` would promise patterns and exhaustiveness Go can't check):
- `{switch header}` … `{case list}` … `{default}` … `{/switch}`. The header is any Go switch header, copied verbatim: a tag (`{switch post.Status}`), an init statement (`{switch s := f(); s}`), none (`{switch}` with conditions in the cases), or a type switch (`{switch v := item.(type)}`). A `{case …}` list is copied verbatim too (`{case "scheduled", "queued"}`, `{case n > 10}`, `{case posts.Video}`). It compiles to a plain Go `switch` with each case's template as its body, so Go's rules apply: no fall-through, the first matching case wins, at most one `{default}`, duplicate constant cases are Go's error at the `.orbit` line.
- Decided by rule (simplest): content other than whitespace or `{/* */}` between `{switch …}` and the first `{case}`/`{default}` is a compile error (it could never render); `fallthrough` isn't supported (no statement position in a template); `{case}`/`{default}` outside a `{switch}`, a second `{default}`, and an unclosed `{switch}` are compile errors like a stray `{else}`.

- **Attributes**: `a`, `a="s"`, `a='s'`, `a=bare`, `a={expr}`, `{a}` (shorthand for `a={a}`), and `{...attrs}` (spread of an `orbit.Attrs`; HTML elements only; names validated at runtime, §4).
- **Directives**:
  - `set:html={expr}`: raw element content. `expr` must have type `orbit.HTML`: codegen emits `orbit__w.HTML(expr)`, so a plain `string` variable is a compile error at the `.orbit` position (untyped string constants are accepted, since the author wrote them). The error is Go's own (`cannot use body (variable of type string) as orbit.HTML value in argument to orbit__w.HTML`), not rewritten (decided by rule: simplest; the docs explain it).
  - `set:text={expr}`: escaped element content.
  - `set:html` and `set:text` work on HTML elements and `<Fragment>`. An element with a `set:` directive takes no children (whitespace aside), and a `set:` directive on a component is a compile error (decided by rule: Astro behavior).
  - `set:json={expr}`: **server→client data**. Only valid on `<script type="application/json">`; anywhere else it's a compile error: `set:json only works on <script type="application/json">`. Such a script is never processed or bundled (§5). `expr` (any type) is encoded with `encoding/json` into the element content via `orbit__w.JSON("<path>:L:C", expr)` (the position of the `set:json` attribute), escaped for the script-data context: `<` → `\u003c`, `>` → `\u003e`, `&` → `\u0026`, U+2028/U+2029 → `\u2028`/`\u2029`. This blocks `</script>` and `<!--` breakouts. An encode error is a render error with the `.orbit` position. The client reads it with `json("posts")` from the component's module (`import { json } from "./X.orbit"`), typed from the value's Go type when the script has a static `id` (§5c), or with `JSON.parse(document.getElementById("posts").textContent)`. For per-element data, use `data-*` attributes (escaped like any attribute) and read `el.dataset`, or **`orbit.JSON(v)`** as the value of any attribute (§5c): written single-quoted, always (`false`/`null` included), and on a `data-*` attribute of an HTML element typed for the component's scripts as `data(el, key)`. All three patterns are documented, with a custom-element example.
  - `slot="name"`: on a child of a component, routes it to that named slot. The attribute itself isn't written to the output, and several children with the same slot name all render there, in source order.
  - `is:inline`: on `<script>`/`<style>`, leaves the tag untouched.
  - `is:global`: on `<style>`, skips scoping.
  - `server:defer` (bare, on a component tag, `<Self>` included): **deferred server rendering**, Astro's server islands. The call site doesn't render the component. It writes a placeholder holding the `fallback` slot, and the browser fetches the component's HTML from `/_orbit/island/<buildID>/<id>` after the page loads (§3.4, §5, §5b). Props are passed as usual and must be JSON-serializable, which is checked at generate time (§3.4).
    - The only allowed children are the fallback: elements or `<Fragment>`s with `slot="fallback"`, plus whitespace. Any other child is a compile error at the child: `only slot="fallback" content is allowed inside a server:defer component`. Passing other slots, which Astro supports, is deferred past the MVP (§12). With no fallback, the placeholder is empty.
    - On an HTML element, `<slot>` or `<Fragment>`, it's a compile error: `server:defer only works on .orbit components`. A value (`server:defer="x"`) is a compile error too: `server:defer takes no value`.
  - `client:*` (on a component tag): controls **when the component's own `<script>` modules load** in the browser (§3.4, §5). Astro has these directives only for framework components; Orbit applies them to the vanilla scripts of `.orbit` components.
    - `client:load`: eager, part of the page bundle. This is the same as no directive, and no wrapper is emitted.
    - `client:idle`: loads once the browser is idle (`requestIdleCallback`, falling back to `setTimeout` where it's missing, as Astro does).
    - `client:visible` or `client:visible="200px"`: loads when an instance scrolls into view (`IntersectionObserver`). The optional value is its `rootMargin`.
    - `client:media="(max-width: 600px)"`: loads when the media query matches, at page load or later (`matchMedia`). The value is required.
    - Values must be static strings. An `{expr}` value is a compile error, `client:visible takes a static string value, not an expression` (decided by rule: simplest; the marker is folded into a precomputed `Raw` constant, §3.4).
    - `client:load` and `client:idle` take no value (`client:idle takes no value`), and `client:media` without one is an error: `client:media needs a media query, e.g. client:media="(max-width: 600px)"`. The messages name the directive written.
    - At most one `client:*` is allowed per tag: `only one client:* directive is allowed per component`. On an HTML element, `<slot>` or `<Fragment>`, a `client:*` directive is a compile error: `client:visible only works on .orbit components; move the <script> into a component`.
    - `client:only` is rejected: `client:only is for framework components, which Orbit doesn't support; use client:load, client:idle, client:visible or client:media`.
    - **The directive covers the component's whole subtree** (user decision, like an Astro island): its own scripts plus the scripts of every component it renders, transitively, go into that call site's lazy entry. If any of those components is also rendered eagerly elsewhere on the page, its scripts stay eager (eager wins). Nested directives inside a lazy subtree apply their own strategy once the outer one has fired.
    - `server:defer` and `client:*` on the same tag is a compile error: `server:defer and client:* can't be combined; put client:* on a component inside the deferred one` (decided by rule: Astro has no such combination, so the simplest option is to reject it).
  - **Reserved namespaces**: `server:` and `client:` are reserved. An unknown directive in either is a compile error at the attribute, listing the valid ones: `unknown directive "client:hover" (client directives: client:load, client:idle, client:visible, client:media)`.
  - **Astro-only directives** (decided by rule: simplest, with a clear error rather than passing them through as plain attributes): `class:list` and `define:vars` are compile errors with a hint: `class:list isn't supported; build the class string in the frontmatter (e.g. strings.Join)` / `define:vars isn't supported; pass data with orbit.JSON on a data-* attribute, or set:json`. Other colon attributes (`xlink:href`, `xml:lang`) are plain HTML.
- **Security warnings**: the compiler warns (doesn't fail) on `on*={expr}` and `style={expr}`, because attribute escaping doesn't make a value safe in a JS or CSS context: `src/components/Card.orbit:14:9: warning: onclick={…} is escaped for HTML, not for JavaScript; don't put untrusted values here`. There's no switch to silence them (decided by rule: simplest). URL attributes are filtered at runtime (§4). Document both.
- **Raw-text elements**: `<script>` and `<style>` content is opaque, with no `{}` interpolation. `<title>` and `<textarea>` allow `{expr}`; other markup inside them is text (RCDATA, as in HTML).
- **Void elements** (`br img input meta link hr area base col embed source track wbr`) take no closing tag. Every other element must be closed explicitly, or self-closed (`<div />` renders `<div></div>`, as in Astro), and a mismatch is a parse error with line:col. No implicit auto-closing, so error messages stay clear.
- **Component attribute → field mapping**:
  - The attribute name is matched against the target component's parsed `Props` fields, ignoring case, `-` and `_`: `id` → `ID`, `url` → `URL`, `is-open`/`isOpen` → `IsOpen`. Two fields that normalize to the same name are an error.
  - When the target's fields can't be listed from its parse (an embedded struct, or `type Props = other.T`), fall back to PascalCase plus an initialism table: golint's common-initialisms list (`ID`, `URL`, `HTTP`, `API`, `HTML`, `JSON`, …), listed in full in `reference/template-syntax.md`.
  - `a="s"` becomes a Go string literal
  - a bare `a` becomes `true`
  - `{expr}` is used as-is
  - Children that are only whitespace pass no slot.
  - **Unknown props are pre-checked by Orbit**: an attribute that matches no field of the target's parsed `Props` is an Orbit error at the attribute name, in the user's spelling, listing the attribute names that would work (each field in lower camel case: `IsOpen` → `isOpen`, `ID` → `id`): `src/pages/index.orbit:9:6: unknown prop "psot" on <Card> (props: post, featured)`.
  - When the fields can't be listed (the embed/alias fallback above), Orbit skips the pre-check and Go's `unknown field` error is reported at the attribute name through its field-key directive (§3.3). The Go compiler always checks the value types.
- **Scripts and styles**: non-inline `<script>`/`<style>` tags anywhere in a template are extracted from the HTML (§5).

### 2.4 Markdown files
**Status: Implemented** (2026-10-26; `internal/markdown`, user docs `docs/markdown.md`). Implementation notes: Markdown units carry `compiler.Unit.Retype`, which in pass 2 converts the frontmatter to the layout's `Props` types instead of type-checking the impl package (on errors the unit keeps pass 1 and reports them); the unknown-key check runs in pass 1 from the component index when `Props` lists all its fields, otherwise in pass 2 with go/types (promoted fields can be set at the top level; nested maps set direct fields only); the `.chroma` rule always sets `color` and `background-color`, falling back to `CanvasText`/`Canvas`; a block without a language gets `data-language="plaintext"`; dashes follow Astro's smartypants (user decision, after the first implementation): exactly `--` is an em dash, `---` and longer runs stay, via Orbit's own `-` inline parser with the typographer's dash substitutions off (no guillemets); ```` ```orbit ```` blocks are highlighted by Orbit's own Chroma lexer (`internal/markdown/orbitlexer.go`: Go frontmatter, HTML template, `{…}` as Go with a regexp2 balancing-group mirror of `scanBraced`, control tags, TypeScript `<script>`, CSS `<style>`), built on first use and not in Chroma's registry, so CLI startup is unchanged (7.15 ms median before and after) and the binary grows 38 KB; highlighting the docs' 139 orbit blocks takes ~19 ms warm, ~27 ms cold; the CLI starts ~5.7 ms slower (Chroma's registries at init). The user chose every recommended answer to the **(Q)** points: YAML frontmatter via `go.yaml.in/yaml/v3` (CLI dependency, approved); frontmatter keys set the layout's typed `Props` fields, an unknown key or a wrong type is an error; an import exposes `<Post />`, `Post.Frontmatter`, `Post.Headings` and, for pages, `Post.URL`; relative `.md` links are rewritten to page URLs (missing target an error, missing anchor a warning); highlighting uses Chroma classes plus a generated `light-dark()` stylesheet (github / github-dark by default, configurable, `css: false`), through Orbit's **own code-block renderer over Chroma** (not goldmark-highlighting, which measured 420 ms vs ~30 ms). Decided by rule (Astro): raw HTML allowed, github-slugger heading ids, smart punctuation on.

**What a `.md` is.** A Markdown file is a component with no Go code: frontmatter (YAML) plus a Markdown body, compiled at generate time. Extensions (Astro's list): `.md`, `.markdown`, `.mdown`, `.mkdn`, `.mkd`, `.mdwn`.
- Under `src/pages/` (and not `_`-prefixed) it's a **page**, with the route rules of §4: `blog/hello.md` → `/blog/hello`, `index.md`, `404.md`. A route collision with an `.orbit` page is the existing duplicate-route error (`route /about is already defined by src/pages/about.md; …`). A bracket in a `.md` page path is a build error at the file: `a Markdown page can't have route params; rename it, or write a [slug].orbit page`.
- Elsewhere under `src/` it's compiled **only when imported** (Astro behavior), so a stray `README.md` never breaks generate.
- Imported from an `.orbit` frontmatter as `Post "./post.md"`: the same alias, relative-path, inside-`src/` and unused-import rules as `.orbit` imports (§2.2). The relative-import error becomes `only .orbit and .md files can be imported by relative path; …` (update `components.md`/`troubleshooting.md` with the implementation, since docstest asserts the current wording). A `.md` can't import anything; `layout` is its only dependency.

**Frontmatter (Q: format).** YAML between `---` lines, parsed with `go.yaml.in/yaml/v3` (the YAML organization's maintained continuation of `gopkg.in/yaml.v3`; CLI-only dependency, to be approved), using `yaml.Node` so every key and value has a line:col. Positions are offset by the opening fence, so errors read `src/pages/blog/hello.md:L:C`. Anchors/aliases, tags and multi-document streams are errors (simplest). `layout` is consumed by Orbit: a path relative to the `.md`, ending in `.orbit`, inside `src/` (`layout ../layouts/Post.orbit: no such file` at the value). A key with no value is an error. Keys become Go field names with the route-param rules (§2.2: PascalCase plus initialisms, `[A-Za-z][A-Za-z0-9_-]*`, collisions are errors at the second key).

**Generated packages.** A `.md` gets the usual decl/impl pair (§3.1), with an `_md` suffix on the last segment so it never collides with a sibling `.orbit`: `src/pages/blog/hello.md` → `orbit_gen/{decl,impl}/pages/blog/hello_md` (packages `hello_md`, `hello_md_impl`); `404.md` → `p_404_md`. Component ID `<Name>-<hash8>` as usual (§3.4).

Declaration package (what importers see; Q: what an import exposes):
```go
package hello_md

import (
	orbit__rt "github.com/orbit-z/orbit"
	"time"
)

type Props struct{}
type Params struct{} // pages only, like any page

// Generated from the YAML values (types inferred: string, bool, int, float64,
// time.Time for YAML dates/timestamps, []T for homogeneous lists, nested
// anonymous structs for maps; mixed lists are an error at the list).
var Frontmatter = struct {
	Title string
	Date  time.Time
	Tags  []string
}{
	Title: "Hello, Orbit",
	Date:  time.Date(2026, 10, 26, 0, 0, 0, 0, time.UTC),
	Tags:  []string{"news", "go"},
}

var Headings = []orbit__rt.Heading{{Depth: 2, Slug: "why-markdown", Text: "Why Markdown"}}

const URL = "/blog/hello" // pages only

var Orbit__Render func(*orbit__rt.Ctx, *orbit__rt.Writer, Props, orbit__rt.Slots, Params) error
func Render(…) error { … } // the uniform wrapper of §3.2
```
`Frontmatter` is an anonymous struct, so two files with the same keys and types share a type (struct identity) and fit in one slice. It's a package var, so every importer reads the same values: read-only by convention. The HTML is **not** in decl, so a body edit recompiles only the impl package; frontmatter and heading edits change decl and recompile importers.

Implementation package, for a page with a layout:
```go
package hello_md_impl

import (
	orbit__rt "github.com/orbit-z/orbit"
	. "example.com/blog/orbit_gen/decl/pages/blog/hello_md"
	Layout "example.com/blog/orbit_gen/decl/layouts/post"
	"time"
)

// The layout's props, built once at package initialization (zero per-request
// allocations). Each assignment carries a //line directive to its YAML key.
var orbit__lprops = func() (p Layout.Props) {
//line ../../../../src/pages/blog/hello.md:2:1
	p.Title = "Hello, Orbit"
//line ../../../../src/pages/blog/hello.md:3:1
	p.Date = time.Date(2026, 10, 26, 0, 0, 0, 0, time.UTC)
//line ../../../../src/pages/blog/hello.md:4:1
	p.Tags = []string{"news", "go"}
//line render.go:20:1
	p.Headings = Headings
	return p
}()

const orbit__html = "<p>Orbit compiles …</p>\n<h2 id=\"why-markdown\">Why Markdown</h2>\n…"

func orbit__content(orbit__w *orbit__rt.Writer) error { orbit__w.Raw(orbit__html); return orbit__w.Err() }

var _ = func() int { Orbit__Render = orbit__render; return 0 }()

func orbit__render(orbit__ctx *orbit__rt.Ctx, orbit__w *orbit__rt.Writer, _ Props, _ orbit__rt.Slots, _ Params) error {
	if orbit__err := orbit__w.Enter("src/pages/blog/hello.md"); orbit__err != nil {
		return orbit__err
	}
	defer orbit__w.Leave()
	return Layout.Render(orbit__ctx, orbit__w, orbit__lprops, orbit__rt.Slots{Default: orbit__content})
}
```
- `orbit__content` is a package-level func (no captures), so the `Slots` value allocates nothing; the page is `Raw` writes plus the layout's own render. Without a layout, `orbit__render` is the single `Raw` write (the page is the bare HTML, as in Astro).
- `<Post />` in an `.orbit` compiles to the ordinary call `Post.Render(orbit__ctx, orbit__w, Post.Props{}, orbit__rt.Slots{})`. Attributes are rejected by the unknown-prop pre-check (`unknown prop "x" on <Post> (Post takes no props)`); children are ignored as for any component without a `<slot>`. `server:defer`/`client:*` on it aren't special-cased (simplest; `client:*` matters when its layout has scripts).
- Island and route tables, `orbittest.Render` and `RenderComponent` treat `.md` packages like any other: the uniform `Render` signature is kept.

**Frontmatter → layout props (Q: how a layout receives frontmatter).** Each key is matched to a field of the layout's `Props` with the attribute rules (§2.3: ignoring case, `-`, `_`). An unmatched key is an Orbit error at the key, in the unknown-prop form: `unknown frontmatter key "tilte" for layout Post (props: title, date, tags, headings)`. Values are converted **using the layout's `Props` field types from go/types** in the typed pass (§3.3 pass 2: the layout's decl package is checked before any impl package, so the type is available):

| Field type | From |
|---|---|
| string kinds | any scalar, verbatim source text |
| `bool`; int/uint/float kinds | YAML bool; numbers, range-checked |
| `time.Time` | YAML date (UTC midnight) or timestamp |
| `orbit.HTML` | a string (author-written, like a string constant in `set:html`) |
| `[]T`, `map[string]T`, structs | sequences, maps, maps matched to exported fields (recursively) |

Other types (`any`, pointers, interfaces, funcs, chans) are errors at the key. Mismatches are Orbit errors at the YAML value: `frontmatter draft: "yes" isn't a bool (Post.Props.Draft is bool)`. A field `Headings []orbit.Heading` is filled with the headings (a `headings` key is then an error). A layout `Props` edit re-emits the impl of every `.md` that uses it (an extra edge in the incremental dependency graph: md impl → layout decl **types**, not just the import).
- **Fallback** (a layout decl package with type errors, unreadable export data): emit the assignments with untyped constants and composite literals guessed from the YAML (as for `Frontmatter`), so Go reports any mismatch at the `.md` line through the `//line` directives, and the build fails on the layout's own error anyway.

**The Markdown pipeline** (`internal/markdown`, CLI only; goldmark v1.8.x, already used by `docs/site`):
- goldmark with CommonMark plus, by default, `extension.GFM` (tables, strikethrough, linkify, task lists) and `extension.Footnote` (Astro's remark-gfm includes footnotes), and `extension.Typographer` for `smartypants` (Astro default on). `orbit.json` `markdown.gfm` / `markdown.smartypants` turn them off (§8).
- **Raw HTML** passes through (`html.WithUnsafe()`, Astro behavior; Q). Link destinations aren't URL-filtered: they're static author content, like static template attributes (§4). A raw `<script>`/`<style>` is left as written (not extracted or bundled, §5), like `is:inline`.
- **Heading IDs**: an AST transformer assigns github-slugger IDs (Astro's `rehypeHeadingIds`; the same algorithm as `docs/site`'s `slugify` + `uniqueID`) to every Markdown heading h1–h6 and collects `orbit.Heading{Depth, Slug, Text}` (plain text, markup stripped). No self-link anchors, no `{#id}` syntax (Astro defaults). Raw-HTML headings aren't touched.
- **Links**: an AST transformer rewrites a relative destination whose path ends in a Markdown extension and resolves to a `.md` **page** to that page's route (fragment kept): `./routing-guide.md#x` → `/blog/routing-guide#x` (Q: on by default). A missing target or a non-page `.md` is an error at the link; an unknown fragment (no such heading id in the target) is a warning, since the id may come from a layout or raw HTML. Checked after every file is parsed (one project-wide pass, cheap: a map lookup per link). Absolute, external and non-Markdown links, and image destinations, are left as written (no image pipeline, §12).
- **Code blocks (Q: theme/CSS; and goldmark-highlighting vs. a direct Chroma renderer, see Cost)**: a fenced block with a language Chroma knows renders as `<pre class="chroma" tabindex="0" data-language="go"><code>` with class-based token spans (`chromahtml.WithClasses(true)`); unknown or no language gives the same wrapper with escaped text. The info string after the language is ignored (Astro behavior). Lexer lookup is **memoized per language name**.
- **Theme CSS**: a virtual stylesheet `orbit:style/markdown-highlight.css`, generated from the two configured Chroma styles (default `github` / `github-dark`), merging each token rule into `color: light-dark(<light>, <dark>)` (and `background-color`; non-color properties from the light style). It's added once to the stylesheet of every page whose static graph (§5) contains a `.md` with at least one highlighted block, **first** in the stylesheet so user styles override it. About 4.3 KB per Chroma style unminified (measured for `github`). `"css": false` omits it; `"syntaxHighlight": false` disables Chroma (plain `<pre><code class="language-go">`).
- `compressHTML` (§3.3) doesn't touch Markdown HTML (goldmark's output has one newline between blocks; simplest). The HTML is one `Raw` constant per file, emitted as a Go string literal.

**Styling Markdown content.** The `.md` has no `<style>`, so its elements carry no scope attribute (§5), and a layout's scoped rules don't match them, exactly like slot content (§3.2) and like Astro. The documented answer is Astro's: `:global(…)` under a layout element (`.prose :global(h2)`) or `<style is:global>`. Considered and not proposed: stamping the layout's scope attribute onto the Markdown elements (possible for pages, since the layout is static, but not for `<Post />` rendered by arbitrary parents, and it differs from Astro).

**Source positions.** goldmark segments are byte offsets into the body; Orbit keeps the body's start offset and line so that link errors and warnings map to `src/…md:L:C` (columns in bytes, as in §3.3). YAML positions come from `yaml.Node`. Generated Go for a `.md` contains no user Go code, so the only Go errors possible are frontmatter assignments in the fallback path, which carry `//line` directives to the key. The generated `Frontmatter` literal and `Headings` get no directives (always valid Go).

**Assets.** A `.md` has no scripts or styles of its own; its graph node has one edge, to its layout, so the layout's (and its imports') CSS/JS join the page as for an `.orbit` import (§5), plus the highlight stylesheet when needed. The layout must contain `</head>` for head injection, as for any page.

**Dev loop (§7).** `.md` files under `src/` are already watched. A body-only edit (same frontmatter, same headings) regenerates the impl package only, like a template edit (~0.22 s, dominated by `go build`); a frontmatter or heading edit regenerates decl too and recompiles importers. Link checking reruns project-wide on any `.md` change (cheap). `markdown` options in `orbit.json` regenerate every `.md`. Markdown that the user's own code reads at runtime from outside `src/` (e.g. `docs/site`) uses the `watch` globs of `orbit.json` (dogfood follow-up, below).

**LSP (§9).** The LSP's in-memory generate includes `.md` decl packages so gopls completes `Post.Frontmatter.` and `Post.Headings` in `.orbit` files; native completion offers `<Post` tags (imported non-page `.md` files, the ones in the index). **Implemented** (2026-10-26, user-approved additions): import-path completion offers `.orbit` and `.md` paths; Orbit's diagnostics are published for every compiled `.md` (pages and imported files), live as the user types: an open `.md`'s buffer goes through `project.UpdateMarkdown` (the Markdown front of that file plus the project-wide link check, in memory, no gopls). Typed frontmatter errors (Retype, go/types) come from the LSP's typed check (§9 Startup step 2, which now also runs without `orbit_gen/` when a compiled `.md` has a layout), each tied to its frontmatter key's source text and the layout's index `Props`: shown at the key's current position while both are unchanged, hidden after an edit of the key until the next check (startup, 300 ms after `orbit_gen/` changes, or the Markdown typed check 300 ms after the last edit; user decision "Yes, debounced", 2026-10-26). gopls's diagnostics in `.md` generated files are dropped (no user code; the untyped fallback would report false mismatches). Requests other than diagnostics on `.md` documents answer `null`; highlighting and the rest stay the editor's Markdown support. Details in §9.

**Runtime.** One addition, still stdlib-only: `type Heading struct { Depth int; Slug, Text string }` (named after Astro's `MarkdownHeading`; document it in `reference/runtime-api.md`).

**Cost** (measured 2026-10-26, Ryzen 7 9700X, one thread, Orbit's own `docs/`: 22 files, 523 KB, 269 fenced blocks; scratch benchmark, not in the repo):
- goldmark + GFM + auto heading IDs: **7.5 ms** for all 22 files (~14 µs/KB). A typical 25 KB page: ~0.4 ms.
- Chroma tokenize + HTML format of all 269 blocks, lexer looked up once per language: **~30 ms** (Go blocks are 20 ms of it). Lexers compile lazily on first use (~30 ms once per process; the dev process keeps them).
- **goldmark-highlighting as is: 420 ms**: it calls `lexers.Get` per block, and for a language Chroma doesn't know (`orbit`, `mermaid`, `astro`, …) `Get` falls back to matching the name against every lexer's filename globs (~1.5 ms per block, 86% of the profile). So Orbit must memoize the lookup, which goldmark-highlighting (last commit 2023, pseudo-version only) has no hook for: either a ~100-line node renderer calling Chroma directly (recommended; one dependency fewer) or an AST transform that strips unknown languages before goldmark-highlighting sees them.
- CLI binary: goldmark ~1.5 MB, Chroma (with its 279 embedded XML lexers, 2.5 MB) and `github.com/dlclark/regexp2/v2` ~6 MB more (measured: the CLI grew 26.8 → 33.2 MB). User server binaries gain only their HTML constants.
- Net: a `.md` edit adds ~1–2 ms to a ~220 ms rebuild; a full generate of a docs-sized site adds ~40 ms, parallel per file.

**Out of scope here**: content collections and glob imports (§12), MDX (expressions/components in Markdown), remark/rehype-style plugins, image processing, code-block titles/captions (`file=`), and heading self-links.

## 3. Compilation

### 3.1 Generated package layout
Each `.orbit` file becomes **two Go packages**, in two separate trees under `orbit_gen/`:

| Package | Path | Contents | Imports |
|---|---|---|---|
| declaration | `orbit_gen/decl/components/card` (package `card`) | `Props` and its transitive dependencies: methods on them, and the hoisted types, consts and funcs they reference. Plus the hook `var Orbit__Render func(*orbit__rt.Ctx, *orbit__rt.Writer, Props, orbit__rt.Slots) error` and the exported wrapper `func Render(orbit__ctx, orbit__w, orbit__props, orbit__slots) error`, which panics with `orbit: src/components/Card.orbit not linked; import example.com/blog/orbit_gen/app` if the hook is nil (e.g. in a user test that skipped the app). For a **page**, also the generated `type Params` (§2.2); the page's hook takes it as a fifth argument (`func(…, orbit__rt.Slots, Params) error`), while its `Render` wrapper keeps the uniform signature and builds `Params` from `orbit__ctx.Param` calls (§3.2). | User Go packages used by `Props`, plus the runtime as `orbit__rt` (and as `orbit` only if `Props` code uses it) |
| implementation | `orbit_gen/impl/components/card` (package `card_impl`) | Everything else that's hoisted: lowercase helpers, other types. Plus `func orbit__render(...)` (the frontmatter body and template) and the link `var _ = func() int { Orbit__Render = orbit__render; return 0 }()`. | Its own declaration package via dot-import (`import . ".../decl/components/card"`), so `Props` and `Render` resolve unqualified. Other components' **declaration** packages only. The runtime as `orbit__rt` (and as `orbit` only if user code uses it). |

How this works:
- **Calls**: a call site `<Card …>` compiles to `Card.Render(orbit__ctx, orbit__w, Card.Props{…}, orbit__rt.Slots{…})`, where `Card` is the alias for the declaration package.
- **No cycles**: implementation packages import only declaration packages, so Go never sees an import cycle, even with mutual recursion.
- **Self**: `<Self>` compiles to `Render(…)`, the dot-imported wrapper.
- **Package names**: the implementation package is named `<name>_impl` (`card_impl`), distinct from the declaration package `card`. Go then prints the declaration type as `card.Props` instead of `"example.com/blog/orbit_gen/decl/components/card".Props`; the CLI rewrites it further to the user's alias (§3.3, error output).
- **Linking**: each implementation package sets its hook in a package-level var initializer, not in `init()`: package variables are initialized before any `init` function runs, so the hook is set as early as possible and never depends on the order of `init` functions. `orbit_gen/app` imports `orbit_gen/link` (as `_`), which imports every implementation package (as `_`; the route table calls each page through its declaration package's `Render`), so every hook is set before `main` runs. Rendering *another* component during package initialization is unsupported (sibling packages initialize in import-path order), and a frontmatter `func init` is rejected (§2.2).
- **Unexported names in decl**: a name that only `Props` (and other declaration-package code) uses may stay unexported. A dot-import only brings exported names, so implementation code can't see an unexported name that `Props` pulled into the declaration package. Codegen reports this clearly instead of leaving Go's "undefined": `src/components/Card.orbit:5:3: item is used by Props, so it lives in the component's declaration package and must be exported (rename it to Item)`.
- **Clashes with decl exports**: an `.orbit` import alias, or a name hoisted into the implementation package, that equals an exported name of the component's own declaration package is an Orbit error at that name (`Item "./Item.orbit"` or an impl-side `type Item` when `Props` pulled an `Item` into decl), instead of Go's `Item redeclared` / `Item already declared through dot-import` at a generated position: `Item clashes with Item in the component's declaration package (Props uses it); rename one`. The same applies to the generated `Props`, `Render` and a page's `Params`: `Props clashes with the generated Props of the component's declaration package; rename it` (both decided by rule: simplest). Shadowing a decl export inside the body (`Item := 42`) is legal Go and allowed.
- **Verbatim user code**: the user's Go code is copied without renaming, so source maps stay trivial. Each frontmatter import, and the implicit `orbit` import, is placed in whichever package(s) use it. Usage is decided with object resolution: an `ast.SelectorExpr` whose `X` is an `*ast.Ident` with `Obj == nil` (not a local that shadows the import name) and the import's name. The scan covers the hoisted part, the body, and every template expression.
- **Cost**: one indirect function call per component render, which is negligible.

Path sanitizing (the same relative path in both trees; `src/` is dropped):
- `src/components/Card.orbit` → `orbit_gen/decl/components/card` (package `card`) and `orbit_gen/impl/components/card` (package `card_impl`)
- Each segment is lowercased; `-`, `.` and any other non-identifier character become `_`.
- `src/pages/blog/[slug].orbit` → `pages/blog/slug_param`
- `[...rest]` → `rest_rest`
- A segment that is a Go keyword (`default`, `type`, `func`, …), `main`, `init`, or starts with a digit gets a `p_` prefix: `404` → `p_404`, `default.orbit` → `p_default`.
- Sanitized paths that collide (e.g. `my-card.orbit` and `my_card.orbit`) are an error naming both files.

Extra generated files:
- `orbit_gen/manifest/manifest.go`: per-page asset URLs (prod; dev reads `manifest.json`, §5).
- `orbit_gen/app/app.go`: the route table (with an adapter from each page's typed `Render` to `Route`, §4), the blank import of `orbit_gen/link`, and `func New(opts ...orbit.Option) *orbit.Site`.
- `orbit_gen/link/link.go`: a blank import of every implementation package. It's a leaf package so that a template or frontmatter edit recompiles only that impl package and `link` (8–12 ms at 200 files), while `app`, which imports every page's decl package (21–38 ms to compile), and the server entry stay build-cache hits: Go stops recompiling one level above a package whose compiled output is unchanged. Sharding `link` (16 shards by path hash: a 3 ms recompile) was measured and dropped: within noise of the whole `go build`.
- `orbit_gen/cmd/server/main.go`: the default server entry, generated only if the user has no `cmd/server`.

Each generated file starts with `// Code generated by orbit. DO NOT EDIT.`. Stale dirs are removed only if they carry that marker.

### 3.3 Codegen rules
- **No `gofmt`**: formatting would shift offsets and break source maps. Codegen emits readable code by construction.
- **Line directives** (verified in the spike, milestone 0):
  - **File names are relative** to the generated file's directory (`../../../../src/components/Card.orbit`), with `/` separators on every OS. A relative name is resolved against the directory of the file that contains the directive: `go/scanner` (so `go vet` and gopls's parser) always does this, and `cmd/compile` does from Go 1.27 (it joins `filepath.Dir(file)` with the name; cmd/go passes files relative to its cwd and prints the result relative to the cwd, so `go build` and `go vet` print the same `./src/…orbit:L:C` from the module root, `../src/…` from `src/`, and so on). Go 1.23.4 and 1.24.0 print the relative name unresolved, which is why `go 1.27` is a hard minimum (Context). Relative names keep `orbit_gen/` reproducible and committable and let checkouts share the build cache; absolute names would only have helped on Go ≤1.24.
  - **Form**: always `:L:C`. Columns are 1-based bytes (a tab counts as 1).
  - **Inline spans** (frontmatter body statements, `{expr}`, attribute expressions, control headers, field keys, tag names): an inline `/*line <file>:<line>:<col>*/` right before the span, and right after it a reset `/*line <genfile>:<line>:<col>*/` naming the generated file's bare basename (`render.go`) and the true position of the next character, so generated glue (`)`, `{`, `,`, conversions) never inherits an `.orbit` position. Codegen tracks its own output line and column to emit these.
  - **Hoisted declarations** (imports, types, consts, funcs): framed by **own-line** `//line <file>:<line>:<col>` before and `//line <genfile>:<line>:1` after, with the declaration starting at the beginning of the next line. Inline `/*line*/` comments there become part of the declaration's doc or line comment, so gopls hover shows `line decl.go:13:24`; `go/ast` strips own-line `//line` directives from docs. Multi-line declarations keep correct positions on their continuation lines, because user code is copied verbatim.
  - A page's generated `Params` type has no `.orbit` source (its fields come from the file path), so it gets no directive. It's always valid Go; the errors about it (a collision, a bad param name) are Orbit's own, at the file (§2.2), and a misspelled `params.X` is reported at the use, which is user code.
  - Generated field keys (`Post` for attribute `post`) get a directive pointing at the attribute name. A component call gets one before `Card.Render`, pointing at the tag name.
  - **`-trimpath` doesn't trim directive file names**: stack traces of a `-trimpath` binary show absolute `.orbit` paths (`/abs/…/src/components/Card.orbit:25`), while generated-file frames are trimmed. Document this (`reference/cli.md`).
  - Test (milestone 4): a golden project with deliberate errors (frontmatter, hoisted helper, a continuation line of a multi-line declaration, `{expr}`, control header, unknown prop with the pre-check skipped) asserts that `go build` and `go vet` report the same `src/…orbit:L:C`, and that the CLI's cleaned-up output matches a golden file. gopls ignores line directives (§9), so the LSP integration test checks Orbit's *mapped* diagnostics at the same positions (milestone 12).
- **Error output** (`orbit build`, `orbit dev`'s overlay, `orbit check`): the CLI post-processes `go build`/`go vet` output, which already points at `.orbit` lines.
  - It strips the `[<gen>:L:C]` part of related positions: Go prints "other declaration" lines as `./src/components/A.orbit:7:6[/abs/…/decl.go:10:53]`.
  - It rewrites qualified generated names to the user's names: `card.Props`, or a fully quoted `"example.com/blog/orbit_gen/decl/components/card".Props`, becomes `Card.Props`, using the alias the reporting `.orbit` file gives that component (plain `Props`, and a page's `Params`, in the component's own file). Together with the `_impl` package names (§3.1), messages read in the user's terms.
- **Typed writes**: codegen type-checks template expressions with `go/types` and emits a typed write for each, avoiding `any` boxing and the runtime type switch: `w.String(s)`, `w.Int(int64(n))`, `w.Uint`, `w.Float`, `w.Float32`, `w.Bool`, `w.HTML(h)`, `w.Bytes(b)`, `w.Error(e)`, `w.Stringer(s)`, `w.Render(r)`, and for attributes `w.AttrBool`, with URL attribute values written as pieces through `w.URL(s)` (escaped and scheme-filtered, §4; user decision, milestone 9; `w.AttrURL` stays for other callers). A string or number attribute value (`data-id={n}`, `title={s}`, not a URL attribute) is written **as pieces** (milestone 9): its ` name="` and closing `"` are merged into the neighbouring `Raw` constants and the value is a plain `w.String`/`w.Int`/`w.Uint`/`w.Float`/`w.Float32`, byte-identical to `Attr`, with no boxing (`Attr(name, int)` allocated for values ≥ 256). `uintptr` and named numbers with `Error`/`String`/`Format` methods stay on `Attr`. An `orbit.JSONValue` attribute value is `WriteAttrJSON` (§5c): pieces ` name='` and `'` around `w.JSONAttr("<path>:L:C", <expr>)` (the value's `{`), byte-identical to `Attr`. Pass 2 also produces the components' **client-module types** as a by-product (§5c): per unit, the `data-*`/`set:json` keys (`Output.JSONSites`, found by pass 1, typed by pass 2's `types.Info`) and the named Go types they reach, mapped to TS (`internal/compiler/tstypes*.go`), and the generate-time errors for `orbit.JSON` arguments and `set:json` values encoding/json can never encode; `project.GenFiles` emits them as `orbit_gen/types/*.d.ts`. Typed writes are on in `orbit build`, `orbit generate` and `orbit dev`.
  - The choice mirrors `Expr`'s runtime behavior exactly (§4), so typed and fallback output are byte-identical; a golden test renders the same templates both ways and compares (the spike's 55 expression kinds are its seed).
  - **Exact-type rule**: `Expr`'s type switch matches *exact dynamic types*, so `type Slug string` does **not** hit `case string`; it falls through to `fmt.Sprint`. Call `types.Unalias` first, then map the static type:

    | Static type | Typed write |
    |---|---|
    | untyped `nil` | nothing |
    | constants | by their default type; may be folded into the `Raw` constant |
    | `orbit.HTML` | `HTML` |
    | `string` (or an alias of it) | `String` |
    | `orbit.URL` | `String(string(x))` |
    | `[]byte` | `Bytes` |
    | ints, untyped rune | `Int(int64(x))` |
    | uints, `byte` | `Uint(uint64(x))` |
    | `float64` | `Float` |
    | `float32` | `Float32` (formatted with bitSize 32: `0.1`, not `0.10000000149011612`) |
    | `bool` | `Bool` |
    | `orbit.Renderer`, unnamed `func(*Writer) error` | `Render` |
    | a static interface that implements `error`, or a concrete type implementing `error` | `Error` |
    | a concrete `fmt.Stringer` (value or pointer receiver, `time.Time`, `type Status int` with `String`) | `Stringer` |
    | a named type with no such methods, underlying `string`/int/uint/`bool`/`float64`/`float32` | the matching typed write, with a conversion (same bytes as `fmt.Sprint`) |
    | static `fmt.Stringer`, `any` and other interfaces; named `[]byte` or func types; `T` with `String` only on `*T`; `*string`; slices; `uintptr`; complex | **`Expr`** (the generic path) |

  - **Engine** (no `golang.org/x/tools/go/packages`, which compiles every impl package twice: once for its export data, again in `go build`):
    1. Pass 1 generates all packages with `Expr`/`Attr` fallbacks, **in memory**, recording each expression's offset.
    2. One `go list -export -e` (with the build's `-tags`, `-mod` and `GOFLAGS`) over the non-`orbit_gen` imports: user packages, the runtime and std. Their export data is read with `importer.ForCompiler(fset, "gc", lookup)`. These are compiles `go build` reuses from the cache right after. It's **started in the background** (`Checker.Preload`) as soon as the `.orbit` files are parsed, over the packages parsing predicts (the runtime, `src/locals`, every frontmatter Go import, `time` when there are Markdown files), so it runs during pass 1 and esbuild; the check uses it when it covers every import of the pass-1 output, and otherwise loads again (a wrong guess costs time, never correctness). It's the critical path of `orbit generate` (about 27 ms of 42 at 200 files).
    3. Decl and impl packages are type-checked **from the pass-1 source**, in parallel, behind a memoized importer.
    4. Pass 2 finds each expression by its recorded offset, picks the write from `types.Info.Types`, and **re-emits** the file (rather than patching it), so directive columns stay correct. Then the files are written.
  - **Fallback** to `w.Expr(any)`/`w.Attr`: in tolerant/LSP mode (no type check at all), for a package with type errors (the later `go build` reports them), and, with a warning, when export data can't be read.
  - **Dev**: the checker stays **resident in the dev process**, hot and incremental. A body edit re-checks one impl package; a `Props` edit re-checks that decl package and its importers; a user `.go`, `go.mod` or `orbit.json` edit reruns `go list -export` and re-checks everything. That `go list` starts when the edit is seen (`Incremental.Invalidate` preloads the last load's packages), so it overlaps the front and esbuild.
  - **No persistent type cache**: a full check is at most about 70 ms, mostly `go list`.
  - **Cost** (spike C, Ryzen 7 9700X, 16 threads unless noted; s200 = 200 components, about 5.8k expressions; ±15% noise). The type check is never the bottleneck; `go build` and the link are.
    - Full check, warm: 46 ms at s200 (go/packages: 110 ms).
    - Hot re-check of one edited component: about 0.3 ms (0.24 ms at 16 threads, 0.29 ms on 4 cores).
    - `orbit build` with std cached, s200: 705 ms typed vs. 752 ms all-`Expr` (on 4 cores: 1200 vs. 1308 ms), i.e. within noise. With an empty GOCACHE, about 3.7 s either way.
    - Dev body edit with the resident checker: the all-`Expr` total (236 ms, including the rebuild) plus about 0.3 ms.
    - User `.go` edit that every `Props` depends on: the check step is 69 ms (go/packages: 647 ms), out of a 0.9 s total dominated by `go build` (§7).
    - Typed code and `Expr` code compile at the same speed.
- **Static HTML**: adjacent static text, static attributes and scope attributes are merged at compile time into one `Raw` string constant per run, with static attribute values pre-escaped (§4b).
- **Whitespace** (`compressHTML`, §8, user decision): applied to template text at codegen time, so the `Raw` constants already hold the compressed HTML. `"html"` (default) collapses each whitespace run to one space or newline and drops whitespace-only text whose neighbors are all block boundaries (looking through `{if}`/`{for}`; components, slots and HTML comments count as inline); `"jsx"` applies Babel's JSX line rule per text; `false` is verbatim. `<pre>`, `<textarea>`, `<script>`, `<style>`, HTML comments, attribute values and `{expr}` output are never altered. The exact rules, and the neighbor scan, are in `internal/compiler/DESIGN.md` (settled gap 2) and `internal/compiler/codegen_ws.go`; the user-facing ones in `docs/reference/template-syntax.md#whitespace`.
- **`</head>` marker**: where a template's static HTML contains `</head>` (usually in a layout), codegen splits the `Raw` there and emits `orbit__w.HeadEnd()`, which records the buffer offset for asset injection (§4).
- **Locals** (user decision, milestone 9): `render` declares `locals` **only when the component's code references it** (the same object-resolution scan as imports, §3.1), so a request whose pages and components never read `locals` does no lookup and no allocation. The type is `src/locals.Locals`, or `orbit__rt.NoLocals` without one. (Before milestone 9 it was declared in every `render`.)
- **Source map**: each copied span is recorded as `{kind, orbitStart, orbitEnd, goStart, goEnd}`.
  - `kind=exact` means a 1:1 byte copy: frontmatter statements, expressions, control headers, the import alias.
  - `kind=span` means the whole range maps to the whole range, e.g. attribute name `is-open` → field key `IsOpen`, or a component tag → its `Render` call.
  - `kind=echo` marks the generated `_ = name` lines (§2.2). They map to no `.orbit` range; an LSP rename drops gopls's edits there (§9).
- **Tolerant mode** (for the LSP): the parser recovers. Unclosed tags close at EOF, an unterminated `{` ends at end of line, and errors are collected rather than aborting. No type-checking; every expression uses the `Expr` fallback. Each expression sits on its own line inside `w.Expr(...)`, so broken input stays local and gopls's error-tolerant parser can still complete `props.Po|`.

### 3.4 `server:defer` and `client:*` call sites
**Component IDs**: `<Name>-<hash8>`, the file's base name plus the 8 hex chars of its scope hash (§5): `src/components/Comments.orbit` → `Comments-9b1e44a2`. They're the same on every OS and in every build, and are used in island URLs and lazy markers (decided by rule: Astro names island endpoints after the component; the hash keeps two `Comments.orbit` files apart).

**`server:defer`**: the call site doesn't call `Render`. For
```orbit
<Comments server:defer postID={post.ID}><p slot="fallback">Loading comments…</p></Comments>
```
codegen emits:
```go
if orbit__err := orbit__rt.Defer(orbit__ctx, orbit__w, "Comments-9b1e44a2", /*line ../../../../src/pages/blog/[slug].orbit:14:4*/Comments.Props/*line render.go:…*/{
	/*line …*/PostID/*line render.go:…*/: /*line …*/post.ID/*line render.go:…*/,
}, func(orbit__w *orbit__rt.Writer) error { orbit__w.Raw("<p data-o-5c7d1e2f>Loading comments…</p>"); return orbit__w.Err() }); orbit__err != nil {
	return orbit__err
}
```
and `Defer` (§4) writes:
```html
<orbit-island src="/_orbit/island/3f9a2c1d7e4b5a60/Comments-9b1e44a2" props="<token>"><p data-o-5c7d1e2f>Loading comments…</p></orbit-island>
```
- The props literal is type-checked by Go and pre-checked for unknown props (§2.3), as in a normal call. The fallback is compiled in the parent, like slot content, so it carries the parent's scope attribute. With no fallback, `nil` is passed.
- **Sealing** (`internal/islandcrypto`, about 30 lines, stdlib only; a deterministic SIV construction):
  - **Keys**: two 32-byte keys derived from the master island key (§4) with `crypto/hkdf` over SHA-256, using the info strings `"orbit island mac"` and `"orbit island enc"`. They're derived once per `Site`, and the AES-GCM cipher is created once too.
  - **Nonce**: `HMAC-SHA256(macKey, lenprefix(componentID) ‖ lenprefix(buildID) ‖ propsJSON)[:12]`, where `propsJSON` is `Defer`'s `encoding/json` output.
  - **Token**: `nonce ‖ AES-256-GCM(encKey).Seal(nonce, propsJSON, ad)`, as base64url with no padding. The associated data `ad` is `lenprefix(componentID) ‖ lenprefix(buildID)`. Both values come from the island URL's path (§5b), so a token can't be moved to another component or to another build's path. Length prefixes keep the concatenation unambiguous.
  - **Opening**: verify and decrypt with the GCM tag, then recompute the HMAC nonce from the plaintext and compare it with the token's nonce using `subtle.ConstantTimeCompare`. A mismatch is rejected.
  - **Deterministic**: the same props, component and build always give the same token, so the same island URL across renders and instances. That makes island URLs cache-ready (HTTP caching of islands comes after the MVP, §12). A nonce repeats only for identical inputs, which give identical ciphertexts, so there's no nonce-reuse hazard; an observer learns only whether two tokens hold equal props, which a cacheable URL reveals anyway.
  - All primitives are FIPS-approved (HKDF, HMAC-SHA256, AES-GCM).
  - **Measured**: about 0.42 µs to seal 128 B of props, 0.94 µs for 1 KB and 4.9 µs for 8 KB (a vendored pure-Go AES-GCM-SIV, the alternative considered, took 0.75 / 3.1 / 21.7 µs).
  - **Confidential and tamper-proof, but not bound to a user or a time**: anyone who has a token can replay it. Authorization therefore belongs in the component (cookies, `locals`), never in props. Document this in `lazy-loading.md`.
- **JSON-serializable props, checked at generate time** in the go/types pass (§3.3, pass 2). Orbit walks the target's whole `Props` type (every field is encoded, whether the call site sets it or not) using `encoding/json`'s rules, and reports an error at the `server:defer` attribute, naming the field path:
  - funcs (so also `orbit.Renderer` and `orbit.Slots`), channels, `unsafe.Pointer`, complex numbers;
  - interface types, including `any` and `error`: a decoded value can't be verified to have the same dynamic type;
  - map keys other than strings, integers or `encoding.TextMarshaler`s.

  Types that implement `json.Marshaler` together with `json.Unmarshaler` (on the pointer), or the `encoding.TextMarshaler`/`TextUnmarshaler` pair, are accepted as they are (e.g. `time.Time`). Fields tagged `json:"-"` and unexported fields of nested structs are skipped, as `encoding/json` skips them (decided by rule: Go stdlib convention). Example: `src/pages/blog/[slug].orbit:14:13: <Comments server:defer>: Props.OnLoad has type func(), which can't be sent to a deferred component; props must be JSON-serializable`.
  - The walk covers only the `Props` types of deferred call sites, so its cost is expected to be well under 1 ms; it's measured with the rest of pass 2.
  - Where the type check doesn't run (tolerant/LSP mode, a package with type errors, unreadable export data), `Defer`'s `json.Marshal` error becomes a render error at the `.orbit` position.
- **The island table**: `orbit_gen/app` registers every component that appears with `server:defer` anywhere in the project, and only those, so no other component can be rendered by URL:
  ```go
  orbit.NewIsland("Comments-9b1e44a2", "src/components/Comments.orbit", comments.Render)
  ```
  `NewIsland` (§4) is generic over `Props`: it decodes the opened JSON into a `Props` with `json.Unmarshal` and calls `Render` with no slots. Unknown JSON fields are ignored and missing ones stay zero (`encoding/json` defaults), so a page rendered by the previous deploy still loads its islands when `Props` gains a field.

**`client:*`**: the call site renders the component normally, wrapped in a marker element. The marker is folded into the surrounding `Raw` constants, so it costs only its bytes at render time:
```html
<orbit-lazy component="Counter-1c2d3e4f" client="visible" opts="200px">…component output…</orbit-lazy>
```
- It's a wrapper element, like Astro's `<astro-island>` (decided by rule: Astro behavior. Observers need an element, and a component's output can have zero or several root elements). Head injection adds `orbit-island,orbit-lazy{display:contents}` once (§5), so the wrapper doesn't affect layout, but it is in the DOM: a child selector such as `.list > .item` doesn't match across it. Document this.
- `client:visible` observes the wrapper's element children, as Astro does, because a `display:contents` element has no box of its own.
- The wrapper is always emitted for a lazy directive, even on a page where the component's scripts end up eager (eager wins, §5). The loader ignores IDs that aren't in the page's lazy map.

## 4. Runtime package (`github.com/orbit-z/orbit`, repo root)
The runtime package depends only on the standard library (plus the framework's own stdlib-only `internal/islandcrypto`, §3.4, §10).

                                                                // returns r unchanged when one is already attached

- Tests import a component through its declaration package (`card "example.com/blog/orbit_gen/decl/components/card"`) and link everything with `import _ "example.com/blog/orbit_gen/app"`. Without that import, the `Render` wrapper panics with its "not linked" message (§3.1), and `orbittest` repeats the hint.
- Tests live in normal Go packages (e.g. `internal/views_test/`, or next to `cmd/server`), not in `src/`.
- `orbittest` renders with the same pooled `Writer` and escaping code as SSR, so the output equals production output.
  - **`Render`** calls the component's `Render` directly, with `httptest.NewRequest("GET", "/", nil)` unless `WithRequest` is given. No middleware runs and **no head injection** happens (a component on its own has no page assets, like `RenderComponent`). `server:defer` call sites write their placeholder, sealed with a **fixed test island key and the build ID `0000000000000000`**, so placeholders are identical on every run and snapshot tests of pages with islands are stable (decided by coordinator: simplest).
  - **Test detection (milestone 8, user decision)**: `testing.Testing()`; measured +38 KB on a minimal server binary (+68 KB on a small `net/http` program), and it registers no test flags.
  - **`Get`** sends a GET through the given handler, so routing, the user's middleware and head injection all apply, and islands use that site's own key and build ID. Under `go test`, `app.New()` uses the same fixed test key and build ID `0000000000000000` as `Render` (detected with `testing.Testing()`, decided by rule: consistent with `Render`), unless `ORBIT_KEY` or `WithKey` is set, so `Get` snapshots of pages with islands are stable too. Only `WithLocals` (attached to the request, so `EnsureLocals` returns it) and `WithRequest` (a copy with method GET and URL `path`) apply to `Get`.
  - **`WithParam`** applies to `Render` only (with `Get`, the router sets params from the path). It's repeatable, one call per param, and a later call for the same name replaces the earlier value (decided by rule: Go stdlib, like `http.Request.SetPathValue(name, value)`; replaces the removed `WithParams(orbit.Params)`). A page rendered with `Render` gets its typed `params` from these values through its `Render` wrapper (§3.2); a param the page's route doesn't have is ignored by `params` but still visible to `ctx.Param`.
  - An option passed to a function it doesn't apply to fails the test rather than being ignored (decided by rule: simplest).
  - `orbittest` owns the `-update` flag; a test package that imports it must not define its own (`flag.Lookup("update")` reads it).
- **HTTP layer**: stdlib `net/http` only, with no web framework dependency.
  - Orbit's file-based router is its own matcher, because Go's `ServeMux` can't express `[...rest]` and Astro's priority rules.
  - **Method rule**: static files (`/_orbit/*` assets, `public/` files) answer **GET and HEAD only**; pages answer **all methods** (§5b). The island endpoint `/_orbit/island/…` answers GET, HEAD and POST; any other method gets a 405 with `Allow: GET, HEAD, POST` (decided by rule: Astro also answers 405, and `ServeMux` sets `Allow`).
  - Static files are served with `http.ServeContent` (ETag, Range). `/_orbit/*` files have hashed names and get `Cache-Control: public, max-age=31536000, immutable` (dev: `no-cache`).
  - Page responses get `Content-Type: text/html; charset=utf-8` unless the page set one (`ctx.Header()`).
  - Everything is a standard `http.Handler` or middleware, so it composes with chi/Gin/Echo and any ecosystem middleware.
- **`Expr` escaping**, checked in this order against the value's *exact* dynamic type (a `type Slug string` isn't `string` and falls through to `fmt.Sprint`; typed writes mirror this, §3.3):
  - `nil` → nothing
  - `HTML` → raw
  - `string`, `URL` → HTML-escaped
  - `[]byte` → HTML-escaped as a string
  - ints, floats, bools → strconv (`float32` with bitSize 32, so `float32(0.1)` prints `0.1`)
  - `Renderer` / `func(*Writer) error` → called
  - `error` → escaped `Error()`
  - `fmt.Stringer` → escaped string
  - slices of these → each element
  - anything else → `fmt.Sprint`, escaped
- **`Attr`**:
  - `true` → bare attribute
  - `false` / `nil` → omitted
  - anything else → attribute-escaped and quoted
  - **URL attributes** (`action`, `background`, `cite`, `codebase`, `data`, `formaction`, `href`, `icon`, `longdesc`, `manifest`, `poster`, `profile`, `src`, `usemap`, `xmlns`: `html/template`'s list, plus `xlink:href`; decided by rule: Go stdlib): a value whose scheme, after trimming whitespace and control characters and ignoring case, is `javascript:` or `vbscript:` is replaced with `about:invalid#orbit`, unless it has type `orbit.URL`. This applies to `Attr`, `AttrURL` and `Spread`.
- A slice in an attribute value is formatted as in content (elements concatenated, no separator).
- **`Spread`**: each attribute name must match `[A-Za-z_:][-A-Za-z0-9_:.]*`; an invalid name (spaces, quotes, `>`, `/`, `=`) is a render error. Entries are written sorted by name, so output is stable, at the spread's position. Duplicates of attributes written on the same element aren't merged: both are written, and browsers use the first.
- **Buffered responses**: SSR responses are always buffered, never streamed. A page renders into a `sync.Pool`'d `bytes.Buffer`; then the response gets `Content-Length` and is written once. Middleware that must rewrite a response wraps the `http.ResponseWriter` in standard net/http style (§5b).
- **Head injection**: the page's `<link rel=stylesheet>` and `<script type=module>` tags (and the loader) are built **once per route** in `NewSite` (per request in dev with a dev manifest) and written by the first `HeadEnd()` (the first `</head>`) during the render, so the page body is never moved (milestone 9: −10% on a small page with assets). With no marker, they go right after a leading `<!DOCTYPE …>` (never before it, which would trigger quirks mode), otherwise at the start. Injection happens before the response is written, so wrapping middleware sees the final HTML. Pages that need it also get the inline loader and its `display:contents` style here (§5).
- **Router**: routes are compiled into a segment trie (no regexp): static, `[param]`, and `[...rest]` (matches 0+ segments). Priority is static, then param, then rest; ties go to more segments, except that an exact route beats a rest param matching zero segments (`/docs` beats `/docs/[...rest]` at `/docs`; decided by rule: Astro). `index.orbit` is the directory root, and `404.orbit` is used for not-found.
  - **`_` files aren't routes** (decided by rule: Astro): a file under `src/pages/` whose name, or a directory on its path, starts with `_` is a component (`src/pages/blog/_parts/Byline.orbit`). So `src/pages/_orbit/…` is never a route, and no page can sit under the reserved `/_orbit/` prefix; the runtime router still rejects such a pattern at startup.
  - Malformed brackets are build errors at the file: `invalid route pattern "/[slug": segment "[slug" has unbalanced brackets`, `invalid route pattern "/blog/[]": segment "[]" has an empty parameter name` (decided by rule: simplest).
  - Param values are percent-decoded, like `ServeMux`'s `PathValue`; a rest param is the matched segments joined with `/`, and `""` when it matches none.
  - **Param storage**: the router writes each match into the pooled `Ctx`'s param storage (a reused slice of name/value pairs: names are the route's own strings, values are substrings of the request path), read back with `ctx.Param`. There's no map, so a param match allocates nothing (a map cost 2 allocs / 336 B); only a value that needs percent-decoding allocates its decoded string. The storage is reset when the `Ctx` goes back to the pool.
  - Route param names must match `[A-Za-z][A-Za-z0-9_-]*` and give distinct `Params` field names; both are build errors at the file (§2.2).
  - **Unsupported route shapes are build errors** at the file (user decision for the MVP): a segment that mixes text and a parameter (`post-[id].orbit`, `[lang]-[version].orbit`), and a rest param that isn't the last segment (`[...path]/edit.orbit`). Both messages suggest a whole-segment `[param]`: `src/pages/blog/post-[id].orbit: route segment "post-[id]" mixes text and a parameter; use a whole-segment parameter such as [id].orbit and parse it in the page`.
  - Two files with the same route (`blog.orbit` and `blog/index.orbit`, or `[slug].orbit` and `[id].orbit` in one directory) are a build error naming both files.
  - Without a `404.orbit`, not-found responses are a 404 with an empty body.
- **Trailing slashes: none** (user decision; one fixed behavior, the `trailingSlash` modes are deferred, §12). A page's canonical URL has no trailing slash: `/blog/hello`, and `blog/index.orbit` is `/blog`. `/` stays `/`. The router answers `/blog/hello/` with a **308 to `/blog/hello`**, keeping the query string (`/search/?q=go` → `/search?q=go`), as `net/http`'s `ServeMux` does for its redirects. Same in dev and prod. Paths for files (`/_orbit/…`, `public/` files) are never redirected.
  - The redirect is issued only when the path without its trailing slash matches a page route; otherwise the request falls through to `next` untouched, so a user route such as `/api/items/` keeps working in Orbit-first setups. *Decided by rule* (simplest option that never steals the user's routes; log it in `docs/DECISIONS.md`).
- **Errors**: panics are recovered per request.
  - Prod (user decision): a minimal built-in page (`500 Internal Server Error`), never showing the error. The error and its `.orbit` position are logged to stderr with the `log` package (`orbit: GET /blog/hello: src/pages/blog/[slug].orbit:14:5: …`): for a returned error, the position of its frontmatter `return` (§2.2, `orbit.ErrorAt`); for a panic, the innermost `.orbit` line on the stack. A custom `src/pages/500.orbit` comes after the MVP (§12).
  - Dev: error overlay with file:line.
- **Locals helpers**: `EnsureLocals` is what middleware uses. It returns the attached `*L` (and `r` unchanged), or attaches a `new(L)` with `WithLocals` and returns the new request, so every middleware in the chain can call it and they all share one value. `LocalsFromRequest` returns `nil` when nothing is attached, rather than a detached zero value whose writes would be silently lost (decided by rule: Go stdlib convention; context accessors such as `httptrace.ContextClientTrace` return nil when absent). Pages never see nil: `LocalsOf` allocates. `WithLocals` on a request that already carries locals shadows them for handlers further down only, like `context.WithValue`; middleware that ran earlier keeps its pointer (decided by rule: Go stdlib).
- **Island key** (resolved once, in `NewSite`), in this order:
  1. `WithKey`, if given.
  2. `$ORBIT_KEY`: standard base64 of exactly 32 bytes. Anything else panics at startup with a clear message (decided by rule: Go stdlib convention for constructors without an error result, like `ServeMux.Handle` with a bad pattern).
  3. The key that `orbit build` embeds in the binary: fresh random bytes per build, set with `-ldflags=-X` (§6), so no key is written to `orbit_gen/` (which stays deterministic) or to the repo. Astro also generates a key per build and embeds it.
  4. Otherwise (plain `go build` or `go run`), a random key per process, with a one-line warning on stderr.

  All instances of one build share the embedded key, so horizontally scaled instances open each other's tokens. A new build has a new key, so during a **rolling deploy**, islands on pages from the old version get 400s from new instances and keep their fallback. Production deploys with rolling updates (or several builds behind one load balancer) need a stable `ORBIT_KEY`, created with `orbit create-key` (§6). Document this in `deploy.md` and `lazy-loading.md`. `RenderComponent` fragments seal with the same key resolution, minus `WithKey`.
- **Build ID**: 16 hex chars (64 random bits), embedded by `orbit build` with `-ldflags=-X` next to the key, or random per process otherwise (fixed to `0000000000000000` under `go test`, per `testing.Testing()`). It's part of every island URL path (`/_orbit/island/<buildID>/<id>`, §5b) and of the associated data (§3.4), so each deploy gets fresh island URLs (future cache keys, §12). The endpoint accepts any build ID that authenticates, not only its own, so with a stable `ORBIT_KEY`, rolling deploys keep working (decided by rule: simplest option that doesn't break rolling deploys).
- **Loader**: the client loader (§5) is TypeScript in the framework repo (`loader/`). `go generate` minifies it with esbuild into a committed Go string constant, so the runtime embeds it with no dependency.

## 4b. Performance design
The SSR hot path is built for speed. There's no fixed target number; the results are measured and published (see Benchmarks below).
- **Static HTML is precomputed**: adjacent static text and attributes are merged into one `Raw` string constant per run (§3.3), so most of a page is a few `copy`s.
- **Static attributes are pre-escaped** at compile time, including the scope attribute.
- **Zero-alloc escaping**: the escaper scans for characters that need escaping and, if there are none, writes the original string directly.
- **No bufio layering**: the `Writer` writes straight into the pooled `bytes.Buffer` (§4).
- **No reflection on the hot path**: typed writes (§3.3) cover expressions; `Expr`'s type switch handles the common types, and reflection appears only in its last-resort `fmt.Sprint` and generic-slice cases.
- **Slots are a value struct**, not a map: `Default` plus a small `Named` slice. A call with no children allocates nothing, and neither does slot content that uses no parent variables (a static func value). Slot content that captures parent variables (`<Card>{p.Title}</Card>`) allocates one closure per such slot, because the call goes through the decl package's hook and escapes. **Revised (user decision, 2026-10-26)**: `orbit build` will use direct calls for acyclic imports, keeping the closures on the stack, while `orbit dev` keeps the hooks so a component body edit doesn't recompile its parents; spec in §3.5 (being written). Measured (500 capturing slots, `GOMAXPROCS=1`): hook 13.0 µs, 500 allocs, 24 KB; direct 7.6 µs, 0 allocs.
- **Zero allocations in Orbit's own render path** is a tested rule (like the router's 0-alloc match): from milestone 5, `testing.AllocsPerRun` tests assert that a typical page (typed writes, static or no slot content, no locals, no `server:defer`) renders with 0 allocations in Orbit's code, and is served with exactly 1: the `Content-Length` value (string and `[]string` in one 48-byte object), which can't be pooled because `net/http` may read header values after the handler returns. Measured (milestone 5): render 0 allocs, serve 1 alloc / 48 B, about 200 ns for a small param page. The floor that remains is `net/http`'s own: measured on Go 1.27.3 at about 14 allocs (1.4 KB) per request for an empty handler and about 19 (2.2 KB) for a 1 KB page; a test measures Orbit's handler on top of that with a reused `ResponseWriter`. What may still allocate: locals (`new(L)`, and `EnsureLocals`' context copy; not pooled, since a retained `locals` would then be silently reused), slot closures that capture, the `Expr` fallback and user `String()`/`Error()` methods, percent-decoded params, `server:defer` props, `orbit.JSON` values (encoding/json's own allocations only: boxing a non-pointer value, and its internal copy of a non-addressable one; Orbit's reused per-Writer encoder adds 0, asserted by `TestJSONAttrAllocs`, §5c), and user code.
- **Response headers** use shared, read-only `[]string` values for constant headers (`Content-Type: text/html; charset=utf-8`) instead of `Header().Set`, saving one allocation per request (measured 20.7 → 18.9 allocs/request).
- **Route matching** walks a precompiled segment trie, with no regexp. Matched params go into the pooled `Ctx`'s storage, not a map, so a param match is **0 allocations** (it was 2 allocs / 336 B with `map[string]string`); a page's typed `Params` is a stack value built from `ctx.Param` calls (§3.2).
- **`Ctx` is pooled** per request (with its `Writer` and buffer).
- **Locals are allocated lazily**, on the first `LocalsOf`.
- **gzip is left to the user's middleware**; Orbit never compresses.
- **`server:defer` keeps slow parts off the first byte.** Responses are always buffered (§4), so a page's first byte waits for its slowest part. `server:defer` is the way to keep slow parts (DB queries, third-party APIs) from delaying it: the page renders the fallback and is sent at once, and the slow component renders in its own island request (§3.4, §5b). Cost on the page: one `json.Marshal` (reflection, off the template hot path) and one seal (HMAC-SHA256 plus AES-GCM, about 1 µs for 1 KB of props, §3.4) per deferred instance, plus the inline loader (a few hundred bytes). Pages without islands pay nothing. Documented in `rendering.md`, `performance.md` and `lazy-loading.md`.
- **`client:*` markers are static**: the `<orbit-lazy>` wrappers are folded into `Raw` constants (§3.4), so lazy scripts cost nothing at render time.
- **The exported runtime types stay light for importers** (dev-loop compile time): every generated package mentions `*orbit.Ctx`, and the compiler loads the type graph it reaches, including unexported fields and method signatures, and compiles any generic instantiation found there (with its type descriptors) again in each importer. So `Ctx`'s and `Site`'s keyring holds the `*islandcrypto.Sealer` as `any` (read with the `sealerOf` function, not a method), which keeps its `sync.Pool`'s `atomic.Pointer[poolChainElt]` out of every generated package: a package mentioning `*orbit.Ctx` went from 196 symbols to 6 (object 149 → 94 KB, mostly export data). Same allocations and island benchmark numbers.

**Benchmarks** (results published in `docs/performance.md`; no CI regression gates):
- **Head-to-head vs. Astro**: two dedicated, mirrored sites, `bench/orbit-site` and `bench/astro-site` (kept separate from `examples/blog` so the example stays clean and the comparison is easy to audit). The Astro one is an equivalent project served by `@astrojs/node` in standalone mode, as a single process (no cluster, no Bun). Scenarios, driven by a load tester such as `oha`:

## 5. Assets (scripts and styles)
- **Scope ID**: `o-` + the first 8 hex chars of sha256 of the file's project-relative path with `/` separators (`src/components/Card.orbit`), so IDs are the same on every OS. It's added as an attribute to every HTML element in the template, but only when the component has a scoped `<style>`.
- **Scoped CSS**: parse with `tdewolff/parse/v2/css`. Add the attribute selector `[data-o-xxxx]` to the last compound of each selector (Astro's default `scopedStyleStrategy: "attribute"`, user decision at the dogfood checkpoint): +1 attribute specificity, so scoped rules beat global rules with the same selector whatever the bundle order. Within the compound it goes before the first pseudo-class or pseudo-element (`a:hover` → `a[data-o-…]:hover`), as in Astro.
  - Recurse into `@media`, `@supports` and `@layer`.
  - Skip the bodies of `@keyframes` and `@font-face`.
  - `:global(sel)` opts out locally; the scope then goes on the nearest compound outside the `:global(…)` (`.prose :global(p)` → `.prose[data-o-…] p`), and a fully `:global` selector isn't scoped. Pseudo-classes and pseudo-elements come after the scope (`p::first-line` → `p[data-o-…]::first-line`), as in Astro.
  - **Order in the page stylesheet**: the import graph in module-evaluation order: a component's imports first, in import order, then its own styles; each component once.
- **`is:inline`** is stripped from the emitted tag; every other attribute stays as written (Astro behavior).
- **Which scripts are processed** (Astro's rule): a `<script>` with no attributes, or only a `src` pointing at a local relative file, is processed and bundled. Any other attribute means it's left as-is, like `is:inline`: `type="application/ld+json"`, `type="text/template"`, `async`, `src="https://…"`, and so on.
- **Per-page graph**: a page's assets are its own scripts and styles plus those of every transitively imported component. This is static, from imports, like Astro: a component's script is included once per page, even if it's rendered conditionally or many times.
- **esbuild**: one build call with a plugin that serves virtual modules (`orbit:script/<id>.ts`, `orbit:style/<id>.css`), each with `resolveDir` set to its `.orbit` file's directory, so relative imports and the nearest `tsconfig.json` resolve from there.
  - One entry per page: `format=esm`, `bundle`, `minify`, hashed names under `/_orbit/`. No code splitting in the MVP (§12): each page's bundle is self-contained.
  - A page with no scripts gets no JS entry and no `<script>` tag.
  - Bare imports resolve from `node_modules` if one exists.
  - **Implemented (milestone 6)**: block modules resolve to the `.orbit` file itself (file namespace, `?orbit-script=i` suffix) with content padded to the block's line and column, so esbuild's error positions and source maps are `.orbit` positions and `resolveDir`/tsconfig lookup come for free. `orbit generate` also bundles, in memory, so `generate` and `build` write the same `orbit_gen/` (about 8 ms on 200 components). Fonts and images imported from scripts/CSS are hashed into `/_orbit/`. An import of a `.orbit` file that isn't a block (`import { data } from "./X.orbit"` from a block script or a `.ts` file) loads one constant module, `export { data, json } from "orbit:client"`; `orbit:client` is the embedded runtime (`internal/assets/client/client.ts`, 368 B minified) and `orbit:types` is empty (§5c). The CLI binary grows by about 8 MB with esbuild; user servers don't link it.
  - **CSS imported from a script** (`import "flatpickr/dist/flatpickr.css"`) joins the page's stylesheet, unscoped, as esbuild bundles CSS imports by default (decided by coordinator: esbuild default). A lazy component's imported CSS stays in the page stylesheet too.
- **Lazy entries (`client:*`)**: each component that has a processed `<script>` and at least one lazy call site (`client:idle`, `client:visible` or `client:media`) anywhere gets its own esbuild entry, `orbit:lazy/<id>.ts`, which imports that component's script modules. It's built with the same settings into `/_orbit/<Name>-<hash>.js`, and is self-contained because there's no code splitting (§12).
  - **Whole-subtree scope and eager wins, per page** (user decision: a directive covers the component's whole subtree):
    - A component is **eager on a page** if it's reachable from the page root (deferred islands included) by a path of call sites that crosses **no** lazy directive. Its scripts go in the page bundle.
    - Every other component with scripts that's reachable only through lazy call sites is **lazy on that page**: it gets no page-bundle entry, and the page lists its entry as a `lazy` asset `{ID, URL}`.
    - Entries stay **per component**, deduplicated across call sites. Each lazy *call site* gets a static list (in the page's lazy map) of the entries to `import()` when its strategy fires: the tagged component plus every lazy-on-this-page component in its static subtree.
    - A directive-less call inside a lazy subtree is part of that subtree, so it's lazy unless the same component is also reached eagerly elsewhere.
    - A nested lazy directive inside a lazy subtree takes its own components out of the outer list. Its own strategy is observed only after the outer one has fired.
  - Scripts stay once-per-page modules: the loader `import()`s each entry at most once, when the first instance meets its strategy. With several strategies on one page, whichever fires first loads it.
  - A module that queries the DOM when it loads sees only the instances present at that moment, not those that arrive later in a deferred island. So `styles-and-scripts.md` and `lazy-loading.md` recommend custom elements (`customElements.define` with `connectedCallback`) for the scripts of lazy and deferred components.
  - Code shared between a lazy entry and the page bundle (e.g. `src/scripts/util.ts`) is duplicated, and each copy has its own module state, until code splitting arrives (§12). Document this.
  - Styles are unaffected: a lazy component's CSS stays in the page's stylesheet.
- **Deferred components' assets**: a `server:defer` component and everything it imports stay in the page's static graph, so their CSS and scripts load with the page, and the island fragment needs no assets of its own. Those scripts run before the fragment arrives, which is another reason for custom elements.
- **The loader**: one small inline `<script type="module">` (TypeScript source in the framework's `loader/`, minified (islands about 1.1 KB, lazy about 1.3 KB; about 0.75 KB each gzipped) and embedded in the runtime, §4), plus `<style>orbit-island,orbit-lazy{display:contents}</style>`. Head injection adds it only to pages that need it: the islands part when `Route.Islands` is set, and the lazy part, with the page's `{id: url}` map, when the page has `lazy` assets. Both are decided statically from the page's graph, so islands nested in fragments are covered (decided by rule: consistent with the static asset graph above). The loader is inline, as Astro inlines its island scripts, which saves a request before the island fetches can start (decided by rule: Astro behavior). A strict CSP needs `'unsafe-inline'` or the script's hash; document this (CSP hashes are deferred, §12).
  - **Islands**: once the page is parsed, the loader fetches every `<orbit-island>` in parallel, with `GET <src>?p=<token>`, where `src` is `/_orbit/island/<buildID>/<id>` as written by `Defer` with the build ID of the instance that rendered it. When that URL would exceed 8000 characters (about 8 KB of props), it uses `POST` to the same path instead, with the token as a `text/plain` body (decided by rule: simplest limit that fits nginx's default 8 KB request-line buffer; Astro switches at 2048). Fetches use `redirect: "manual"`.
    - On a 2xx response, the placeholder is replaced by the fragment, parsed with `Range.createContextualFragment` so that inline scripts in it run (as in Astro, no wrapper remains). The new nodes are then scanned for `<orbit-island>` and `<orbit-lazy>` elements, so nested islands and lazy components inside islands work.
    - On any other status, or a network error, the fallback stays. In dev, the loader logs the status and the response body with `console.error`; in prod it stays silent (decided by rule: simplest).
  - **Lazy**: observes each `<orbit-lazy>` whose ID is in the map, according to its strategy, and `import()`s the entry when the first instance fires.
  - **Without JS**, island fallbacks stay, and lazy components are still rendered on the server; only their scripts never load.
- **TypeScript** (client side):
  - `<script>` content is **TypeScript by default**, like Astro: the virtual modules use `loader=ts`. Plain JS is valid TS, so nothing breaks.
  - Scripts can import `.ts`/`.tsx`/`.js` files from anywhere in the project (e.g. `src/scripts/`) and npm packages.
  - esbuild picks up `tsconfig.json` if present (`paths`, `target`, `jsx` settings).
  - esbuild **only strips types and doesn't type-check**. Type checking is done by `orbit check` through **Bun** (§6). `orbit new` scaffolds a `tsconfig.json` modeled on Astro's `strict` preset (`target`/`module` `ESNext`, `moduleResolution: Bundler`, `strict`, `noEmit`, `isolatedModules`, `rootDirs: [".", "orbit_gen/types"]`, `include: ["src/**/*.ts", "orbit_gen/types/*.d.ts"]`, §5c) and an empty `src/env.d.ts` for the user's global declarations (no `package.json` or `typescript` package is needed, since `bun check` bundles the checker).
  - `<script is:inline>` is emitted untouched, so it must be plain JS.
- **Manifest**:
  - Prod: the result is compiled into `orbit_gen/manifest`, mapping page → `[]Asset` (including its `lazy` entries).
  - Dev: esbuild uses an incremental `api.Context` that outputs to `.orbit/dev/_orbit/` and, after every rebuild, writes `.orbit/dev/manifest.json` atomically (temp file plus rename). With `ORBIT_DEV=1`, the app reads asset URLs from `$ORBIT_STATIC/manifest.json` (re-read when its mtime changes) instead of the compiled manifest, so a CSS/JS-only rebuild with new hashes needs no Go rebuild.

## 5b. Orbit as middleware, the server entry, and typed locals

### Orbit is an `http.Handler` middleware, and the user chooses its position
`site.Middleware(next)` works like this:
- If the request matches something Orbit owns, Orbit serves it:
  - `/_orbit/*` and `public/` files, for **GET and HEAD only**; other methods fall through to `next`.
  - page routes, for **all methods** (the page reads `ctx.Request.Method`). So `POST /blog/hello/like` reaches the user's mux only if no page matches it, and a `[...rest]` page claims every method under its prefix; document this for Orbit-first setups.
- Otherwise it calls `next.ServeHTTP` **untouched**. Nothing is buffered or written.

So the user's own `main.go` decides precedence just by composing handlers:

```go
// cmd/server/main.go  (scaffolded by `orbit new`, owned by the user)
func main() {
    site := app.New()                       // generated: example.com/blog/orbit_gen/app

    api := http.NewServeMux()
    api.HandleFunc("GET /api/posts", listPosts)
    api.HandleFunc("POST /blog/{slug}/like", like)   // can call orbit.RenderComponent(...)

    // A) Custom routes take precedence over pages: the mux's "/" is the least specific
    //    pattern, so any more specific route wins and everything else goes to Orbit.
    api.Handle("/", site.Handler())
    h := logging(theme(api))

    // B) Pages take precedence: Orbit first, falling back to the mux. Give the mux a
    //    catch-all so unmatched paths render 404.orbit instead of the mux's plain 404.
    // api.Handle("/", site.NotFound())
    // h := logging(theme(site.Middleware(api)))

    if err := orbit.ListenAndServe(h); err != nil {
        log.Fatal(err)
    }
}
```

- Because it's a plain `func(http.Handler) http.Handler`, Orbit can also sit inside chi (`r.Use(site.Middleware)` or `r.NotFound(site.Handler().ServeHTTP)`), Gin (via `gin.WrapH`), and so on. These embeddings aren't tested in the MVP (§12).
- **Middleware order**:
  - Middleware wrapped *outside* Orbit (logging, auth, CORS, gzip) applies to pages and custom routes alike.
  - Middleware placed *after* Orbit only sees requests Orbit didn't handle.
  - There is no Orbit-specific middleware type (no `OnRequest`; user decision). All middleware is plain `func(http.Handler) http.Handler` in the user's `main.go`; request-scoped data reaches pages through typed locals (below).
- **Inside `site.Middleware`** (prod and dev):
  1. Island endpoint `/_orbit/island/<buildID>/<id>` (GET, HEAD, POST; other methods get a 405): render a deferred component as a fragment (see "Deferred island requests" below). This prefix is reserved and is never a static file.
  2. Static file lookup (`/_orbit/*`, `public/`; GET/HEAD only).
  3. Page router (trie match; the trailing-slash 308, §4).
  4. Take the `*Locals` attached by `EnsureLocals`/`WithLocals` from the request context, if any (otherwise `LocalsOf` allocates lazily).
  5. Page `Render` into the pooled buffer, then head injection at the `HeadEnd` offset.
  6. Write the response once, with `Content-Length`.

  If none of steps 1–3 matches, it calls `next`. `site.Handler()` uses `NotFound()` (which renders `404.orbit`) as `next`.
- **Short-circuits** come from the page frontmatter: `return ctx.Redirect("/login", 302)`, `return orbit.ErrNotFound` (renders `404.orbit`), or `return err` (500). Middleware can also short-circuit the usual net/http way, by writing a response and not calling `next`.
- **Response rewriting** (headers, status, body) uses a standard wrapping `http.ResponseWriter` in the user's middleware. Because page responses are buffered and written once (§4), the wrapper sees the complete HTML with assets injected.
- **Server entry**: `orbit.json` `"server": "./cmd/server"` (the default when the directory exists).
  - Without an entry, Orbit generates `orbit_gen/cmd/server`, which runs `orbit.ListenAndServe(app.New().Handler())`.
  - `orbit new` always scaffolds `cmd/server/main.go`, so the composition is visible from day one.
- **Dev and prod**: the same user `main` runs in both.
  - The dev server builds the entry and runs it with `ORBIT_DEV=1`, `ORBIT_ADDR=127.0.0.1:<port>`, `ORBIT_STATIC=.orbit/dev` (holding `_orbit/` and `manifest.json`) and `ORBIT_PUBLIC=public`. It also passes an `ORBIT_KEY` generated once per `orbit dev` session, so open pages' islands survive app restarts; an `ORBIT_KEY` the user has set wins.
  - `app.New()` reads these, so in dev the app itself serves `/_orbit/*` and `public/` (§7). In prod, `public/` is copied into `dist/client` and `ORBIT_PUBLIC` is unset.
  - `orbit.ListenAndServe` listens on `orbit.Addr()`. Users who start their own `http.Server` should use `orbit.Addr()` to stay dev-compatible; document this.
- **Rendering from custom handlers**:
  - `orbit.RenderComponent(w, r, LikeButton.Render, LikeButton.Props{…})` renders any component as a fragment, with no head injection.
  - Rendering a full page from a custom handler (`site.RenderPage`) is deferred (§12).
  - The user's Go code imports components through the generated declaration packages, e.g. `example.com/blog/orbit_gen/decl/components/likebutton`.

### Deferred island requests
A `server:defer` placeholder (§3.4) makes the browser request `/_orbit/island/<buildID>/<id>?p=<token>` (or POST it, §5). That request is handled in step 1 above:
- **Through the user's middleware**: it's an ordinary request from the browser, so it passes through every middleware wrapped around `site.Middleware` (logging, auth, cookies, `EnsureLocals`), exactly like a page request. In setup A it reaches Orbit through the mux's `/` catch-all. Its `locals` come from its own pass through the middleware; nothing from the page request carries over.
- **Opening the token**:
  - An unknown component ID (one never used with `server:defer`) gets a 404.
  - The token comes from `?p=` (GET, HEAD) or the request body (POST, read through `http.MaxBytesReader` with a 1 MiB limit; larger bodies get a 413, as in Astro).
  - It's opened (§3.4) with the component ID and build ID taken from the URL path. A missing, malformed or tampered token, or one sealed with another key, gets a 400 with an empty body (decided by rule: Astro answers 400). So does JSON that doesn't decode into `Props`.
- **Rendering**: the component renders into a pooled buffer with a fresh pooled `Ctx`. `ctx.Request` and `ctx.URL` are the island request, as in Astro, and the route param storage is empty (`ctx.Param` returns `""` for every name). The page's URL is in the `Referer` header, the pattern Astro documents: `page, err := url.Parse(ctx.Request.Referer())`. Browsers send the full page URL on same-origin fetches under the default `strict-origin-when-cross-origin` policy; a `Referrer-Policy: no-referrer` removes it. Document this.
- **Response**: buffered and written once with `Content-Length`, `Content-Type: text/html; charset=utf-8`, no head injection. Headers:
  - `Cache-Control: private, no-store` by default. A component can replace it through `ctx.Header()`; guidance for public caching is deferred with island caching (§12).
  - `X-Robots-Tag: noindex`, so search engines don't index fragments (decided by rule: Astro sets the same header).
- **Errors**: `return err` or a panic gives a 500, and `orbit.ErrNotFound` gives a 404 with an empty body, not `404.orbit`, which is a full page (decided by rule: simplest). `ctx.Redirect` sends its 3xx, which the loader doesn't follow. In dev, a 500 body holds the error text with its `.orbit` position instead of the overlay page, and the loader logs it. Any non-2xx response keeps the fallback.
- **CSRF**: a CSRF middleware that requires a token on POST blocks islands whose props need POST. Exempt `/_orbit/island/`, or use Go's `http.CrossOriginProtection`, which lets same-origin fetches through. Document this.
- **Limitation**: placeholders inside fragments from `RenderComponent` (e.g. htmx partials) load only if the page they land in already has the islands loader. The MVP doesn't handle this (§12).

### Typed locals
Request-scoped data (the current user, a request ID, …) is a **user-declared struct** in the optional Go package `src/locals` (package `locals`):

```go
// src/locals/locals.go
package locals

type Locals struct {
    RequestID string
    Theme     string
}
```

- **Where it lives**: `src/locals/`, package `locals`, holding `type Locals struct`. *Decided by rule* (simplest clear convention, now that `src/middleware` has no other purpose; log it in `docs/DECISIONS.md`).
- **Detection**: the generator looks for `type Locals struct` in `src/locals` with `go/parser`. If there isn't one, it uses `orbit.NoLocals` (`struct{}`).
- **In every page and component that uses `locals`** (and always in the editor's tolerant mode), the generated `render` starts with `locals := orbit__rt.LocalsOf[orbit__locals.Locals](orbit__ctx)` (the runtime and `src/locals` are imported under internal aliases, §3.2), so `locals` has type `*locals.Locals`. The frontmatter and template then use `locals.User.Name` with full type checking, and gopls completes `locals.` in the editor. `LocalsOf` allocates a zero `Locals` lazily, once per request; components share the page's instance. Inside the body the variable `locals` shadows the package name; hoisted helpers that need the type import the package as usual.
- **Setting locals from net/http middleware** in `main.go`:

  ```go
  func requestInfo(next http.Handler) http.Handler {
      return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
          r, l := orbit.EnsureLocals[locals.Locals](r)
          l.RequestID = newID()
          l.Theme = "light"
          if c, err := r.Cookie("theme"); err == nil {
              l.Theme = c.Value
          }
          next.ServeHTTP(w, r)
      })
  }
  ```

  It must wrap `site.Middleware` (or the mux that leads to `site.Handler()`), so it runs before Orbit. `site.Middleware` picks the pointer up from the request context. Every middleware uses the same `r, l := orbit.EnsureLocals[locals.Locals](r)` line: the first one attaches the value, and later ones get the same pointer back, with `r` unchanged. `WithLocals` remains for attaching a value built elsewhere. Custom handlers read locals with `orbit.LocalsFromRequest[locals.Locals](r)`, which returns nil if no middleware attached any (§4). This makes locals the typed bridge between the user's HTTP stack and pages. Island requests (above) run through the same middleware, so deferred components see locals too.
- **Import rule**: `src/locals` (and anything it imports) must not import `orbit_gen/app`, because `app` → impl packages → `src/locals` would be an import cycle. Keep it a plain types package. The generator checks this and reports it clearly.

## 5c. Typed server→client bridge
**Status: Implemented** (2026-10-26; implementation notes at the end of this section). Accepted 2026-10-26: the user chose the recommended answer to every **(Q)** point: (Q1) per-component modules imported by relative path (`import { data } from "./LikeButton.orbit"`); (Q2) `orbit.JSON` on any attribute, several per element; (Q3) `set:json` typed too (`json(id)`); (Q4) single-quoted values; (Q5) nil slices and maps typed `| null`; (Q6) 64-bit ints are `number` with a docs note; (Q7) types in `orbit_gen/types/`; (Q8) TypeScript editor support inside `<script>` is a separate item, next after this one; (Q9) no `bun check` in `orbit dev`. Written before implementation, like §6.1. Replaces the §12 sketch; deviations from it are listed at the end.

Nothing new at runtime beyond `encoding/json` and a ~180-byte accessor; no new dependency.

### Server side: `orbit.JSON`
- **API** (runtime, §4):
  ```go
  type JSONValue struct{ /* v any */ }          // opaque; the zero value encodes as null
  func JSON(v any) JSONValue                      // v encoded exactly as json.Marshal(v) would
  func (w *Writer) JSONAttr(pos string, v JSONValue)  // generated: an attribute value, single-quoted (Q4)
  func (w *Writer) JSON(pos string, v any)        // set:json, now with the position (bug fix, below)
  ```
  `orbit.JSON` is a plain function returning a value type, so gopls completes and type-checks it like any Go call, and pass 1 (no types) still compiles: it goes through the `Attr`/`Expr` fallbacks, which gain a `JSONValue` case. No generics (§4b: a generic runtime type would be re-instantiated in every generated package).
- **Where it's allowed (Q2)**: as the value of **any attribute** of an HTML element: `data-*` (typed, below), but also `hx-vals={orbit.JSON(m)}` (htmx) or `x-data={orbit.JSON(state)}` (Alpine), which take JSON; in a spread (`orbit.Attrs{"data-x": orbit.JSON(v)}`, untyped); and in content, where it's written HTML-escaped like a string (`<pre>{orbit.JSON(cfg)}</pre>`; decided by rule: simplest, it's what `Expr` does with any value, and rejecting it would need a pass-2-only error). On a component tag it's just a Go value of type `orbit.JSONValue` passed to a prop. A `JSONValue` attribute is always written, `false` and `null` included (unlike `Attr`'s bool rule).
- **Several per element**, any `data-*` name; no fixed `data-orbit` (Q2).
- **Typed write** (§3.3): pass 2 classifies an attribute value whose static type is `orbit.JSONValue` as `WriteAttrJSON`: ` name='` and `'` are merged into the neighbouring `Raw` constants and the value is `orbit__w.JSONAttr("src/components/LikeButton.orbit:9:24", <expr>)`, with the user's expression copied verbatim (directives unchanged). The fallback `Attr(name, JSONValue)` gives the same bytes (golden typed-vs-fallback test), without the position.
- **Escaping** (attribute context): `encoding/json` already escapes `<`, `>`, `&`, U+2028 and U+2029 inside strings (`<`…), and JSON has no `&` outside strings, so the only character left to escape is the quote: `'` → `&#39;` in a single-quoted value (Q4), or `"` → `&quot;` in a double-quoted one. `JSONAttr` doesn't rely on `encoding/json`'s HTML-escaping default: like `Writer.JSON` today, it escapes `<`, `>`, `&` itself (a no-op scan when they're absent). Result: the attribute can't be broken out of, and the browser's attribute decoding gives back the exact JSON text. A `FuzzJSONAttr` test asserts it (decode(escape(json)) == json, no unescaped quote).
- **Encoding path (cost)**: each `Writer` keeps one `json.Encoder` (created with the pooled `Writer`, so 0 allocations per render) writing into a small escaping `io.Writer` over the pooled buffer; the encoder's trailing newline is truncated. No intermediate `[]byte` (saves `json.Marshal`'s result copy). Errors: the buffer is truncated back to the attribute's start before the sticky error is set. `set:json`'s `Writer.JSON` switches to the same path.
- **Errors**:
  - **Generate time** (pass 2, at the `orbit.JSON` argument; walk shared with §3.4's `jsonWalker`, which accepts interfaces here since nothing is decoded): func, chan, complex and `unsafe.Pointer` types, and map keys that aren't strings, integers or `encoding.TextMarshaler`s, anywhere in the value's type (fields tagged `json:"-"` and unexported fields skipped, as `encoding/json` does): `src/components/LikeButton.orbit:9:36: orbit.JSON: Post.Notify has type func(), which encoding/json can't encode`. These always fail at runtime, so failing early is safe. A type implementing `json.Marshaler` or `encoding.TextMarshaler` is accepted whatever its kind.
  - **Render time**: what only the value can show (NaN or ±Inf floats, a pointer cycle, an `any` field holding a func, a `MarshalJSON` error) is a render error carrying the `.orbit` position passed to `JSONAttr`: `src/components/LikeButton.orbit:9:24: orbit.JSON: json: unsupported value: NaN`. A typed write without a pass 2 (LSP tolerant mode, a package with type errors) uses `Attr`, whose error has no position (that output is never served: the build fails, §3.3).
  - **Bug fix in the same change** (found while writing this): `set:json` encode errors don't carry the `.orbit` position today. `Writer.JSON(v)` sets `orbit: set:json: …` and codegen passes no position (`internal/compiler/testdata/codegen/card/pages_index.render.go.golden`), although §2.3 and `styles-and-scripts.md` ("fails with an error at the `.orbit` position of the `set:json`") say it does. `Writer.JSON(pos, v)` fixes it the same way.

### Client side: per-component data modules (Q1)
- **`import { data } from "./LikeButton.orbit"`**: a block script (or any `.ts` file under `src/`) imports a component's `.orbit` file **by relative path** to get **that component's data contract**: `data(el, key)`, typed from the component's own `orbit.JSON` uses, plus `json(id)` for its `set:json` blocks (Q3), and the types `Data` / `JSONBlocks`. It never imports the component itself (still impossible: no framework islands).
- **Keys**: one per `data-*` attribute of an HTML element in the component's template (slot content included, since it's compiled in the parent; spreads excluded) whose value is a **direct call** `orbit.JSON(arg)` (the runtime's function, recognized through the file's import spec, so an aliased or shadowed `orbit` works; no `types.Info.Uses` map needed). The key is the attribute's **dataset name**, the DOM's rule (`data-author-name` → `authorName`), as users already read it with `el.dataset` (decided by rule: web standard; simplest). A `JSONValue` that isn't a direct call (a variable, a helper returning one) gives the key with type `unknown`. Names with characters other than `[a-z0-9-]` after lowercasing aren't keys.
- **Type of a key**: the TS mapping (below) of `arg`'s static type. The same key written several times (two elements, `{if}` branches) gets the union of their types, deduplicated (`posts.Post | posts.Summary`).
- **`Data[K]` is what the component may write**, not proof that `el` carries it: an element without the attribute throws at runtime (`orbit: <like-button> has no data-post attribute`).
- **Which mismatches are caught**, for the options considered:

  | Mismatch | (A) sketch: `data<Post>(el)` from `orbit:types` | **(B) per-component module** (recommended) | (C) registry keyed by custom-element tag | (D) magic `orbit:self` specifier |
  |---|---|---|---|---|
  | script uses a field/type the Go type doesn't have | ✓ (for the `T` the user picked) | ✓ | ✓ | ✓ |
  | script picks the wrong type (`Post` vs `Summary`) | ✗ | ✓ | ✓ | ✓ |
  | key typo, or the attribute removed from the template | ✗ | ✓ | ✓ | ✓ |
  | element read isn't the one carrying the data | ✗ | ✗ (runtime error) | ✓ for custom elements, via `this` | ✗ |
  | plain elements (`<button data-x>`), not custom elements | ✓ | ✓ | ✗ | ✓ |
  | works in `bun check`, the user's TS server for `.ts` files, and a future TS proxy, with standard resolution | ✓ | ✓ (`rootDirs`, below) | ✓ (global declarations) | ✗: TS has no per-importer resolution of a bare specifier; `orbit check` would have to rewrite the import |
  | cost | named types only | + one small `.d.ts` per component with data | + a global tag map, a runtime base class (~300 B), collisions between components using the same tag | as (B), plus extraction rewriting |

  (B) is the only one that's both per-component and standard TypeScript: `./LikeButton.orbit` resolves to `LikeButton.orbit.d.ts`, which `rootDirs` overlays from `orbit_gen/types/src/…` onto `src/…`. Its cost is a self-import by file name (renaming the file makes TS report `Cannot find module './LikeButton.orbit'`, loudly, at the import). It also gives `.ts` files typed access to any component's data (`import { data } from "../components/LikeButton.orbit"` in `src/scripts/like.ts`), which the editor checks today (Q8). (C) could be added later on top of (B) for custom elements.
- **Runtime** (`orbit:client`, embedded in the CLI as TypeScript and served by the esbuild plugin; 180 B minified for `data`, ~350 B with `json`, tree-shaken, deduplicated per page bundle):
  ```ts
  export function data(el: Element, key: string): unknown   // JSON.parse(el.getAttribute("data-" + kebab(key))), throws if absent
  export function json(id: string): unknown                 // JSON.parse(document.getElementById(id).textContent), throws if absent
  ```
  `orbit:client`'s own declarations are generic and untyped (`data<T = unknown>(el, key): T`), for attributes written through spreads or by other code; the docs recommend the component module.
- **esbuild** (§5): an import of any `*.orbit` file from a block script or a `.ts` file resolves to one constant virtual module, `export { data, json } from "orbit:client"` (types are erased; the old error `a script can't import a .orbit file` goes away). esbuild never needs pass 2's results, so its input key (§7.1) doesn't change when only types change. `orbit:types` resolves to an empty module (only `import type` makes sense; esbuild drops type-only imports anyway).

### Type mapping Go → TS (follows `encoding/json`, v1 semantics)
`types.Unalias` first. Named types become **named TS declarations** (needed for recursion, readable in hover); everything else is inlined.

| Go (static type) | TS | Notes |
|---|---|---|
| `bool` | `boolean` | |
| ints, uints, floats (`int64`, `uint64`, `uintptr` too) | `number` | precision past 2⁵³: no warning (Q6); use the `,string` option for such IDs |
| `string`, `orbit.HTML`, `orbit.URL` | `string` | |
| `,string` tag option on a bool/int/uint/float/string field (or a pointer to one) | `string` (`string \| null` for a pointer) | as `encoding/json` |
| `[]byte` (slice of a `uint8` kind that isn't a marshaler) | `string \| null` | base64; `[N]byte` arrays stay `number[]` (v1) |
| `[]T` | `T[] \| null` | nil slice → `null` (Q5) |
| `[N]T` | `T[]` | tuples not used (simplest) |
| `map[K]V` (K: string kind, integer kind, or `TextMarshaler`) | `Record<string, V> \| null` | keys are always JSON strings |
| `*T` | `T \| null` | |
| `struct` | interface (named) or `{ … }` (anonymous) | fields below |
| interfaces (`any`, `error`, others) | `unknown` | |
| `time.Time` | `string` | RFC 3339 (`MarshalJSON`) |
| `time.Duration` | `number` | nanoseconds (an `int64`) |
| `json.Number` | `number` | written as a number literal |
| `json.RawMessage` | `unknown` | |
| other types whose static type implements `json.Marshaler` | `unknown` | (later: an override, Out of scope) |
| other types implementing `encoding.TextMarshaler` (value receiver) | `string` | `netip.Addr`, UUID types, … |
| a marshaler only on `*T`, at a `T` position | `unknown` | whether `encoding/json` calls it depends on addressability; `unknown` is never wrong (simplest) |
| func, chan, complex, `unsafe.Pointer`, bad map keys | **generate-time error** | see Errors |
| generic instance `Page[Post]` | `Page<posts.Post>`, with `interface Page<T>` | type parameters map through |

**Struct fields**, exactly `encoding/json`'s `typeFields`:
- Exported fields only (and embedded structs, exported or not); `json:"-"` skips; `json:"-,"` is a field named `-`; the tag name renames; non-identifier names are quoted (`"my-field": string`).
- `omitempty` → optional (`name?: T`), except on a non-pointer struct type, where `omitempty` has no effect; on a pointer, slice or map it also drops `| null` (a nil value is omitted, so a present one isn't null). `omitzero` → optional, and drops `| null` the same way (nil is the zero value; an empty non-nil slice or map is kept).
- **Embedded structs are promoted** with Go's visibility rules and `encoding/json`'s tie-breaks (shallowest depth wins; at equal depth a tagged field wins; otherwise the conflicting fields are all dropped, silently, as `encoding/json` does). Fields promoted through an embedded **pointer** are optional (a nil embedded pointer omits them). An embedded field with a tag name, or of a non-struct type, is a normal field.

**Names**:
- One namespace per Go package, named after the package (`posts.Post`). Two packages with the same name get the shortest distinguishing suffix of their import paths joined with `_` (`internal_posts`, `legacy_posts`). Types declared in an `.orbit` frontmatter (decl or impl package) go in a namespace named after the file's base name (`LikeButton.link`), disambiguated the same way. Names that are TS keywords or predeclared type names (`default`, `string`, …) get a `_` suffix. Each declaration carries its Go path in a doc comment.
- Deterministic output (sorted by namespace, then name), so `orbit_gen/` stays reproducible (§6, committing `orbit_gen/`).

**Unchecked units** (a package with type errors, unreadable export data; §3.3 Fallback): the component's keys are known from pass 1, but not their types, so its module is written with every key `unknown` (deterministic: generate output depends only on sources). `go build` fails on those units anyway.

### Where the types live and how tools see them (Q7)
- **Files**: `orbit_gen/types/go.d.ts` (`declare module "orbit:types"`), `orbit_gen/types/client.d.ts` (`declare module "orbit:client"`, constant), and `orbit_gen/types/<path>.orbit.d.ts` for each `.orbit` file with at least one key (mirroring `src/`). Written by the same `WriteGenerated` as the Go files (only changed files rewritten; stale ones removed), so they're gitignored with `orbit_gen/`, covered by `orbit doctor`'s freshness check, and committed along with it by projects that commit `orbit_gen/`.
- **Starter `tsconfig.json`** (`orbit new`): adds `"rootDirs": [".", "orbit_gen/types"]` and `"include": ["src/**/*.ts", "orbit_gen/types/*.d.ts"]` (decided by rule for the include: Astro ≥ 5 adds its generated `.astro/types.d.ts` to `include` the same way). `src/env.d.ts` is unchanged.
- **`orbit check`** (§6): the generated `.orbit/check/tsconfig.json` adds `"../../orbit_gen/types"` to its `rootDirs` (it already sets `["../..", "."]`, replacing the user's) and `"../../orbit_gen/types/*.d.ts"` to `include`, so the check works on projects whose `tsconfig.json` wasn't migrated. Verified with `bun check` (spike): `./LikeButton.orbit` from `.orbit/check/src/components/LikeButton.orbit.0.ts` resolves through both `rootDirs` entries.
- **Editor**: the user's TS server (VS Code's built-in one) sees the types in `.ts` files under `src/` through the user's `tsconfig.json`; without `orbit_gen/types/` (fresh clone before `orbit generate`) it reports `Cannot find module './X.orbit'`, like Go reports a missing `orbit_gen/` package.
- **Existing projects (migration note)**: add the two `tsconfig.json` entries for editor support; `orbit check` needs nothing. `orbit doctor` gets a ⚠ check: the project uses `orbit.JSON` or `set:json` and `tsconfig.json` lacks the `orbit_gen/types` `rootDirs` entry (fix: the two lines).

### When it's regenerated (dev-loop cost)
- The types are a by-product of pass 2 (§3.3), so they're written by `orbit generate`, `build`, `dev` and `check`, on exactly the edits that already run pass 2: a frontmatter/template edit re-checks its impl package; a `Props` edit its importers; a user `.go`/`go.mod`/`orbit.json` edit everything. Per-unit results (keys, types, the named types reached) are kept in the resident checker, and `go.d.ts` is re-emitted from their union (microseconds; below).
- **No extra Go build and no extra esbuild**: `.d.ts` files aren't Go (cmd/go ignores them), `orbit_gen/` isn't watched (§7), and esbuild's input doesn't depend on types. An edit that only changes types costs a few file writes.
- **`orbit dev` doesn't run `bun check`** (Q9).
- **The LSP neither writes nor serves the types**: it never writes `orbit_gen/` (§9; the types are no exception, since `orbit dev`/`generate` keep them current), and it has no TypeScript features to serve them to (Q8). A future TS proxy could build them in memory from the typed check it already runs (§9 Startup step 2).

### Errors and positions
- TS errors in block scripts map back through `internal/check`'s existing per-script offset table: nothing is injected into the extracted script, so positions need no new mapping (example above).
- Errors inside generated `.d.ts` files would be Orbit bugs; they're printed with their `orbit_gen/types/…` path, prefixed `internal:` (as the LSP does, §9).
- The generate-time and render-time Go errors are at `.orbit` positions (Server side, Errors). They show in `orbit build`, `orbit dev`'s overlay and `orbit check`'s Go half, like `server:defer`'s JSON check; the LSP doesn't show pass-2 errors today, and this doesn't change that.

### (Q) points
1. **(Q1) How a script's types connect to the data**: (B) per-component module imported by relative path, `data(el, key)` keyed by dataset name, typed from that component's `orbit.JSON` uses (recommended; table above), vs. (A) the sketch's hand-picked `data<T>(el)`, (C) a global registry keyed by custom-element tag, (D) a magic `orbit:self` specifier.
2. **(Q2) Server API**: `orbit.JSON(v)` on any attribute (typed for `data-*` on HTML elements), several per element, also allowed in content and spreads (recommended), vs. a fixed `data-orbit` attribute (one per element, the sketch) or a directive (`data-post:json={v}`, which gopls can't see as Go).
3. **(Q3) `set:json` gets types too**: `json(id)` in the same module, keyed by the script's static `id` (a dynamic `id` gives no key) (recommended: same machinery, a few lines), vs. `data-*` only.
4. **(Q4) Quoting**: single-quoted values with `'` → `&#39;` (recommended: measured −43% raw bytes, −16% gzip on a 50-post list; readable in view-source) vs. double quotes with `"` → `&quot;` (every other Orbit attribute, and Astro's `<astro-island props="…">`). Browsers decode both to the same JSON.
5. **(Q5) Nil slices and maps**: honest `T[] | null` / `Record<…> | null`, with `omitempty`/`omitzero` documented as the way to get a non-null type (recommended: that's what `encoding/json` sends; strict TS then catches the `null` case, the point of the bridge), vs. assume non-nil (unsound), vs. Orbit encoding nil as `[]`/`{}` (json v2's default, but then `set:json`, `server:defer` and `json.Marshal` would disagree).
6. **(Q6) 64-bit integers**: plain `number` and a docs note (recommended: `int` is 64-bit, so a warning would fire on almost every struct), vs. a generate-time warning (the sketch), vs. `bigint` (wrong: `JSON.parse` returns numbers).
7. **(Q7) Location**: `orbit_gen/types/` (recommended: one generated directory with one lifecycle; `.orbit/` stays a deletable cache, §1; doctor freshness and the commit option cover it) vs. `.orbit/types/` (the sketch; Astro's `.astro/types.d.ts` analogue).
8. **(Q8) Editor support**: today the benefit lands in **`orbit check`** (block scripts and `.ts` files) and in the **editor for `.ts` files only**: TS inside `.orbit` `<script>` has no language features (§9). Docs show moving logic into `src/…/*.ts` (or `<script src="./like-button.ts">`) for editor checking. Recommended: keep TS proxying a **separate item** with its own spec (it needs `typescript` and a Node runtime, or a TS server that Bun doesn't ship; virtual documents per block script placed like `orbit check`'s extraction), next in line after this one; (B) needs nothing extra from it. Alternative: make it part of this item (much larger; new editor-time requirement).
9. **(Q9) `orbit dev` and `bun check`**: not in this item (recommended: the dev loop stays ~0.2 s; `bun check` is ~15 ms on a small project but grows with scripts, and its errors would need an overlay design) vs. a background `bun check` after each rebuild, printed to the terminal only (non-blocking; measure at 200 files first).

Decided by rule (to log in `docs/DECISIONS.md`): `orbit.JSON` also allowed in content and spreads (simplest); keys are dataset names (web standard); `tsconfig.json` `include` entry (Astro); generate-time errors only for always-failing types (Go stdlib: `json.Marshal` fails on the type); a pointer-receiver-only marshaler at a value position maps to `unknown` (simplest that's never wrong); `[N]T` → `T[]` (simplest).

### Cost (measured in a throwaway spike, `scratchpad/bridge-spike/`; Ryzen 7 9700X, 16 threads, Go 1.27.3, load average 0.2–0.8)
- **Encoding** (`GOMAXPROCS=1`, `b.Loop`, a 7-field `Post` with a `time.Time`, a slice and a pointer, 209 B of JSON):
  - reused per-Writer `json.Encoder` into the buffer with attribute escaping: **740 ns, 2 allocs / 224 B**; `json.Marshal` + escape (today's `Writer.JSON` shape): 795 ns, 3 allocs / 448 B; the same with a pointer argument: 580 ns, **0 allocs**.
  - Of the 2 allocations, 1 is boxing the struct into `any` (at the `orbit.JSON` call) and 1 is internal to `encoding/json`: **Go 1.27's `encoding/json` runs on the json/v2 engine by default** (`GOEXPERIMENT=jsonv2` is on in `internal/buildcfg`), which copies a non-addressable value with `reflect.New` before encoding. Orbit's own code adds 0.
  - a 2-field struct: 185 ns, 2 allocs, vs. 10 ns and 0 allocs for the same two values as plain typed `data-*` attributes (§3.3). The docs keep recommending plain `data-*` for scalars and `orbit.JSON` for structured data.
- **AllocsPerRun rule (§4b)**: `orbit.JSON` is user data, like `Expr` and `server:defer` props, so it's outside the zero-allocation "typical page"; §4b's "what may still allocate" list gains it. A test asserts that `JSONAttr` adds no allocation beyond `encoding/json`'s own (0 for a pointer, equal to `json.NewEncoder(io.Discard).Encode` for a value).
- **Size**: the 209-byte value is 389 bytes double-quoted with `&quot;` (+86%) and stays 209 single-quoted (no `'` in it). 50 such elements: 19,970 vs. 11,470 B raw, 746 vs. 626 B gzipped (the repetition flatters gzip).
- **Generate**: a go/types walk plus TS emission for `Page[Post]` (4 named types, recursion, generics) takes **1.9 µs and 53 allocs per use**, without the method-set checks for marshalers (estimate ×2–3 with them, cached per named type). At 200 uses, well under 1 ms of a ~70 ms `orbit generate` (§12 Dev-loop speed work); writing the `.d.ts` files is a few more file writes. Measured with `bench/devloop` when implemented; no change to the template-edit loop is expected (no Go or esbuild work added).
- **Client**: `data` is 180 B minified (`json` adds ~170 B), only in bundles that use it.
- **`orbit check`**: `bun check` on the spike's two files: 15 ms; one more `.d.ts` per component with data.

### Implementation notes
- **Code**: runtime `json.go` (`JSON`, `JSONValue`, `JSONAttr`, `Writer.JSON(pos, v)`, a per-Writer `json.Encoder` over an escaping sink); compiler `codegen_json.go` (`Output.JSONSites`, direct-call detection by the file's runtime import names, dataset names), `typed_bridge.go` (keys and types per unit, `TypedUnit.Types`, generate-time errors), `tstypes.go`/`tstypes_emit.go` (mapper, `typeFields` port, naming, `EmitTypes`); `project.GenFiles` writes `orbit_gen/types/`; `internal/assets` `client.go`; `internal/check` tsconfig; `internal/doctor` `tsconfig` check; `orbit dev` keeps its early build when only `.d.ts` files were written.
- **Positions**: `JSONAttr`'s is the attribute value's `{`; `set:json`'s is the `set:json` attribute.
- **Measured** (Ryzen 7 9700X, `GOMAXPROCS=1`): `JSONAttr` typical post 510 ns / 1 alloc by value, 365 ns / 0 allocs by pointer; 2-field struct 130 ns / 1 alloc, 95 ns / 0 by pointer; plain typed attributes 13 ns. `orbit:client` 368 B minified. Mapper: 5.3 µs / 68 allocs cold for `Page[Post]`, 7 ns cached.
- **Deviations and additions** (small, logged in `docs/DECISIONS.md` "Typed bridge"): `JSONValue` implements `json.Marshaler`, and `set:json` unwraps a `JSONValue`; `set:json` values get the same generate-time unsupported-type check as `orbit.JSON` arguments; a component without keys has no module (importing it is `TS2307`); named non-struct types (`time.Duration`) are `type X = …` declarations rather than inlined; tag names follow Go 1.27's json/v2-engine parsing on malformed tags; fallback errors without a position read `orbit: orbit.JSON: …`; the mapper goldens are in `testdata/tstypes/` and the pipeline goldens in `testdata/types/`.

### Deviations from the §12 sketch, and why
- `data<T>(el)` on a fixed `data-orbit` → a per-component `data(el, key)` over any `data-*` attribute: the sketch couldn't catch a wrong `T` or a missing attribute (Q1, Q2).
- `.orbit/types/orbit-types.d.ts` → `orbit_gen/types/` with one module per component plus `go.d.ts` (Q7).
- The int64 warning is dropped (Q6); slices and maps are `| null` (the sketch didn't say; Q5); embedded structs follow `typeFields`' tie-breaks (not a plain flatten); `TextMarshaler` → `string`, and pointer-receiver marshalers → `unknown`.
- `set:json` gets types too (Q3), and its missing error position is fixed.

|---|---|

**Exit codes** (every command, following Go's `flag` package): `0` success (warnings don't change it), `1` failure (compile error, failed check, a ✗ in `doctor`), `2` usage error (unknown command or flag, missing argument; usage printed to stderr). `orbit preview` exits with the server's own code.

**Flags**: Go's `flag` syntax (`--port 3000`, `--port=3000`, `-port 3000`). `orbit build` has no build flags of its own besides `--embed`: Go build flags come from `GOFLAGS` (e.g. `GOFLAGS=-tags=prod`; with `--embed`, Orbit adds `orbit_embed`), and `GOOS`/`GOARCH`/`CGO_ENABLED` pass through to `go build` for cross-compiling.

**Positions in CLI output** are printed relative to the project root as `src/…:L:C`; Go's own `./src/…` prefix is normalized away, while plain `go build`/`go vet` still print `./src/…`.

**Version pinning**: when the project's `go.mod` has the `tool github.com/orbit-z/orbit/cmd/orbit` directive, a globally installed `orbit` hands the command to the pinned CLI, so the generator always matches the runtime version in `go.mod` (implemented, milestone 11): `go tool -n orbit` builds the pinned CLI (or finds it in the build cache) and prints its path, and the global CLI execs that binary directly (`syscall.Exec` on Unix; a child process on Windows), with `ORBIT_REEXEC=1` set to prevent loops and the toolchain's `bin` first on `PATH`, as `go tool` does. Going around the `go` command keeps Ctrl-C clean: `go tool orbit dev` exits 1 on Ctrl-C (the tool gets SIGINT twice, from the terminal and from `go`), the hand-over exits 0. It costs about 35 ms per command (`go tool orbit` itself adds about 65 ms). A global CLI is one whose main module is `github.com/orbit-z/orbit`; a `go tool` build never hands over. `orbit new` and `orbit doctor` are exempt (doctor must run when the pinned CLI doesn't build, and it reports the mismatch). Without the directive, a global CLI whose version differs from the `github.com/orbit-z/orbit` requirement in `go.mod` stops with a version-mismatch error pointing to `orbit doctor`; the check is skipped when `go.mod` has a `replace` of the module with a local directory, or doesn't require it. The tool directive adds the CLI's dependencies (esbuild, fsnotify, tdewolff) to the user's module graph; the runtime package itself stays stdlib-only.

**Fresh clones and CI**: `orbit_gen/` is gitignored by default, so a clone needs one step before anything else. Document it in `project-structure.md`:
```sh
go tool orbit generate     # creates orbit_gen/
go vet ./...
go tool orbit build
```
Alternative: commit `orbit_gen/` (replace the `orbit_gen/` line in `.gitignore` with `orbit_gen/static/`, which `--embed` writes and stays ignored). Then plain `go build ./...` works on a fresh clone; generation is deterministic, so CI can check `go tool orbit generate && git diff --exit-code orbit_gen`.

**`orbit build` pipeline**
1. Load `orbit.json` and read the module path from `go.mod`.
2. Scan `src/**/*.orbit` and parse them all, reporting every error rather than only the first. Build the import graph and check for cycles.
3. Compute scope IDs, rewrite CSS, and run esbuild into `dist/client/_orbit/`, producing the manifest.
4. Generate `orbit_gen/` (two passes with typed writes, §3.3; no type cache).
5. Copy `public/` into `dist/client/`. A conflict with `_orbit/` is an error.
6. `go build -o dist/server <server entry>` (the user's `main`, or the generated default). Errors already point at `.orbit` lines via line directives; the CLI strips generated positions and rewrites generated type names (§3.3, error output). At runtime, `app.New()` finds the `client/` directory next to the binary (in the binary's own directory, not the working directory) unless `ORBIT_STATIC` or `WithStaticDir` overrides it.
   - **Island key and build ID**: each `orbit build` generates a random island key and a random build ID and passes both with `-ldflags=-X github.com/orbit-z/orbit.buildKey=… -X github.com/orbit-z/orbit.buildID=…`, so nothing random is written to `orbit_gen/` (§4). `$ORBIT_KEY` at runtime overrides the embedded key.
   - **`--embed`**: before the server build, copy `dist/client` to `orbit_gen/static/client/` (go:embed can't reach outside the package directory) and generate `orbit_gen/static/static.go` with `//go:embed all:client` behind the `orbit_embed` build tag. The server is built with `-tags orbit_embed`, and `app.New()` then uses `WithStaticFS(static.FS)` automatically. The result is one self-contained `dist/server` binary; `dist/client` is still written for CDN uploads. The env var `ORBIT_STATIC` overrides the embedded files if set.

### 6.1 `orbit fmt` (formatter)
**Status: Implemented** (2026-10-26; `internal/format`, `cmd/orbit/fmt.go`, LSP `textDocument/formatting`; user docs `docs/reference/cli.md#orbit-fmt`, `docs/editor-setup.md#formatting`). Accepted 2026-10-26. The user chose the recommended answer to every **(Q)** point it was asked: gofmt tabs in the frontmatter; `orbit fmt` like `go fmt`/`bun fmt` (in place over `src/`, `-l`/`-d` read-only, exit 1 when unformatted); the first release covers frontmatter, expressions/control headers and script/style; Bun formatting on whenever Bun ≥ 1.4.4 is found, no switch. Settled by the coordinator with the recommendations (triage rules): `.md` files are never touched (Astro leaves Markdown to Prettier); the starter, `examples/blog`, `docs/site` and the docs' `orbit` blocks are reformatted when fmt ships and kept fmt-clean by tests; no `orbit check --fmt`; imports keep gofmt's sort. Also with the implementation: `compiler.SplitFrontmatter` skips a leading UTF-8 BOM (Go stdlib behavior; today a BOM hides the frontmatter). Small details are logged in `docs/DECISIONS.md` ("Formatter").

**Implementation notes and deviations** (the spec below is kept as designed; where the implementation differs, this list wins):
- **Syntax errors**: `File.SyntaxErrors()` returns the errors raised before `validate` (split, lexer, parser). Go code that `go/format` rejects refuses the file too; so does a `//` comment ending a control header (`{if x // c` + newline + `}`), with its own message (`a // comment can't end a {if} header; use /* … */`), since `if x // c {` can't compile. An expression ending in a `//` comment is valid (codegen puts the call's `)` on the next line), so the formatter keeps a line break before its `}`.
- **Body chunks** are formatted inside `func _() {…}` with every non-raw-string line indented one tab, then dedented, instead of `format.Source(chunk)` on the partial source: go/format's partial path rejects a leading IIFE (`func() {…}()` is parsed as a malformed declaration), and go/printer formats a comment at the left margin of a function body differently from an indented one (`//0` → `// 0`), which broke idempotence. Raw string lines are never touched.
- **Chunk joining**: a chunk that ends with a comment on its own line(s) after its last statement gets a blank line before the next chunk even when the source had none; otherwise the comment would become the next statement's doc comment on the second run and move chunks (not idempotent).
- **Indentation from the output**: an expression's continuation lines and a block's closing tag take their base indentation from the line *as formatted so far* (regions are formatted in source order), not from the source, so a region that starts on the last line of a reformatted one formats the same on the second run. Scripts and styles are therefore formatted in the same ordered pass (one `bun fmt` at a time per file; files in parallel, at most GOMAXPROCS `bun` processes overall).
- **Safety check additions**: Go regions must also keep their number of comments (gofmt drops an empty `//` right above a block statement); a control header may differ by parentheses only (gofmt drops `if (x)`'s); CSS is compared after esbuild's `MinifySyntax` too (CSS printing keeps `.5rem` vs `0.5rem` as written); a formatted block containing `</script` (`</style`) is left as written. On the corpus (starter, `examples/blog`, `docs/site`, `internal/compiler/testdata`, the docs' `orbit` blocks) no region is left as written (the parentheses rule came from `internal/compiler/testdata/parse/control.orbit`'s `{if(x)}`, the only warning before it).
- **BOM**: `SplitFrontmatter` skips a leading BOM, so a BOM file's frontmatter is found and formatted; the BOM is kept by `orbit fmt` and no longer rendered.
- **Bun notice**: printed only when some file has a script or style Bun would format (`format.Result.Skipped`), not on every run without Bun.
- **Directory walks** also skip the project's own `dist/` (build output); explicit paths are followed even if they're symlinks, entries met in a walk aren't.
- **LSP**: formats the documents the server follows (`.orbit` files under the workspace's `src/`, the open buffer); other documents and Markdown get `null`.
- **Rendered-output test** (`internal/format/render_test.go`): instead of serving pages, `examples/blog` and `docs/site` are copied, "unformatted" (spaces in the frontmatter, padded braces), and generated in memory (`Generator.Plan`) before and after formatting under `compressHTML` `"html"`, `"jsx"` and `false`; the generated Go must be equal token for token (comments, i.e. line directives, and the `.orbit` positions passed to `ErrorAt` excepted). The generated code holds every static byte and the code that writes the rest, so this covers every request, not a sample. It runs without Bun; script/style changes are covered by the esbuild safety check.
- **Docs blocks**: a ```` ```orbit ```` block whose info string has the word `unformatted` (the "Before" examples of `cli.md`) is exempt; every other block that parses on its own must be fmt-clean. Asserted by `internal/format`'s `TestCorpus` (with the starter, `examples/blog` and `docs/site`), not in `internal/docstest`; `go test ./internal/format -run TestRewriteDocs -rewrite-docs` reformats the blocks.
- **Benchmark** (`orbit fmt -l` on `bench/devloop`'s 200-file project, 40 of them with a `<script>` and a `<style>`; 16 cores, Bun 1.4.4): 0.02 s wall (0.09 s CPU) without Bun, 0.04 s wall (0.35 s CPU) with Bun; on 4 cores (`GOMAXPROCS=4 taskset -c 0-3`) 0.02 s without Bun, 0.07 s with Bun.

**Invariant: formatting never changes rendered output.** `orbit fmt` rewrites only Go code (frontmatter, `{…}`, control headers) and the content of `<script>`/`<style>` blocks; template text, tags, attributes and the whitespace between them are copied byte for byte, so the result renders the same bytes in every `compressHTML` mode (§3.3 Whitespace: whitespace inside `{…}` and inside `<script>`/`<style>` is never template text). Script/style content changes bytes but not meaning (verified, below). HTML reindentation is a later phase with its own design (below).

**First release (Q: one release or phase 1 alone)**: the three regions together, since they share the parse, the region rewriter and the tests:
1. Frontmatter with `go/format`.
2. Template expressions and control headers with `go/format`.
3. `<script>`/`<style>` content with `bun fmt` (optional, needs Bun ≥ 1.4.4).

Later: HTML reindent between block-level elements only (never inline text, `<pre>`, `<textarea>`, raw-text elements; under `compressHTML: false` even that changes output, so it would be off or opt-in there; design it then). `gofmt -s` simplifications aren't applied (`go fmt` doesn't either).

**CLI** (`cmd/orbit/fmt.go`; formatting in a new `internal/format`, used by the CLI and the LSP; no new dependency: `go/format`, `go/scanner`, the existing esbuild API, Bun as an optional external program).
- `orbit fmt [-l] [-d] [-w] [paths…]` and `orbit fmt [-l|-d] --stdin-filepath=PATH`. Version hand-over as for every command (§6), so a project formats with its pinned CLI.
- **Paths (Q)**: none → every `.orbit` file under the project's `src/` (project = nearest `go.mod`; with none, `orbit fmt: no go.mod found; pass the files or directories to format`, exit 1). A directory → its `.orbit` regular files, recursively, skipping directories named `.*`, `node_modules` and `orbit_gen`; symlinks aren't followed (gofmt). A file → formatted whatever its location, without a project (formatting is per file); a file named explicitly that doesn't end in `.orbit` is an error (`orbit fmt: x.md: orbit fmt formats .orbit files; format Markdown with bun fmt`).
- **Modes (Q)**: no flag writes changed files in place (atomically: temp file in the same directory + rename, keeping the mode), silent on success (Orbit's commands are silent; `go fmt`, `bun fmt` and `prettier --write` also write by default). `-l` lists differing files (project-relative, `/` separators, sorted), `-d` prints `gofmt -d`-style unified diffs (`diff -u` headers `--- PATH.orig` / `+++ PATH`, a small line diff in `internal/format`; the stdlib's `internal/diff` isn't importable); neither writes unless `-w` is added. `-w` alone = no flag. `--stdin-filepath` reads stdin, writes the result to stdout (or the path/diff with `-l`/`-d`); `-w` or paths with it are usage errors.
- **Exit codes (Q)**: 0 success; 1 if any file failed (syntax error, Bun error or timeout, I/O), or with `-l`/`-d` and no `-w`, any file differs (so `orbit fmt -l` is a CI check, like `bun fmt -l` and `prettier -l`; gofmt exits 0 there); 2 usage. Files are processed in parallel (GOMAXPROCS), output sorted by path; one file's failure doesn't stop the others.

**Pipeline per file** (pure function `format.Source(path, src, opts) (out []byte, diags []compiler.Diagnostic)` plus `format.Regions` for the LSP):
1. `compiler.Parse(src, Strict)`. **Refuse the file** (unchanged output, exit 1, every error printed as `file:line:col: message`) on any *syntax* error: the frontmatter split and the lexer/parser errors (unclosed tags/blocks, `{` without `}`, mismatched closers, a `//` comment ending template Go code). The `validate` pass and `Analyze`'s checks (directive misuse, unknown props, unused imports, reserved names) are semantic and don't block formatting, as gofmt formats code that doesn't type-check. Implementation: `Parse` keeps the diagnostics raised before `validate` distinguishable (a `Syntax` flag on `Diagnostic`, or `ParseSyntax`).
2. Compute the **regions** (byte spans of the original file) and their replacement text: frontmatter code chunks, the delimiter lines, each `{…}` Go region, each formatted script/style content. Regions never overlap and are applied back to front. Any region whose Go code doesn't parse (go/format error) refuses the whole file, with the error mapped to the `.orbit` position (go/scanner positions in the wrapper → offset into the region → file).
3. **Safety net** (cheap, always on): the output is re-parsed and must give the same template tree as the input (node kinds, tag names, attribute names/kinds/static values, `Text` values byte-identical); Go regions must have the same go/scanner token stream (comments excluded; kinds, and literals except number literals compared by value; auto and explicit semicolons equal; an import block compared as a sorted set of specs); script/style blocks must give the same esbuild `Transform` output with `MinifyWhitespace` and `LegalComments: none` (loader `ts`/`js`/`css`) before and after. On a mismatch the region keeps its original text and a warning is printed (`file:line:col: warning: formatting this <script> would change its code; left as is (please report this)`); warnings don't change the exit code. This catches a mangled multi-line template literal (the reindent below) and Orbit bugs, not Bun's or gofmt's own choices.
4. If the output equals the input, the file is "formatted" (`-l` doesn't list it, no write).

**Frontmatter rules.**
- The delimiter lines become exactly `---` (trailing spaces and tabs dropped; delimiters may carry them, §2.2).
- The code is split with the same scanner as `Analyze` (`anScan`/`anSplit`/`anClassify`, §2.2) into depth-0 statements, each hoisted (`import`, `type`, `const`, named `func`/method) or body. Consecutive statements of the same kind form a **chunk**; the formatter never reorders statements or moves them between chunks (hoisting is semantic; the source order is what the user reads).
- **Comments between chunks**: a line comment on the last line of a statement belongs to it. The comment lines directly above a statement (no blank line between, go/parser's doc rule, `anDoc`) belong to its chunk; any other comment run belongs to the chunk before it (to the first chunk if there's none).
- **Hoisted chunk**: formatted as a file, `format.Source("package p\n\n" + chunk)`, then the `package p\n\n` prefix is removed. A full file (not a partial one) is what makes `go/format` sort imports (`ast.SortImports`: by path within blank-line-separated groups, duplicates removed); `.orbit` imports sort with the rest (their `./`/`../` paths sort first in a group).
- **Body chunk**: `format.Source(chunk)` on the chunk alone, which `go/format` parses as a partial source (a statement list, wrapped internally in `func _() { … }`) and prints at the indentation of its first code line, which is column 0 for a depth-0 chunk. Printing at depth 0 directly (not dedenting the output of a wrapped func) keeps the continuation lines of a multi-line raw string untouched. `return err`, labels and `goto` parse fine (no type check). A body chunk that `go/format` reads as a declaration list (`var x = 1`) prints the same.
- **Joining**: chunks are joined in order; between two chunks there's one blank line if the source had at least one there, otherwise none; inside a chunk, gofmt's own rules (it keeps at most one blank line, and separates an import block from the next declaration). Leading and trailing blank lines are dropped; the code ends with one newline before the closing `---`. An empty frontmatter (`---\n---`) stays empty; a comment-only frontmatter keeps its comments (trailing whitespace trimmed).
- **Indentation**: always tabs, gofmt's (Q: the repo's docs and examples use 4 spaces today; they'd be reformatted when `orbit fmt` lands). `go/format` offers no spaces mode, and gofmt's alignment is defined with tabs.
- **Line directives and source maps** are unaffected: codegen reads the formatted file like any other (§3.3; generated code itself is never formatted).

**Template expressions** (`Expr.Code`, `Attr.Code` of `AttrExpr`/`AttrShorthand`/`AttrSpread`, in content, attributes and RCDATA):
- Formatted as a standalone value: `format.Source("package p\n\nvar _ = " + code + "\n")`; the result is the text from the expression's first token to the end of its last token or trailing comment (located by re-parsing the formatted wrapper, not by string offsets). So `{a+b}` → `{a + b}` (gofmt's top-level spacing), `{f( x )}` → `{f(x)}`. A spread formats its operand (`{...attrs}`); a shorthand is an identifier, only its padding changes.
- **Braces hug the code**: `{ title }` → `{title}`, `{ }` → `{}` (Prettier's JSX printer; the code is trimmed by the parser anyway, §2.3). Attribute forms are never changed (no shorthand introduced or expanded, quotes and `a=bare` kept).
- **Multi-line expressions** keep gofmt's line breaks (it preserves the user's breaks in calls, composite literals and binary expressions). Continuation lines are re-indented: base = the leading whitespace of the template line holding the `{`; each continuation line gets base + one *template indent unit* per leading tab in gofmt's output. Lines that start inside a multi-line raw string (found with go/scanner on the formatted text) are copied as is. The template indent unit is detected per file: the leading whitespace of the template's indented lines (outside raw-text elements and `<pre>`): a tab if the first such line starts with a tab, otherwise the smallest number of leading spaces; two spaces when nothing is indented (Orbit's starter and Prettier's default).
- A `/* */` comment inside an expression is kept (it's in the wrapper file). A `//` comment can't occur (a syntax error, refused, §2.3 integration rule).

**Control headers**: the code is formatted inside a statement, `format.Source("package p\n\nfunc _() {\n\tif " + cond + " {\n\t}\n}\n")` (`for` likewise), and taken back from the formatted text between the keyword and the body's `{`, located by re-parsing (`IfStmt.If`+2 … `Body.Lbrace`, `ForStmt`/`RangeStmt` likewise); a multi-line header is re-indented like a multi-line expression. Tags are respelled `{if c}`, `{else if c}`, `{else}`, `{/if}`, `{for clause}`, `{/for}` (single spaces, no padding; the lexer already accepts `{ if c }`, `{else  if c}`, `{ /if }`). Examples: `{for i:=0;i<n;i++}` → `{for i := 0; i < n; i++}`, `{if n,ok:=m[k];ok}` → `{if n, ok := m[k]; ok}`. A condition needs parentheses around a composite literal in both the formatter's wrapper and codegen's `if … {`, so anything that compiles formats.

**Scripts and styles** (`Script.Content`, `Style.Content`):
- **Which**: processed scripts as `.ts`; any other `<script>` with no `type` or a JavaScript MIME type (`module`, `text/javascript`, `application/javascript`, the HTML spec's list) as `.js` (it isn't compiled, so it must be JS); every other `type` is left as is (`application/json`, `application/ld+json`, `importmap`, templates; `set:json` scripts have no content). Every `<style>` as `.css`. Empty or whitespace-only content is left as is. Rule: simplest.
- **Invocation**: `bun fmt --no-script --stdin-filepath=<path>.<n>.<ext>` with stdin = the dedented content, run in the project root (the file's directory outside a project), environment inherited. `<path>` is the project-relative `.orbit` path and `<n>` the block's index among the file's scripts (or styles), the naming `orbit check` uses (`src/components/Card.orbit.0.ts`), so Bun finds the user's `.prettierrc`/`bunfig.toml [fmt]`/`.editorconfig` as for a sibling `.ts` file, and a `package.json` `fmt` script can't take over (`--no-script`). One trailing newline is removed from the output. Exit status ≠ 0 → the file is refused, with Bun's first `error:` line and its `at <name>:L:C` mapped back to the `.orbit` position (line + block start line, column + dedent): `src/components/Card.orbit:31:9: <script>: Variable declaration expected.`
- **Indentation** (block content isn't template text, but a textual re-indent could change a multi-line template literal or CSS string): the content's common leading whitespace *k* (over non-blank lines) is removed before Bun and added back after, so the block keeps its indentation and literal lines shift by −k then +k (unchanged). Whitespace-only lines are neither dedented nor re-indented. Content that starts on the tag's line (`<style> .a { color: red } </style>`) moves to its own lines with k = the tag line's indentation + one template indent unit; on one line it can't hold a multi-line literal, so that's safe. The closing tag goes on its own line at the tag line's indentation. The print width isn't reduced by k (simplest; Prettier's embed would reduce it). The esbuild safety net (above) catches the remaining cases (a multi-line literal starting on the tag's line).
- **Bun detection**: `bun --version` once per run (shared with `internal/check`); missing or < 1.4.4 → scripts and styles are skipped with one stderr notice naming the install or upgrade command (as `orbit check`), exit code unchanged (Q: on by default).
- **Timeouts and parallelism**: one `bun fmt` process per block (measured: ~1.3 ms per invocation with Bun 1.4.4 on a small block, so stdin per block beats batching through temp files), at most GOMAXPROCS at a time across files, 10 s timeout each (the file is refused with `bun fmt timed out after 10s`).
- **Caching**: none (gofmt has none; a 200-file project with one script each is ~0.3 s of Bun CPU, spread over cores). Revisit with numbers.

**Line endings, BOM, final newline**:
- **CRLF**: a file whose first line break is `\r\n` is CRLF. Regions are formatted on LF text and written back with `\r\n` line breaks; everything else keeps its bytes (template text is rendered, so normalizing it would change output under `compressHTML: false`). Mixed files follow their first line break.
- **BOM**: kept. `SplitFrontmatter` skips it (as Go's scanner does), so the frontmatter after it is found and formatted, and it isn't rendered.
- **Final newline**: the template's end is never changed (adding or removing a newline is rendered under `compressHTML: false`). A file that ends with the closing `---` and no line break gets one (the template stays empty, since the delimiter's line break isn't template text).

**Markdown (Q)**: `orbit fmt` doesn't touch `.md` files (Astro leaves Markdown to Prettier; `bun fmt` formats Markdown, YAML frontmatter included). Directory walks skip them; a `.md` named explicitly is an error pointing to `bun fmt`.

**LSP** (`internal/lsp`, `textDocument/formatting`): advertised as `documentFormattingProvider: true`. Formats the open document's buffer with `format.Regions` and returns one `TextEdit` per changed region (minimal edits, so cursors and folds outside them stay), ranges in UTF-16 via the document's line index. Full document only: no `rangeFormatting` and no `onTypeFormatting` (gopls has neither). `FormattingOptions` (`tabSize`, `insertSpaces`) are ignored (gopls ignores them; the frontmatter is gofmt's, the template's unit is detected, Bun reads its own config). A syntax error returns no edits (`[]`), since the diagnostic is already shown; a Bun error or timeout drops only that block's edit. Without Bun, script/style regions are skipped and a `window/showMessage` (Info) says so once per session. Requests don't wait for gopls or the readiness barrier: formatting is syntax-only. `.md` documents get `null`. VS Code: `package.json` sets `configurationDefaults` `"[orbit]": {"editor.defaultFormatter": "orbit-z.orbit"}`; format-on-save stays the user's choice.

**`orbit check` (Q)**: doesn't check formatting; CI runs `orbit fmt -l` as its own step (it needs no `orbit_gen/`).

**Tests** (`internal/format`, `cmd/orbit`, `internal/lsp`):
- Golden files `internal/format/testdata/*.orbit` → `*.golden` (`-update`), one case per rule above: chunk interleaving and comments, imports with `.orbit` paths, raw strings in a body and in an expression, multi-line expressions with tab and space templates, every control header form, braces padding, CRLF, BOM, missing final newline, empty and comment-only frontmatter, refused files (each syntax error kind, with positions), and script/style cases (skipped without Bun; Bun output is pinned to ≥ 1.4.4 and the goldens are regenerated deliberately).
- **Idempotence**: fmt∘fmt = fmt on every golden and the corpus (`examples/blog`, `docs/site`, `internal/compiler/testdata`, the starter, every ```` ```orbit ```` block in `docs/`).
- **Equivalence**: for the corpus, the template trees are equal (as the safety net), and the frontmatter and every Go region are equal as go/ast trees with positions and comments ignored (imports compared as sets).
- **Rendered-output equality**: the corpus pages are generated and rendered before and after formatting, under `compressHTML` `"html"`, `"jsx"` and `false`, with byte-identical HTML (processed script/style bundles compared after esbuild minification).
- `FuzzFormat`: on any input that parses without syntax errors, `Source` doesn't panic, is idempotent, and keeps the template tree.
- CLI: modes and exit codes (`-l`, `-d`, `-w`, `--stdin-filepath`, usage errors), path walking and skips, atomic writes, the Bun notice; LSP: the edits applied to the buffer give the CLI's output (UTF-16 ranges with non-ASCII text), `[]` on a syntax error.
- Once it ships, the starter (`orbit new`), `examples/blog`, `docs/site` and the docs' `orbit` blocks are reformatted, and a test keeps the starter fmt-clean (Q: also assert it for the docs' blocks in `internal/docstest`).
- **Benchmark**: `orbit fmt -l` on `bench/devloop`'s 200-file synthetic project, without and with Bun; measured and published, no target. It doesn't run in `orbit dev`/`build`, so the dev loop is unaffected.

## 7. Dev server (`internal/dev`)
- The proxy listens on `localhost:4321` (`--port`; `--host` listens on all interfaces, as Astro's `--host` does) and serves only `/__orbit/*`: `/__orbit/events` (SSE), `/__orbit/reload.js`, and the overlay.
- Everything else, including `/_orbit/*` and `public/` files, is proxied to the **user's server entry**, which runs with `ORBIT_DEV=1` on a random localhost port and serves assets from `ORBIT_STATIC` and `ORBIT_PUBLIC` (§5b). So auth, logging and custom routes (e.g. a handler for `/robots.txt`) behave exactly as in prod.
- **Reload injection**: the proxy strips `Accept-Encoding` from forwarded requests, so responses come back uncompressed even under a user gzip middleware. `text/html` responses get the reload script before `</body>`, and `Content-Length` is recomputed. Responses without `</body>`, such as `/_orbit/island/*` fragments, are left alone. A response that is still `Content-Encoding`-compressed is passed through without injection, with a one-time warning.
- Pages render per request in dev exactly as in prod; only the asset source (`ORBIT_STATIC`, `ORBIT_PUBLIC`) and the error overlay differ (§5b).
- `fsnotify` watches `src/`, `public/`, `*.go` in the module, and `orbit.json`, `go.mod`/`go.sum`, `tsconfig.json` and `package.json` (excluding `orbit_gen`, `dist`, `.orbit`, `node_modules`, `testdata/`, `_`- and dot-directories, and `_test.go` files), with a 50 ms trailing debounce; events during a build join the next batch, and a file created and removed within one batch (atomic saves) is dropped. Requests wait from the first file event until the rebuild and swap are done; a request whose dial is refused mid-swap is retried once against the new app. (Implemented, milestone 10.) It also watches the files matching `orbit.json` `"watch"` globs (§8), inside or outside the module: each pattern's leading literal directory, recursively when the pattern can match deeper. A change made only of watched (and `public/`) files restarts the running binary without regenerating or `go build`, then reloads; mixed with other changes, the app is restarted even when no Go rebuild was needed.

### 7.1 Live reload
Every change ends with a **full page reload**; there's no HMR. What the server does depends on the change:
- **Only `<style>`/`<script>` content**: incremental esbuild rebuild, which rewrites `.orbit/dev/manifest.json`; the running app picks up the new hashed URLs (§5). No Go rebuild. When only asset files under `src/` changed (`.ts`, `.css`), the bundles are rebuilt from the last bundle input without reloading the project.
- **esbuild is skipped** (user addition, milestone 10) when a key over the asset input (block contents, kinds, line:col, page graphs) is unchanged and no asset file changed: template, frontmatter, `Props` and `.go` edits.
- **`public/` files**: nothing to rebuild.
- **Anything else**, including **gaining or losing a scoped `<style>` or a processed `<script>`** (or toggling `is:global`), which changes the scope attributes in the template output or the esbuild entries. Also templates, frontmatter, user `.go` files, `src/locals`, `orbit.json`, `go.mod`:
  0. **`.go`-only edits start `go build` at once** (user addition, milestone 10), in parallel with regenerating, into the unused one of two binary slots (`.orbit/devserver/server-{0,1}`). If regenerating writes nothing to `orbit_gen`, that build stands; otherwise it's rebuilt after. An unneeded early build is cancelled.
  1. Regenerate only the affected packages, with typed writes (the compiled `orbit_gen/manifest` stays empty in dev, so a CSS edit never forces a Go rebuild). The type checker stays resident in the dev process and re-checks only those packages (§3.3): about 0.3 ms for a body edit.
  2. `go build "-ldflags=-s -w" -gcflags=all=-dwarf=false "-gcflags=./orbit_gen/...=-l -dwarf=false" -buildvcs=false`, with `GOGC` and `GOMEMLIMIT` removed from its environment (dev builds only; the server keeps them). No DWARF or symbol table, no inlining in generated packages (the last matching `-gcflags` pattern wins, so the `orbit_gen` one repeats `-dwarf=false`), no VCS stamping (a `git` run per build), and cmd/compile's own heap tuning, which it applies only when both variables are unset. A `-gcflags` or `-buildvcs` in `GOFLAGS` replaces Orbit's; a `-ldflags` there is merged. The resident type checker's `go list -export` gets the same `-gcflags`/`-buildvcs`, so it shares compiled packages with `go build`. Only changed packages recompile, thanks to the per-component packages. Measured in the spike (§3.3): compiling the changed package takes about 35 ms of a body-edit rebuild, the rest is the app recompile and link, and `-ldflags=-w` brought that rebuild from 190 to 148 ms. The post-MVP build-speed pass (`-s -w`, `-dwarf=false`, `-buildvcs=false`, no `GOGC`, and the runtime's island sealer kept out of `Ctx`'s type graph, see §4b) took a template edit from ~0.22 to ~0.19 s and the worst case below by ~20–25%; numbers in `docs/performance.md`.
  3. Stop the old app (SIGINT, wait for graceful shutdown up to 5 s, then kill), then start the new one on a fresh port and wait until it accepts connections. Requests during the swap wait. Running both side by side would break user apps that bind fixed ports or hold file locks.

Then it sends a `reload` event over SSE.

**Measured worst case**: a user `.go` edit that every `Props` depends on (e.g. `internal/posts`) makes `go build` recompile every generated package. At 200 components that takes about 0.75 s on 16 threads and about 1.3 s on 4 cores, even with no type check at all (spike C). It's `go build`, not typed writes; the dev build flags of step 2 are the mitigation in place. **Milestone 9 finding** (`bench/devloop`): a `.go` edit that changes only a function body costs as much as an API change, because cmd/go recompiles a package's direct importers whenever it changes, even when its export data doesn't. Results and milestone 10 mitigations are in `bench/devloop/README.md` and `docs/performance.md`.

The client (`/__orbit/reload.js`, a few lines, embedded) calls `location.reload()` on `reload`. If the SSE connection drops, it reconnects with backoff and reloads once it's back.

On a compile error, the old app keeps running and the proxy serves an overlay page for HTML requests: the cleaned-up message (§3.3, error output), `file:line:col`, and a code frame. If the new app fails to start, the overlay shows its stderr. Render errors are shown by the app's own dev error overlay (§4). The overlay stays subscribed to SSE, so fixing the error reloads automatically.

## 8. Config (`orbit.json`, all optional)
```json
{ "site": "https://example.com", "server": "./cmd/server", "embed": false, "compressHTML": "html", "sourcemap": false, "watch": [] }
```
- `compressHTML` (user decision; like Astro's option): `"html"` (default; HTML-aware lossless whitespace collapsing, Astro's `true`; `true` is accepted and means `"html"`, user decision), `"jsx"` (Astro v7's default JSX whitespace rules; `{" "}` forces a space) or `false` (verbatim). Applied at codegen time, so it costs nothing at runtime. `<pre>`, `<textarea>`, `<script>`, `<style>`, HTML comments and `{expr}` output are never altered. Rules in `internal/compiler/DESIGN.md`.
- `site`: the absolute site URL, exposed as `ctx.Site`. Unset gives a nil `ctx.Site` (like `Astro.site` being `undefined`); a value that isn't absolute (no scheme or host) is an error when `orbit.json` is loaded.
- `server`: the server entry package; default `./cmd/server` if it exists, else the generated one (§5b).
- `embed`: like `orbit build --embed`; the flag turns embedding on even when this is `false`.
- `sourcemap` (user request, milestone 6): `true` makes `orbit build` also write external source maps next to the bundles under `/_orbit/`, **not linked** from them (no `sourceMappingURL`), with sources mapped to the `.orbit` files. Default `false`. `orbit dev` always writes linked source maps that point at the `.orbit` line and column (user request).
- `markdown` (§2.4): `gfm` (default `true`), `smartypants` (default `true`), `syntaxHighlight` (`false`, or `{"themes": {"light": "github", "dark": "github-dark"}, "css": true}`; `"dark": null` for one theme). An unknown Chroma style name is an error listing the available ones.
- `watch` (user decision, dogfood checkpoint): globs relative to the project root (`../` allowed) whose changes restart the app in `orbit dev` (§7); each `/` part is a `path.Match` pattern, a `**` part matches zero or more directories; patterns match files only. Invalid patterns are errors when `orbit.json` loads (`orbit.json: watch[0] "…": …`); a missing base directory is a warning in `orbit dev`.
- Plain JSON, no comments. Unknown keys are ignored, as `encoding/json` ignores unknown fields (decided by rule: Go stdlib).
- `null` means unset (decided by rule: Go stdlib). `server` must be non-empty and relative; `orbit generate` doesn't check that it exists (`orbit doctor` does). Any other `compressHTML` value is an error: `orbit.json: compressHTML must be "html" (or true), "jsx" or false, not "none"`. JSON syntax errors carry `orbit.json:L:C` (decided by rule: simplest).

There is no `base` or `trailingSlash` option in the MVP (§12); trailing-slash behavior is fixed (§4).

## 9. Language server (`orbit lsp`, `internal/lsp`)
- **Transport**: a minimal hand-written JSON-RPC 2.0 over stdio (`Content-Length` framing, a few hundred lines, `internal/lsp/jsonrpc.go`). Messages are proxied as `json.RawMessage`: only the fields Orbit must inspect or rewrite (URIs, positions, ranges, text edits) are decoded, generically along known paths (`map[string]json.RawMessage`), patched and re-encoded. Everything else (`data`, `labelDetails`, `documentation`, unknown fields) passes through untouched. No typed protocol structs, which go stale and drop fields.
  - **Every range is rewritten**, including `textEdit.range`, the `insert`/`replace` ranges of an `InsertReplaceEdit`, and `additionalTextEdits`.
  - gopls v0.24.0 completion items always carry a `textEdit` and never `data`, and docs come inline in `documentation`: `completionItem/resolve` isn't implemented (-32601), so Orbit doesn't offer or proxy it.
- **Position encoding: UTF-16, always.** gopls (v0.24.0) ignores `general.positionEncodings` and never returns a `positionEncoding`; it always speaks UTF-16. Orbit therefore offers only UTF-16 to the client too.
  - Internally everything (source maps, segments) is in bytes. Orbit converts at both edges: `.orbit` positions with a per-document line index on the client side, and generated-file positions with the overlay's line index on the gopls side. Locations in user `.go` files pass through unchanged (UTF-16 on both sides).
  - At startup Orbit re-checks gopls's `initialize` result: if a future gopls returns a `positionEncoding`, it's honored at the gopls edge.
- **Startup**:
  1. Find the project root (`go.mod` plus `src/`).
  2. Parse every `.orbit` file in tolerant mode and generate in memory. **The LSP never writes `orbit_gen`** (that would race with `orbit dev` and leave broken Go on disk). Where `orbit_gen` is missing or stale, the in-memory files are sent to gopls as overlays.
     - **Typed check** (implemented, milestone 12): tolerant output never equals `orbit generate`'s typed `render.go`, so a byte comparison alone would make every impl file an overlay. While gopls starts, Orbit compiles a strict copy of the current sources with `internal/project`'s pipeline (one `go list -export` plus go/types, about 70 ms at 200 files) only to compare with disk: a file whose typed output equals the disk is read by gopls from disk and mapped through the typed source map. Every other file (edited, broken, not generated, stale) is a tolerant overlay, and a file's first change makes it one. Startup waits for the check at most 5 s; a later result still closes overlays (leaving files open in the editor alone). Requests wait for this decision before mapping positions. The check runs again 300 ms after `orbit_gen/` watched-file events, so overlays close once `orbit dev` or `orbit generate` catches up.
     - There's no "Run orbit generate" prompt (removed at the milestone 12 checkpoint, user decision: without `orbit_gen` startup is only ~50 ms slower at 200 files; `orbit doctor` still reports a missing `orbit_gen/`).
  3. Index all components: path, alias suggestions, `Props` fields (name, type string, doc comment, from `go/ast`), and slot names.
  4. Spawn gopls with the same root. Lookup order: the `goplsPath` initialization option (`initializationOptions: {"goplsPath": "…"}`; the VS Code extension sets it from its `orbit.goplsPath` setting), then `gopls` on PATH, then `go tool gopls` if the user's `go.mod` pins it (optional). If none is found, show how to install it. The tool pin is optional because it pulls in all of x/tools, can raise shared dependency versions through MVS, and its first build takes 30–60 s, which risks client startup timeouts.
  5. **Old gopls is refused.** Read `serverInfo.version` from gopls's `initialize` result; it's JSON with the `GoVersion` gopls was built with (`"GoVersion":"go1.23.4"`). If that is older than the project's `go` directive, gopls can't type-check the project's language features: v0.18.1 built with go1.23.4 falsely rejects Go 1.26's `new(expr)`. Orbit then shuts gopls down, disables the Go-proxied features for `.orbit` files (native template features keep working), and shows an actionable error naming the install command (`go install golang.org/x/tools/gopls@latest`). The recommended minimum is **gopls v0.24.0** (the version verified in the spike); document it in `editor-setup.md`.
  6. **Readiness barrier**: gopls's initial workspace load doesn't see overlay-only directories. It loads each overlay lazily with its own serial `go list file=…` (about 25–35 ms each). Forward lookups work on demand, but **reverse lookups (references, rename) silently miss importers** until every overlay is loaded, and "all diagnostics published plus a quiet period" isn't a reliable signal. After sending the overlays, Orbit asks gopls which `orbit_gen/` packages it has loaded (`gopls.packages`, which waits for the workspace load; its progress isn't forwarded) and sends a `textDocument/documentHighlight` only for the missing overlay-only ones, open documents first, 4 at a time; only those are re-sent afterwards so gopls publishes their diagnostics. With 16 or more overlay-only files (counted before `initialize`: no file on disk), gopls starts on an empty placeholder folder (a temp dir, removed after the barrier) and gets the project's folder in its place (`didChangeWorkspaceFolders`) once every overlay is open, so one workspace load sees them all instead of hundreds of lazy loads. With the project folder already there, each `didOpen` would cost gopls time proportional to the overlays already open (zero-config view selection, a snapshot clone, a lazy load). If only the typed check finds that many, the folder is removed and re-added. (Implemented, milestone 12; the first version sent one `documentHighlight` per overlay in parallel, and each kept its own decoded copy of the imports in gopls: 3 GB and 9.7 s at 200 files.) Measured: 102 overlays 2.4 s → 0.18 s; 200 files overlay-only 9.7 s → 1.4–3.8 s (folder re-add) → 0.33 s (placeholder), gopls ~180 MB; with `orbit_gen` on disk, no barrier work. Until then, references, rename and `prepareRename` are held; completion, hover and diagnostics don't wait for Orbit's barrier (with the placeholder, gopls itself holds them until its workspace load ends, ~0.3 s). Progress is shown with `window/workDoneProgress`.
- **Acting as gopls's client**: Orbit answers or forwards gopls→client requests, and **never answers gopls with an error**: an error answer is fatal (gopls reports "no views" and every request fails). Unknown requests get `null`.
  - `workspace/configuration` (section `gopls`): the client's `gopls` section, or `{}`. Orbit sets `diagnosticsDelay: "50ms"` unless the user sets it (a decl change reaches an importer's diagnostics in 54 ms instead of 1.0 s), and `zeroConfig: false` unless the user sets it (Orbit's gopls sees only the project's module; zero-config view selection cost ~1 s over 400 overlays). Scopes for the startup placeholder folder are mapped to the root.
  - `client/registerCapability`: forwarded. gopls registers `workspace/didChangeWatchedFiles` (`**/*.{mod,work}`, `**/*.{go,mod,sum,work}`) and `workspace/didChangeConfiguration`. Orbit adds its own `**/*.orbit` watcher. The client's watched-file events for `.go` files (including `orbit_gen` rewritten by `orbit dev`/`generate`) and `didChangeConfiguration` are forwarded to gopls.
  - `window/workDoneProgress/create` and `$/progress`: forwarded (`null` if the client lacks support).
  - `workspace/applyEdit`: edits mapped to `.orbit`, dropped if unmappable (not observed in the spike).
  - `window/showMessage(Request)`: forwarded, except gopls's "Warning: editing render.go, a generated file." (sent on the first `didChange` of each overlay), which is swallowed.
- **Open documents**: on `didOpen`/`didChange`, re-parse and regenerate that file in memory, then send **both** its declaration and implementation files to gopls as overlays (`didOpen`/`didChange` for `orbit_gen/decl/<pkg>/decl.go` and `orbit_gen/impl/<pkg>/render.go`). A frontmatter edit can move code between the two. gopls overlays are visible across packages, so other components see new `Props` with no disk write (completion sees a new field within 1–2 ms). `didSave` re-indexes; nothing is written. On `didClose`, an overlay stays open until the on-disk generated file matches it, or the typed check finds its typed output on disk.
  - **Markdown documents** (§2.4): `.md` files under `src/` are followed too (`docPath`): `didOpen`/`didChange` keep the buffer on the document (an uncompiled `.md` may become compiled when an `.orbit` file imports it) and run `project.UpdateMarkdown`, which re-parses that file if it's compiled, regenerates it, reruns the link checks and recomputes the diagnostics; only the files whose pass-1 output changed are re-sent to gopls. `didClose` reloads the disk content; watched-file events for an open `.md` are ignored. Opening a `.md` never loads a project (only an `.orbit` file does, when the editor's root has none).
- **Positions**: map orbit offsets to Go offsets through the source map: find the containing segment (with an inclusive end, so a cursor at the end of `props.` maps); `exact` segments use offset arithmetic, `span` segments clamp, and `echo` segments map to nothing. The reverse mapping uses a second sorted index.
- **Request routing** depends on the cursor position, as classified by the orbit parser:
  - **Go regions** (frontmatter, `{expr}`, attribute exprs, control headers) → gopls: completion, hover, definition, references, signatureHelp, **rename**. For rename:
    - `prepareRename` is **gated by Orbit's own routing**: it's forwarded only when the cursor is in a Go region that maps to user code (gopls would also prepare a rename of glue identifiers such as `orbit__w`). It waits for the readiness barrier.
    - gopls's `WorkspaceEdit` is mapped edit by edit through the source maps of every affected generated file (other components' impl/decl files, and user `.go` files, which pass through unchanged).
    - Edits on `echo` regions (the `_ = name` lines, §2.2) are dropped: renaming `title` gives an edit there as well as on its declaration and its `{title}` use.
    - The rename is rejected with a clear message if any other edit lands in an unmapped region.
    - gopls always returns `documentChanges` (with overlay URIs and versions), even when the client says it doesn't support them. Orbit converts them to `changes` for clients without `workspace.workspaceEdit.documentChanges` support.
    - A rename of a `Props` field also rewrites the matching attribute names at every `<Card field=…>` call site (via the field-key spans) and keeps their kebab/camel form.
    - Renaming an `.orbit` import alias updates the tags that use it, and its Go uses (`Card.Props`).
    - A rename of a layout `Props` field that a `.md` frontmatter sets is refused (user decision: Orbit doesn't edit Markdown), naming the file, line and key: `can't rename Title: the frontmatter of src/pages/blog/hello.md:3 (title) sets it, …`.
    - Implemented (milestone 12): `prepareRename` gates glue with a gopls definition request (a user variable that shadows `ctx` stays renameable); a shorthand attribute keeps its meaning (renaming the field gives `article={post}`, renaming the variable `post={value}`); a Go import used by both generated files is renamed in both (gopls renames a package name in one file, so Orbit sends a second rename); refusals are `RequestFailed` errors with a message, while positions with nothing to rename get `null` (LSP spec); a renamed attribute keeps its call site's spelling (kebab, snake, all-lowercase; anything else becomes lowerCamel); stale `orbit_gen` files that belong to no `.orbit` file are skipped. Warm `prepareRename` about 0.2 ms, `rename` about 0.7 ms at 50 components.
  - Results are mapped back. Locations inside `orbit_gen/**` are translated to their `.orbit` source using that file's map, rebuilt from the overlay or disk on demand.
  - Outside rename, edits that land in unmapped regions are dropped. The exception is auto-import `additionalTextEdits`, which are rewritten as insertions into the frontmatter import block, or into a new `import` line at the top of the frontmatter.
  - **Tag name** after `<` → native: imported component aliases first, then unimported components (with an additionalTextEdit that adds the `.orbit` import), then HTML tag names.
  - **Import path** (implemented 2026-10-26): inside the string of a frontmatter import spec whose path starts with `.` (an `import [X] "…"` line, or an `[X] "…"` line in an `import ( … )` block; found on the line's text, so it works while the frontmatter doesn't parse) → native, taking precedence over gopls: every `.orbit` file and every `.md` under `src/` (`Project.MarkdownPaths`), minus the file itself and those already imported, as paths relative to the file, sorted nearest first. With no alias, accepting one also inserts the alias (`compiler.FieldName` of the base name, made unique as for tag auto-imports). `/` is a completion trigger character for it (ignored elsewhere).
  - **Attribute position**:
    - On a component: Orbit asks gopls for completion inside a synthetic `Card.Props{|}` literal (implemented, milestone 12: in an overlay-only scratch package per target component, `orbit_gen/orbit__lsp/<pkg>/props.go`, opened once and never written or edited, so the user's overlay isn't touched; gopls sees unsaved `Props` changes through the decl overlay). gopls returns the unset fields first, then deep completions and every in-scope identifier (58 items in the spike). Orbit **keeps only kind 5 (Field) items with no `.` in the label**, maps the field names to attribute names, uses their inline `documentation` (merged with the native index's doc comments), and replaces gopls's `Field: ${1:}` snippet with attribute insert text (`post={$1}`). Fields already set are excluded by Orbit (the scratch literal is always empty). This handles embedded fields and type aliases; the native index is the fallback.
    - On an HTML element: global and element attributes from an embedded trimmed JSON dataset (a subset of the MIT-licensed vscode-html-languageservice data).
    - On either: directives (`set:html`, `set:json`, `slot`, `is:inline`, …).
    - On a component only: `server:defer`, `client:load`, `client:idle`, `client:visible`, `client:media` (never offered on HTML elements, where they're errors, §2.3).
  - **`slot="`** → the target component's slot names; inside a `server:defer` component, only `fallback`.
  - **Definition** on `<Card` → `Card.orbit`. On a component attribute → the `Props` field. On a `params` field (or `params` itself) → gopls answers with the generated `Params` in the page's `decl.go`, which has no source-map entry; Orbit maps it to the start of the page's own `.orbit` file (the field comes from its file name) instead of dropping it.
  - **`params.`** in a page is a Go region, so completion and hover come from gopls: `Params` is in the page's declaration overlay, and its fields complete like any struct's (`Slug string`). Renaming a `params` field is rejected (it comes from the file path; rename the file instead).
- **Diagnostics**: **gopls ignores line directives everywhere.** Diagnostics, hover, definition and references all use the generated URIs and raw positions (gopls uses `PositionFor(pos, false)`); nothing is ever reported against an `.orbit` URI. The mapper therefore translates only `orbit_gen/**` locations, through the source maps; the directives exist for `go build` and `go vet`.
  - Results are merged with Orbit's own diagnostics (parser errors, and codegen checks such as unknown props, §2.3) and published per document. A gopls `unknown field` diagnostic on a field key that Orbit already reports as an unknown prop is dropped as a duplicate.
  - gopls's diagnostics for the user's own `.go` files and `go.mod` aren't forwarded: the editor's Go support reports them, and forwarding showed them twice (decided by rule: Astro's language server reports only `.astro` files; milestone 12). This also drops gopls's overlay-only `go.mod` warning "`<module>` is not used in this module".
  - Hover text is cleaned in the LSP (`line …` directive text, pkg.go.dev links to `orbit_gen` packages), since a body statement's inline `/*line*/` directive reaches gopls's hover as a doc comment (decided by rule: simplest; the alternative was own-line directives before body statements, changing every generated file).
  - Diagnostics outside mapped regions are attached to the top of the file, prefixed with "internal:" (this should only come from codegen bugs).
  - **Markdown files** (§2.4): Orbit's own diagnostics (frontmatter, layout, links and fragments, route errors) are published for every compiled `.md`, converted to UTF-16 with the file's line index like `.orbit` ones; gopls's diagnostics of `.md` generated files are not merged. Checks run one at a time; a check asked for while one runs runs after it. Off the request path: it takes `s.mu` only to snapshot and to adopt, never touches gopls, the generated files or the readiness barrier. `.orbit`-only editing never runs it. ## 9b. TypeScript in `<script>` blocks

**Status: Accepted** (2026-10-26; the user asked whether TypeScript 7 native really works, and the coordinator confirmed it with its own test: npm `latest` is 7.0.2 (2026-07-08), a static Go binary; `tsc --lsp --stdio` answered diagnostics, completion and hover in ~30 ms at 52 MB). User answers: (Q1) TypeScript 7 native; (Q2) found locally (setting, project `node_modules`, `tsc` on PATH, always the native binary), then `bun x --package typescript@7.0.2` with Bun; (Q3) in-memory documents under `.orbit/lsp/` with an in-memory copy of `orbit check`'s tsconfig; (Q4) the full first-release feature set; (Q5) in-memory `.d.ts` overlays, debounced; **(Q6) `is:inline` scripts are in, as JavaScript documents (user decision, not the recommendation; Astro covers them)**; (Q7) open every script's document on the first references/rename request. It's the item that follows the typed bridge (§5c (Q8)). It gives processed `<script>` blocks in `.orbit` files TypeScript completion, hover, diagnostics, definition, references, rename and signature help in the editor. Today they get highlighting only (§9 "Out of scope"), so the bridge's types only show up in `orbit check` and in separate `.ts` files. The measurements below come from a throwaway spike in `scratchpad/ts-lsp-spike/` (Ryzen 7 9700X, 16 threads, load average 0.4–1.6, the machine shared).

**In short**: `orbit lsp` starts **TypeScript 7's native language server** (`tsc --lsp --stdio`, a static Go binary, no Node) as a second child next to gopls. It runs only when the project has a processed inline script. Each processed inline script becomes an **in-memory virtual `.ts` document** at `.orbit/lsp/<path>.orbit.<n>.ts`. That document is the `.orbit` file with everything outside the block blanked to spaces, so lines and UTF-16 columns are the same as in the `.orbit` file. It sits next to an **in-memory `tsconfig.json`**, the one `orbit check` generates, and both are sent with `didOpen`; nothing is written to disk. Requests whose cursor is in a script region go to that child. Results come back with the virtual URI swapped for the `.orbit` URI and the positions left alone. Locations in `orbit_gen/types/*.d.ts` are mapped back to the `orbit.JSON` attribute. The types the LSP generates in memory are sent to the child as overlays, so an unsaved Go change updates script completion. Without TypeScript 7 on the machine, the Go and template features work as they do today and the server shows a notice once.

### Finding the engine (Q2)
Lookup order, like gopls's (§9 startup step 4):
1. The **`typescriptPath`** initialization option (VS Code: the `orbit.typescriptPath` setting). It can point at a native `tsc` binary or at a `typescript` package directory.
2. The project's **`node_modules/typescript`** at version 7 or later. This is for projects that already have a `package.json`, and is the place the TS team recommends. Orbit resolves the native binary the way the package's `lib/getExePath.js` does, `node_modules/@typescript/typescript-<platform>-<arch>/lib/tsc` (Go's `GOOS`/`GOARCH` mapped to Node's names: `darwin`, `linux`, `win32`; `x64`, `arm64`), so **Node is never run**.
3. **`tsc` on PATH**, symlinks resolved. If it's the npm shim (`…/typescript/bin/tsc`, a Node script), Orbit runs the native binary next to it as in step 2. That covers `bun add -g typescript` and `npm i -g typescript`.
4. **Bun present**: `bun x --package typescript@7.0.2 tsc --lsp --stdio`. The spike measured 0.62 s for the first download into Bun's cache and 10 ms after that; the shim `execve`s the native binary, so no Bun process stays alive. (Q2 option b.)
5. Not found: a one-time `window/showMessage` notice, "TypeScript features in `<script>` blocks need TypeScript 7: …", with the install line and a pointer to `orbit doctor`. Shown only when an `.orbit` file with a processed inline script is opened.

The **(Q2)** choice is how a user with nothing installed gets TypeScript:
- (a) **Steps 1–3 and 5 only**: the docs say `bun add -g typescript@7` or `npm i -g typescript@7`. Simplest, but it pulls in a package manager.
- (b) **(a) plus step 4 (`bun x`)** (recommended): users who have Bun for `orbit check`/`fmt` get the features with no extra step, and Bun stays optional. The cost is a network fetch on first use, from Bun, to Bun's cache, pinned to an exact version.
- (c) **(b) plus Orbit downloading the platform tarball itself**: the npm registry's `@typescript/typescript-<os>-<arch>@7.0.2`, verified against a `sha512` integrity value pinned in Orbit's source, unpacked into `os.UserCacheDir()/orbit/typescript/7.0.2/` with stdlib `net/http`, `compress/gzip` and `archive/tar` (no new dependency). The LSP would offer it once through `window/showMessageRequest` ("Download TypeScript 7.0.2 (9.7 MB)?"; Neovim supports this request too). This is zero-install for everyone, but the language server would do network I/O and Orbit would own a download path, a pinned hash per platform and cache cleanup.

Pin: Orbit's source names one TypeScript version (7.0.2 today) for the `bun x` fallback and the docs. It's raised with Orbit releases and is at least two weeks old (CLAUDE.md). A user's own TypeScript (steps 1–3) is used as found, if it's 7.0.2 or later.

### Architecture
**Process.** `internal/lsp/tsproxy.go` (new) reuses `jsonrpc.go`'s `Conn` and the patch-only `json.RawMessage` approach of §9: no typed protocol structs. The TS child starts **lazily**, on the first `didOpen` of an `.orbit` document that has a processed inline script, or on the first request that needs every script (references, rename; below). That keeps the 57 MB out of sessions that never edit a script; a cold start costs ~30 ms. Its `initialize` uses the project root as its only workspace folder (`zeroConfig` isn't a concept there). Orbit offers the client's capabilities with UTF-16 only, and checks the returned `positionEncoding`: TS 7 accepts `utf-16`, and any other encoding is converted at the edge like gopls's (§9). If the child exits, Orbit drops its virtual documents, restarts it once after the first crash (lazily, on the next request), and after a second crash shows a notice and stays off until `Restart Language Server`. Go features never depend on it.

**Virtual documents.** For each processed inline script block `n` of `src/<path>.orbit` (§5's rule: `compiler.Scripts`, without `src`, the same set as `orbit check`'s `Extract`), Orbit builds one document:
- **URI**: `<root>/.orbit/lsp/src/<path>.orbit.<n>.ts`, which mirrors `src/`. It's sent with `didOpen`, never written to disk, and named like `check.ExtractPath` but under `.orbit/lsp/` (Q3).
- **Text**: the `.orbit` source with every character outside the block's content replaced by spaces: one space per UTF-16 unit, so two for an astral character. Line breaks (`\n`, `\r\n`) are kept, and `\nexport {};\n` is appended, as in `orbit check`, so every block is a module. **Lines and UTF-16 columns of the virtual document equal those of the `.orbit` file**, so a position needs no arithmetic in either direction. That's simpler than `orbit check`'s offset table, and the client's UTF-16 positions pass straight through. Each block of a file gets its own document, with the other blocks blanked.
- **tsconfig**: an in-memory `<root>/.orbit/lsp/tsconfig.json`, also opened with `didOpen`. Its content is `check.Tsconfig(check.ReadUserTsconfig(root))`, the file `orbit check` writes: it `extends` the user's tsconfig, `rootDirs` is `["../..", ".", "../../orbit_gen/types"]`, and `include` adds the user's `src/**/*.ts` and `orbit_gen/types/*.d.ts`. So relative imports (`../scripts/util`), `./X.orbit` imports (through `rootDirs`), `orbit:client`/`orbit:types` and the user's compiler options resolve the way `orbit check` resolves them, **even in a project whose `tsconfig.json` wasn't migrated** (§5c). Measured: TS 7.0.2 honors an in-memory `tsconfig.json` for project discovery. With the user's tsconfig stripped of `rootDirs`, a virtual document next to it gave `TS2307`, while the same document under the in-memory `.orbit/check` tsconfig resolved `./LikeButton.orbit` and reported the type error. A test guards this behavior (Tests), with writing the file to `.orbit/lsp/` as the fallback if a later TypeScript drops it. When `tsconfig.json` changes (a watched-file event), the in-memory one is recomputed and sent with `didChange`.
- **Sync**: on every `didOpen`/`didChange` of an `.orbit` document, Orbit re-parses it already (§9) and rebuilds the text of its blocks' documents. Each is sent as one full-text `didChange` (decided by rule: simplest; a 10 KB file costs nothing next to TypeScript's 2–4 ms recheck). It's sent only if that block's text changed, which also covers edits outside a block that shift its lines. When the number of blocks changes, documents are opened or closed. Script positions come from the tolerant parse. If the parse fails before the scripts, the previous documents stay as they are, as for overlays.
- **Which documents are open**: the documents of the `.orbit` files open in the editor. References and rename first open the documents of **every** `.orbit` file with a script, once per session, built from the workspace's sources (buffers or disk), so reverse lookups don't miss closed files. This is the TypeScript equivalent of §9's readiness barrier: 200 scripts take ~0.3 s once (spike: 290 ms to the first completion with 200 open, 88 ms for their 200 diagnostics), and RSS grows from 62 to 120 MB (Q7). Documents opened that way stay open; their diagnostics are **not** published (only open `.orbit` documents get TS diagnostics; the whole project is `orbit check`'s job).

**Request routing** (the §9 router gains a region): a cursor inside a processed inline script's content goes to the TS child; Go regions stay with gopls and template positions stay native. Methods routed: `completion` (plus `completionItem/resolve`, below), `hover`, `definition`, `typeDefinition`, `references`, `prepareRename`/`rename`, `signatureHelp`, `documentHighlight`, `codeAction` (Q4). Positions pass through unchanged and the URI is swapped. A script region with no TS child answers `null` (an empty list for completion).
- **Results**: every URI is mapped generically along the known paths (the §9 mapper):
  - a virtual document URI → its `.orbit` URI, with positions unchanged;
  - `orbit_gen/types/<path>.orbit.d.ts` and `orbit_gen/types/go.d.ts` → mapped as described next;
  - `orbit_gen/types/client.d.ts` and every other file (`src/**/*.ts`, `node_modules`, TypeScript's `lib.*.d.ts`) → passed through.
- **`.d.ts` locations** (Q4): Orbit generates these files, so when it emits them in memory (Q5) it keeps a **side table** from each declaration's line to its source.
  - A `data-*`/`set:json` key in `<path>.orbit.d.ts` maps to the attribute's position from the compiler's `JSONSites` (today's `.d.ts` comment `data-like (LikeButton.orbit:14:14)` names the same place).
  - A member or interface in `go.d.ts` maps to the Go declaration from the type mapper's `types.Object` position: a frontmatter type through the typed source map into the `.orbit` file, a user `.go` file directly.
  - Without an entry (stale disk types), the `.d.ts` location passes through.
  
  For `definition`, the mapped location replaces the `.d.ts` one. For `references`, `.d.ts` locations are dropped (they're generated).
- **Edits** (rename, code actions, completion `additionalTextEdits`): an edit in a virtual document must lie inside its block's content, or it's dropped. The exception is TypeScript's import insertion at the top of the file (line 0, inside the blanked frontmatter), which is moved to the first line of the block's content, after any existing imports. An edit in a `.ts` file under `src/` passes through as a normal workspace edit. A **rename whose edits touch `orbit_gen/types/**` is refused** with a message: renaming `likes` means renaming the Go field (`Likes`, or its `json` tag), so rename it in Go. Like §9, the result uses `documentChanges` or `changes` depending on the client's capability.
- **`completionItem/resolve`**: TS 7 returns items without documentation or auto-import edits and fills them in on resolve (`resolveProvider: true`). Orbit starts advertising `resolveProvider` and wraps each TS item's `data` as `{"orbit":"ts","d":<original>}`. A resolve with that marker goes to the child, and the edits it returns are mapped as above. gopls and native items have no `data` and resolve to themselves.
- **Trigger characters**: TS's are `.`, `"`, `'`, `` ` ``, `/`, `@`, `<`, `#`, space and `*`; Orbit already has `.`, `<`, space, `:`, `"`, `'`, `{` and `/`. Orbit advertises the union. When a trigger character isn't one of the cursor region's own, the request answers an empty list without asking anyone (decided by rule: simplest; the alternative was a fixed subset).

**Diagnostics.** TS 7 publishes no push diagnostics for documents unless the client supports pull diagnostics. The spike saw none when the client didn't declare `textDocument.diagnostic`. So Orbit, as its client, declares pull support and asks with `textDocument/diagnostic` for each changed open virtual document, debounced 50 ms after the last change (like gopls's `diagnosticsDelay`, §9). It asks again for every open virtual document on `workspace/diagnostic/refresh`, which the child sends when a `.ts` or `.d.ts` dependency changes. The results come back with `.orbit` positions already. Orbit labels them `source: "ts"`, merges them with Orbit's and gopls's diagnostics for the file (§9 `publish`), and **keeps the `unnecessary`/`deprecated` hints**: the editor fades an unused import, and `orbit check` doesn't print these hints. Diagnostics outside the block's range (which shouldn't happen, since the text there is blank) are dropped.

**Acting as the TS child's client** (like §9's gopls rules; never answer with an error):
- `workspace/configuration`: TS 7 asks for the sections `js/ts`, `typescript`, `javascript` and `editor`. Orbit forwards the client's answer, or `{}` for each.
- `client/registerCapability`:
  - `workspace/didChangeConfiguration` is forwarded.
  - `workspace/didChangeWatchedFiles` is **not** forwarded: in the spike, TS 7 registered `<root>/**/*`, its own `lib/**/*`, and `/tmp/**/*` (an ancestor of the project, from failed lookups; in a home-directory project that would be `~/**/*`). Instead, Orbit registers one watcher of its own with the client, `**/*.{ts,mts,cts,d.ts,js,mjs,json}` under the root, and forwards every event under the root to the child (decided by rule: simplest; the child filters events itself). `orbit_gen/types/` events also close the `.d.ts` overlays that disk has caught up with (Q5), as for gopls.
- `window/workDoneProgress/create` and `$/progress`: forwarded.
- `window/showMessage` and `window/logMessage`: `logMessage` goes to Orbit's log; `showMessage` is forwarded.
- `workspace/applyEdit`: mapped as edits, above.
- Unknown requests get `null`.

**Missing or broken engine.** Nothing about gopls changes. A missing or too-old engine gives the one-time notice (above). In script regions, completion answers an empty list and the other requests `null`. `orbit doctor` reports it (below).

### Feature scope of the first release (Q4)
Recommended in: diagnostics; completion with auto-imports (`completionItem/resolve`); hover; signature help; definition and type definition, including the `.d.ts` → `.orbit`/Go mapping; references; rename, refused for generated types; document highlight; code actions of kind `quickfix` (TS's "Add missing import", "Fix spelling", …), mapped like other edits.

Recommended out:
- **Formatting**: stays with `orbit fmt`/`bun fmt` (§6.1, user decision). The LSP's `textDocument/formatting` already formats scripts with `bun fmt`. Range and on-type formatting aren't advertised.
- **Inlay hints, code lens, semantic tokens, call hierarchy, `source.*` code actions** (organize imports, fixAll): later. TextMate keeps colorizing.
- **Linked editing and document symbols for scripts**.

The cheaper alternative is a first release of diagnostics, completion and hover only, with definition, references and rename later. It's barely cheaper, because references and rename are what need the "open all" step and the edit mapping. Doing it all in one release follows the §6.1 precedent of one release with shared machinery.

### Types fresh in the editor (Q5)
`orbit_gen/types/` on disk changes only when `orbit dev` or `orbit generate` runs. On its own, then, a script's completion would only learn about a new `orbit.JSON` key or a changed Go field after a save with `orbit dev` running (or a manual generate).

Recommended: **serve the types in memory**. Startup step 2's typed check (§9) already compiles a strict copy through `internal/project`'s pipeline, which since §5c also produces the types (`typecheck.go`, the `.d.ts` text that `GenFiles` writes); today the LSP discards them. Orbit compares each file with the disk the same way it compares Go files. Where they differ (or the file is missing), Orbit opens the in-memory text in the TS child as an overlay (`didOpen` of `orbit_gen/types/…`, measured: an overlay `.d.ts` changes the virtual documents' diagnostics in 2.2–4 ms). The overlay is closed once the disk matches.

While typing, the `mdcheck.go` pattern applies (§9 "Markdown typed check while typing"). 300 ms after a change the types may depend on, a background goroutine:
- clones the buffers in strict mode;
- type-checks the `.orbit` files that have `orbit.JSON`/`set:json` sites;
- re-emits their `<path>.orbit.d.ts` and `go.d.ts`;
- adopts the result only if nothing changed in the meantime.

The changes that trigger it are an `.orbit` buffer edit in a file that has, or had, `orbit.JSON`/`set:json` sites, or `.go`/`go.mod` events. It reuses the same resident `compiler.Checker` as the Markdown check, so the `go list -export` happens once. The cost is about what the Markdown check costs, ~20 ms CPU per run at 200 files (almost all the strict clone's `Front`) plus microseconds of TS emission (§5c Cost: 1.9–5.3 µs per use). It runs off the request path, and `.orbit` edits that don't touch data don't run it.

The cheaper alternative is to use disk types only, with docs saying "keep `orbit dev` running". That's no work, but Go → script feedback then waits for a save and a dev rebuild, which is the gap this item exists to close.

The user's own editor TypeScript (for `.ts` files) keeps reading the disk types. That's consistent with how gopls's `.go` view works.

### Other scope decisions
- **(Q6) `<script is:inline>` and other unprocessed scripts**: recommended **out** of the first release. Inline scripts are plain JavaScript in the page's global scope, not bundled modules. Their imports don't resolve, the bridge doesn't apply, and each would need a classic-script virtual document (`.js` with `checkJs` off), where the only value is DOM completion. Astro's language server does treat `is:inline` scripts as JavaScript, so rule 1 points the other way; the trade-off is small value for a second document kind. `type="application/ld+json"` blocks are JSON and stay out; `<script src="./x.ts">` is a `.ts` file (next point).
- **`.ts` files under `src/`**: Orbit's server **leaves them alone** (decided by rule: Astro's language server leaves `.ts` files to the editor's TypeScript). The documentSelector doesn't change, and the user's TypeScript (VS Code's built-in TS 6 tsserver, the TS 7 extension, or `typescript-language-server`/`tsgo` in Neovim) keeps serving them through the user's `tsconfig.json`. Both servers read the same `.ts` files and the same `orbit_gen/types/*.d.ts` from disk, so they agree once types are on disk. Orbit's child also sees the unsaved overlays of Q5, and sees saved `.ts` changes through the watcher. It doesn't see **unsaved** `.ts` buffers (the same as gopls with user `.go` files, §9). One direction is missing: "find references" from a `.ts` file doesn't list uses inside `.orbit` scripts (Out of scope).
- **Frontmatter and `{…}`**: Go, gopls; unchanged.
- **Position encoding**: UTF-16 at both edges (§9). The blanking keeps UTF-16 columns, so no conversion happens in the TS path.

### Editors and `orbit doctor`
- **VS Code extension**:
  - a new setting `orbit.typescriptPath` (`machine-overridable`, like `orbit.goplsPath`), passed as the `typescriptPath` init option; changing it restarts the server.
  - The documentSelector doesn't change. The middleware already sends hover, completion, definition, references, signature help and rename of `.orbit` documents to Orbit, and `completionItem/resolve` and code actions need no middleware.
  - `package.json`'s description mentions TypeScript.
  - VS Code's built-in TypeScript doesn't see `.orbit` scripts, so features don't show up twice. Snippets of the `typescript` language that VS Code offers in embedded `source.ts` scopes may still appear next to Orbit's items, as today.
- **Neovim**: no change to the `vim.lsp.config('orbit', …)` snippet; `init_options = { typescriptPath = "…" }` is documented as optional.
- **`orbit doctor`**: a new **TypeScript** environment check, after Bun: ✓ `tsc 7.0.2 (path)`, or ✓ "TypeScript 7.0.2 through `bun x`" for option (b); ⚠ (never ✗: optional, like Bun) "not found (7.0.2 or later needed); TypeScript features in `<script>` blocks are off in the editor", with the fix line; ⚠ for a `tsc` older than 7 ("has no language server; 7.0.2 or later needed"). Inside a project, the check is a ⚠ only if some `.orbit` file has a processed inline script; otherwise it's informational (✓ "not needed").

### (Q) points
1. **(Q1) Engine**: TypeScript 7's native `tsc --lsp --stdio` (recommended: no Node, ~30 ms start, 57 MB, plain LSP, every editor, the same 7.0.2 checker as `bun check`) vs. `typescript-language-server` + TS 6 (Node ≥ 22, 10× slower and bigger, and tsserver put in-memory files in inferred projects) vs. Volar (Node + TS 6 API) vs. VS Code's built-in TS through virtual documents (VS Code only, no tsconfig).
2. **(Q2) Install story**: (b) found locally (setting, project `node_modules`, `tsc` on PATH, resolved to the native binary, never through Node) plus `bun x --package typescript@7.0.2` when Bun is present (recommended) vs. (a) found locally only, vs. (c) (b) plus an opt-in download of the pinned platform tarball by the LSP (zero-install, but network I/O and a pinned hash per platform in Orbit).
3. **(Q3) Where the virtual documents live**: in memory under `.orbit/lsp/` with an in-memory copy of `orbit check`'s generated tsconfig (recommended: works on unmigrated tsconfigs, agrees with `orbit check`, writes nothing, so `reference/cli.md`'s "It never writes files" stays true) vs. next to the `.orbit` file (`src/…/X.orbit.0.ts`, in memory, under the user's own tsconfig: measured to work in the starter's tsconfig, but `TS2307` when `include` or `rootDirs` doesn't cover it) vs. the LSP writing `.orbit/lsp/tsconfig.json` to disk (the fallback if TS stops honoring in-memory tsconfigs).
4. **(Q4) First-release features**: diagnostics, completion with auto-imports, hover, signature help, definition (with `.d.ts` → `orbit.JSON` attribute / Go declaration), references, rename (refused for generated types), document highlight, quick fixes (recommended), vs. diagnostics + completion + hover first. Formatting stays `bun fmt`.
5. **(Q5) Fresh types**: in-memory `.d.ts` overlays from the typed check at startup and a debounced background typed pass while typing, sharing the Markdown checker (recommended: ~20 ms CPU per run at 200 files, off the request path) vs. disk types only (`orbit dev` must run, and feedback waits for a save).
6. **(Q6) `is:inline` scripts**: out of the first release (recommended; plain global JS, imports and bridge don't apply) vs. in, as JavaScript documents with completion and hover only (Astro does this).
7. **(Q7) "Open all" for references and rename**: open every script's virtual document on the first references/rename request (recommended: ~0.3 s once at 200 scripts, +60 MB) vs. open documents only (rename would silently miss closed files, which is unsafe) vs. open all at startup (pays the 0.3 s and the memory in every session).

Decided by rule (to log in `docs/DECISIONS.md`):
- `.ts` files left to the editor's TypeScript (Astro).
- Full-text `didChange` for virtual documents (simplest).
- One Orbit watcher instead of forwarding TS's broad globs (simplest).
- The union of trigger characters, with off-region triggers answered empty (simplest).
- TS diagnostics only for open `.orbit` documents (Astro).
- Lazy start of the TS child (simplest that keeps memory flat).
- The pull-diagnostics debounce of 50 ms, as gopls's `diagnosticsDelay` (§9).
- `⚠`, never `✗`, in doctor (Bun's precedent).
- A crashed child is restarted once (simplest).

### Cost
- **Editing time**: no change for Go and template requests (separate child, separate routing). The TS child starts only with a script open: ~30 ms to the first answer, 57–62 MB RSS (1 open script; `examples/blog` and a 200-component synthetic project); 117–121 MB with 200 scripts open after references/rename. Per keystroke in a script: block text rebuild (µs), one `didChange`, a 2.5–3.9 ms recheck, 1.7–2.6 ms for a warm completion. Per keystroke elsewhere in an `.orbit` file with scripts: the same `didChange` when line numbers shift. The background typed pass (Q5): ~20 ms CPU per data-affecting edit, debounced.
- **Install**: nothing new is required. Optional: TypeScript 7 (24 MB binary), or nothing with Bun under (Q2 b), which fetches 9.7 MB once into Bun's cache.
- **Build and dev loop**: none. `orbit generate`, `dev`, `build` and `check` are untouched; no new Go dependency.
- **Code**: about 1,000–1,500 lines in `internal/lsp` (`tsproxy.go`, `tsdocs.go`, router and mapper extensions, the side table in `internal/compiler`'s type emitter), plus tests.

### Out of scope
- TypeScript in `is:inline` scripts (Q6) and in JSON blocks.
- "Find references" or rename **from `.ts` files** reaching uses inside `.orbit` scripts. That would need a TypeScript plugin in the user's own TS server; TS 7.0 has no plugin API.
- Unsaved `.ts` buffers seen by Orbit's TS child.
- Inlay hints, code lens, semantic tokens, call hierarchy, organize imports and `source.fixAll` for scripts.
- TS-in-`<style>` analogues (CSS language features in `<style>`), a separate item if wanted.
- Workspace-wide TS diagnostics for closed `.orbit` files (that's `orbit check`), and `bun check` in `orbit dev` (§5c Q9).
- Switching `orbit check` to the same blanked extraction (it would drop `Script.Position`'s offset table); possible later, not needed.

### Risks
- **In-memory tsconfig**: TS 7.0.2 honors it, but it's not documented behavior. If a later version stops, the fallback (Q3) is to write `.orbit/lsp/tsconfig.json`, and the integration test catches the change.
- **TS 7 LSP maturity**: 7.0 is the first native release; the TS team reports 80% fewer failing language-server commands than 6.0, but a crash is possible. Orbit restarts the child once and keeps it isolated from gopls.
- **Version skew**: `bun check` (Bun's embedded 7.0.2) and a user's newer `tsc` may disagree on edge cases. `orbit check` stays the gate.
- **Broad watcher globs** from TS 7 (`/tmp/**/*`, or `~/**/*` for a project in the home directory) are why Orbit doesn't forward its registrations.
- **TS 7.1's API** may later make a plugin approach possible (references from `.ts` files). That would be a follow-up, not a reason to wait.
