# Client modules

This page lists the modules a script can import to read the data a component writes with [`orbit.JSON`](runtime-api.md#json) and [`set:json`](template-syntax.md#setjson), and how Orbit types that data from your Go types. For a walkthrough, see [Passing data to client scripts](../components.md#passing-data-to-client-scripts).

Scripts here means a component's processed `<script>` blocks and the `.ts` files they import (or that `<script src="…">` points at). There are three modules:

| Import | What it is | At runtime |
|---|---|---|
| `"./X.orbit"` (a component's file, by relative path) | `data` and `json`, typed for that component | `orbit:client` |
| `"orbit:client"` | `data` and `json`, untyped | 368 bytes minified (both functions), tree-shaken |
| `"orbit:types"` | your Go types, as TypeScript declarations | empty (use `import type`) |

The runtime is bundled once per page bundle (and once per lazy bundle that uses it), however many component modules the scripts import.

## Component modules: `./X.orbit`

Importing a component's `.orbit` file gives you **that component's data contract**. It never imports the component itself (Orbit has no framework islands): every `.orbit` import bundles to the same small reader.

```ts
import { data, json } from "./LikeButton.orbit"; // from a block script of LikeButton.orbit
import { data } from "../components/LikeButton.orbit"; // from src/scripts/like.ts
import type { Data, JSONBlocks } from "./LikeButton.orbit";
```

It exports:

| Name | Type |
|---|---|
| `data(el, key)` | `data<K extends keyof Data>(el: Element, key: K): Data[K]` |
| `json(id)` | `json<K extends keyof JSONBlocks>(id: K): JSONBlocks[K]` |
| `Data` | an interface with one property per key of the component's `orbit.JSON` `data-*` attributes |
| `JSONBlocks` | an interface with one property per `id` of the component's `set:json` blocks |

For example, with `data-post={orbit.JSON(props.Post)} data-liked={orbit.JSON(props.Liked)}` on line 9 of `src/components/LikeButton.orbit`, Orbit writes `orbit_gen/types/src/components/LikeButton.orbit.d.ts`:

```ts
// Code generated by orbit. DO NOT EDIT.
import type { api } from "orbit:types";

/** The orbit.JSON data-* attributes written by src/components/LikeButton.orbit, by dataset name. */
export interface Data {
  /** data-liked (LikeButton.orbit:9:49) */
  liked: boolean;
  /** data-post (LikeButton.orbit:9:14) */
  post: api.Post;
}
export declare function data<K extends "liked" | "post">(el: Element, key: K): Data[K];

/** The set:json blocks written by src/components/LikeButton.orbit, by id. */
export interface JSONBlocks {}
export declare function json<K extends never>(id: K): JSONBlocks[K];
```

Each property's doc comment lists where the template writes it.

### `data(el, key)`

Reads the attribute for the dataset name `key` (`"authorName"` reads `data-author-name`), parses it with `JSON.parse` and returns it. If `el` doesn't have the attribute, it throws:

```text
orbit: <like-button> has no data-post attribute
```

`Data[K]` is what the component may write on some element, not proof that `el` carries it: call `data` on the element the template puts the attribute on (in a custom element, `this`).

The keys of a component are its `data-*` attributes:

- **on HTML elements** of its template, including slot content (slot content belongs to the file it's written in, not to the component that renders it). Spread attributes (`{...attrs}`) don't count;
- **whose value is a direct `orbit.JSON(…)` call**. The call is recognized through the file's import of `github.com/orbit-z/orbit`, so an aliased import (`o "github.com/orbit-z/orbit"`, `o.JSON(…)`) works, and a function `JSON` from another package named `orbit` doesn't count. A value of type `orbit.JSONValue` that isn't a direct call (a variable, a helper that returns one) still gives a key, typed `unknown`;
- **named by the DOM's dataset rule**: `data-` is dropped, the name is lowercased, and each `-x` becomes `X` (`data-author-name` is `authorName`). A name with characters other than `a-z`, `0-9` and `-` after lowercasing isn't a key (it still renders).

A key written several times (on two elements, or in `{if}` branches) gets the union of the types, without duplicates: `posts.Post | posts.Summary`.

### `json(id)`

Finds the element with this `id` (`document.getElementById`), parses its text content with `JSON.parse` and returns it. If there's no such element, it throws `orbit: no element with id "nav-links"`.

The keys are the `id`s of the component's `<script type="application/json" set:json={…}>` blocks, when the `id` is a static string. A block with a dynamic `id={…}`, or none, gives no key; read it with `JSON.parse` yourself. The type is the mapping of the `set:json` value's type (an `orbit.JSONValue` value is typed by its argument, as in a `data-*` attribute).

### Components without data

A component with no keys (no `orbit.JSON` `data-*` attribute and no `set:json` block with a static `id`) has no module, so importing it is a type error:

```text
src/scripts/like.ts:1:22: error TS2307: Cannot find module '../components/Card.orbit' or its corresponding type declarations.
```

A component with `data-*` keys but no `set:json` keys exports `json` with no valid `id` (`K extends never`), and the other way around.

## `orbit:client`

The untyped runtime:

```ts
declare module "orbit:client" {
  export function data<T = unknown>(el: Element, key: string): T;
  export function json<T = unknown>(id: string): T;
}
```

Use it for JSON attributes that no component module types: ones written through a spread (`orbit.Attrs{"data-x": orbit.JSON(v)}`), by a component you read from another place, or by other code. The type argument is a cast, not a check:

```ts
import { data } from "orbit:client";
import type { api } from "orbit:types";

const post = data<api.Post>(el, "post");
```

Prefer the component module when there is one: it checks the key and picks the type for you.

## `orbit:types`

Every Go named type reached from an `orbit.JSON` argument or a `set:json` value, declared in `orbit_gen/types/go.d.ts` as `declare module "orbit:types"`, with **one namespace per Go package**:

```ts
declare module "orbit:types" {
  export namespace api {
    /** example.com/blog/internal/api.Author */
    export interface Author {
      name: string;
      url?: string;
    }
    /** example.com/blog/internal/api.Post */
    export interface Post {
      id: number;
      slug: string;
      title: string;
      tags: string[] | null;
      published: string;
      likes: number;
      author?: Author;
    }
  }
}
```

It only holds types, so import it with `import type` (`import type { api } from "orbit:types"`). At runtime it's an empty module.

## Type mapping

Types follow what `encoding/json` writes (Go's `json.Marshal`), by the **static type** of the value. Aliases are resolved first. Named types become named TypeScript declarations in `orbit:types` (so recursive types work, and hovers show the name); everything else is written inline.

| Go type | TypeScript | Notes |
|---|---|---|
| `bool` | `boolean` | |
| integers and floats (`int64`, `uint64` and `uintptr` too) | `number` | JavaScript numbers are exact up to 2⁵³; for larger IDs, use the `,string` option |
| `string`, `orbit.HTML`, `orbit.URL` | `string` | |
| `,string` tag option on a bool, integer, float or string field | `string` | `string \| null` for a pointer to one |
| `[]byte` | `string \| null` | base64; a `[N]byte` array is `number[]` |
| `[]T` | `T[] \| null` | a nil slice encodes as `null` |
| `[N]T` | `T[]` | |
| `map[K]V` (K a string or integer kind, or a `TextMarshaler`) | `Record<string, V> \| null` | JSON object keys are always strings |
| `*T` | `T \| null` | |
| `orbit.Opt[T]` | `T \| null` | none encodes as `null`; with `omitzero`, the field is `name?: T` |
| struct | `interface` (named) or `{ … }` (anonymous) | see [Struct fields](#struct-fields) |
| interfaces (`any`, `error`, others) | `unknown` | |
| `time.Time` | `string` | RFC 3339 |
| `time.Duration` | `number` | nanoseconds; declared as `export type Duration = number` in the `time` namespace |
| `json.Number` | `number` | |
| `json.RawMessage` | `unknown` | |
| other types whose static type implements `json.Marshaler` | `unknown` | |
| other types implementing `encoding.TextMarshaler` (value receiver) | `string` | `netip.Addr`, UUID types, … |
| a marshaler declared only on `*T`, used as a `T` | `unknown` | `encoding/json` calls it only for addressable values |
| func, channel, complex, `unsafe.Pointer`, a map with other keys | compile error | see [Unsupported types](#unsupported-types) |
| a generic instance `Page[Post]` | `Page<posts.Post>` | declared as `interface Page<T>` |

Other named types that aren't structs become type aliases (`type Status string` is `export type Status = string`). Constants don't narrow them: Go doesn't close the set of values, so `Status` isn't a union of literals.

### Struct fields

Fields follow `encoding/json`'s rules:

- Only exported fields are written, plus embedded structs (exported or not). `json:"-"` skips a field; `json:"-,"` names it `-`.
- The tag name renames a field. Names that aren't TypeScript identifiers are quoted (`"my-field": string`). Tag names are parsed as your Go version's `encoding/json` parses them (Go 1.27's follows the json/v2 engine on malformed tags).
- `omitempty` makes a field optional (`name?: T`), except on a non-pointer struct type, where `omitempty` has no effect. On a pointer, slice or map it also drops `| null`, since a nil value is left out (on a named type that includes `null`, the field is `NonNullable<IDs>`).
- `omitzero` makes a field optional, and drops `| null` the same way (nil is the zero value; an empty non-nil slice or map is still written). On an `orbit.Opt[T]`, it leaves out a none, so the field is `name?: T` (`T | null` stays when `T` itself can be `null`, such as a pointer).
- Fields of embedded structs are promoted with Go's visibility rules and `encoding/json`'s tie-breaks: the shallowest field wins; at equal depth, a tagged field wins; otherwise the conflicting fields are all left out, as `encoding/json` does, silently. Fields promoted through an embedded **pointer** are optional (a nil pointer leaves them out). An embedded field with a tag name, or of a non-struct type, is an ordinary field.

To get a non-null array from a Go slice, tag the field `omitempty` or `omitzero` (it's then optional), or make sure it's never nil and check for `null` anyway.

### Names

- Each Go package is a namespace named after the package: `posts.Post`. Two packages with the same name get the shortest distinguishing suffix of their import paths, joined with `_`: `internal_posts` and `legacy_posts`.
- Types declared in a `.orbit` frontmatter are in a namespace named after the file: `type like struct` in `LikeButton.orbit` is `LikeButton.like`.
- Names that would clash with TypeScript get a `_` suffix: keywords and predeclared types (`default`, `string`, …), and the names the generated files use (`Record`, `NonNullable`, `Element`, `Data`, `JSONBlocks`, `data`, `json`).
- Each declaration has its Go path in a doc comment (`/** example.com/blog/internal/posts.Post */`). Declarations are sorted by namespace, then name, so the output doesn't change between runs.

### Unsupported types

A type `encoding/json` can never encode is a compile error at the value: a func, a channel, a complex number, an `unsafe.Pointer`, or a map whose keys aren't strings, integers or `TextMarshaler`s, anywhere in the type (fields skipped by `json:"-"`, and unexported fields, don't count). A type that implements `json.Marshaler` or `encoding.TextMarshaler` is accepted whatever it is. Interfaces are accepted: what they hold is only known at render time.

```text
src/components/LikeButton.orbit:9:36: orbit.JSON: Post.Notify has type func(), which encoding/json can't encode
src/pages/index.orbit:16:47: set:json: the value has type func(), which encoding/json can't encode
```

What only the value shows (a NaN or infinite float, a pointer cycle, a func inside an `any`, an error from a `MarshalJSON` method) is a render error at the attribute's position. See [Troubleshooting](../troubleshooting.md#orbitjson-postnotify-has-type-func-which-encodingjson-cant-encode).

## Where the files live

| File | Contents |
|---|---|
| `orbit_gen/types/go.d.ts` | `declare module "orbit:types"`: your Go types |
| `orbit_gen/types/client.d.ts` | `declare module "orbit:client"` |
| `orbit_gen/types/src/…/X.orbit.d.ts` | the module of `src/…/X.orbit`, for each component with at least one key |

They're written with the rest of `orbit_gen/` (so they're gitignored with it) by `orbit generate`, `orbit build`, `orbit dev` and `orbit check`; only changed files are rewritten, and those of a deleted component are removed. `orbit doctor`'s freshness check covers them. The language server doesn't write them; `orbit dev` keeps them current while you work.

TypeScript finds `./X.orbit.d.ts` through `rootDirs`: the starter `tsconfig.json` has `"rootDirs": [".", "orbit_gen/types"]`, which overlays `orbit_gen/types/src/…` onto `src/…`, and includes `orbit_gen/types/*.d.ts` for the two global modules. `orbit check` adds both itself, so it works with any `tsconfig.json`; your editor needs them in yours. See [`tsconfig.json`](../styles-and-scripts.md#tsconfigjson).

If a Go package doesn't type-check, its components' modules are still written, with every key typed `unknown`; `orbit build` fails on the Go error anyway.
